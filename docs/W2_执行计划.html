01分工变更:为什么这个换法其实更好

队友要 CAD + Knowledge,于是整条泳道要重排。这不是妥协,是改进 —— 新分法把两人的耦合点从 2 个降到 1 个。

原方案新方案影响
队友Safety · CAD · ReportKnowledge · CAD主题变成「文档与图纸的解析检索」,一条线
你Supervisor · Knowledge · ScheduleSafety · Schedule · Report + Supervisor/英雄链主题变成「感知输入 → 报告产出 + 编排」
ingest/rag.py(你)/ cad.py(队友)分属两人两个文件都归队友✅ 离线管道单人所有,不用对齐格式
巡检英雄链safety(队友)→ report(队友),但图在你手里 —— 三方联调safety · report · graph.py 全在你手里✅ 演示主线零跨人协调
共享文件冲突面graph.py + ingest/ 两处只剩 graph.py 的 AGENT_REGISTRY 各加一行✅ 冲突点减半
唯一代价:队友这条线不碰视觉、你这条线不碰 RAG。两人依然各自练到 Agent 开发的全部核心动作 (prompt 外置、工具函数 + 错误信封、artifact 传引用、评测集驱动),但技术面各缺一块。 对策:每周交叉 code review 对方一个 Agent —— 这条本来就在规矩里,现在更重要。

02开工前必须清掉的两件事

这两件不做完,W2 的验收门槛无从谈起。建议 W2 第一天上午解决。

前置 A · 收口 TODO-5(半天,你做)
gyt.core.llm 的磁盘缓存与自研退避目前只有单测在调。真实路径是 get_chat_model() → 裸 ChatOpenAI → create_agent 内部直接调模型,绕开了那一层。
为什么必须现在做:W2 一旦写进 5 个 Agent,这条链路就被冻结在错误状态上; 而且「演示断网靠彩排缓存兜底」这个卖点现在是空的。
两条修法(TODOS.md TODO-5 有详细说明,二选一别都上): (a) 自定义 BaseChatModel 子类覆写 _agenerate 转调 llm.ainvoke; (b) 换官方机制 set_llm_cache + 自实现 BaseCache。
验收:补一条「真实 Agent 调用确实经过缓存/重试」的断言测试。没有这条测试,链路会静默失效到演示日。
前置 B · 评测集(各自准备自己 Agent 的,人工活)
新分工后数据集责任跟着 Agent 走,比原来清晰:
数据谁准备规格给谁用
施工规范文档队友10-20 份 PDF/docx,真实规范,带页码Knowledge 入库
RAG 问答对队友20 组:问题 + 正确答案 + 应命中的文档页码RAG 评测门槛
DXF 样例队友3-5 份,其中至少 1 份是 GBK 编码的中文图纸CAD 解析测试
工地照片你30 张,标注:合规 / 违规(违规项类型)/ 非工地干扰项Safety 评测门槛
标注是纯人工活,约各半天,而且是 W2 末验收的硬前提 —— 越早开始越好,别拖到周四。 落盘位置 data/demo/(该目录在 git 里,评测集 CSV 放 backend/eval/)。

03W2 交付清单

队友 · 检索线

① Knowledge Agent(完整交付)
规范问答,回答强制带来源文档 + 页码
② CAD 解析地基(不含查询工具)
DXF 离线解析 + 索引落盘 + GBK 样例过测。查询工具留到 W3

你 · 感知与产出线

① Safety Agent(完整交付)
kimi-k3 识图,输出结构化隐患清单
② Schedule Agent(完整交付)
SQLite 任务 CRUD + 中文自然语言查询
为什么把 CAD 的解析地基提到 W2:CAD 是最重的一个(约 3 人天)、是竞赛亮点、 也是未知数最多的一个 —— DXF 实体种类繁杂、中文编码有坑、真实图纸千奇百怪。 放到 W3 单周做完,一旦踩坑就没有恢复余地。把最有风险的解析层前移到 W2, 问题在还有两周缓冲时暴露。W3 只剩上层查询工具,那部分是确定性工作。
替代方案(不推荐):W2 每人只做一个 Agent,把 CAD 整个压到 W3 —— 节奏更轻松,但把项目最大的不确定性堆在了最后。

04任务分解 · 队友泳道

K1 · Knowledge Agent(约 2 人天 / CC 约 4h)

照 backend/README.md「加一个新 Agent 的四步」走,顺序建议:
  1. ingest/rag.py(离线管道,先做这个) —— 读 PDF/docx/md → 切块并保留页码元数据 → BGE-M3 向量化 → Chroma 落盘。必须幂等:重跑脚本不重算(D18)。 权重已在镜像里,本地首次跑会从 ~/.cache/huggingface 读。
  2. agents/knowledge/tools.py —— search_spec(query, top_k), 每个工具 @tool + @tool_guard,返回 Envelope, data 形如 [{text, source, page, score}]。检索为空要返回 fail(EMPTY_RESULT, ...) 而不是空列表 —— 让 Agent 明确知道"查不到"。
  3. prompt.md —— 两条硬要求写进提示词: ①回答必须列出来源文档名 + 页码;②检索为空时明确说「知识库里没有依据」,禁止编造。 这两条正是评测要打分的地方。
  4. __init__.py —— build_knowledge_agent(),purpose="text"
  5. 挂载 —— graph.py 的 AGENT_REGISTRY 加一行, summary 必填(它是 Supervisor 判断派活的唯一依据)
  6. 评测 —— backend/eval/ 下 20 组问答对 + 跑分脚本
门槛:RAG 评测 ≥80%(答案正确 且 引用页码命中)· 单测覆盖检索/空结果/幂等三条路径

深度上限(D6,做到这就停):10-20 份文档,不做 GraphRAG、不做 rerank、不做微调。 检索效果不好优先调切块大小与提示词,不要往上堆技术。

K2 · CAD 解析地基(约 1.5 人天 / CC 约 6h)

本周只做解析与落索引,不做查询工具(那是 W3)。
  1. ingest/cad.py —— ezdxf 读 DXF,提取:图层、尺寸标注、文字实体、块引用(构件)。 结果落盘成索引(JSON 或 SQLite),后续查询只读索引不重解析(D18:算一次用多次)。
  2. GBK 编码探测 —— 中文 DXF 的经典坑,必须有一份 GBK 样例的单测,断言中文文本实体不乱码。
  3. 坏输入处理 —— 损坏文件 / 非 DXF 伪装 → 返回 fail(FILE_CORRUPT / FILE_UNSUPPORTED), 中文人话报错。上传 DWG → 引导「请先离线转换为 DXF」(不做转换,见 TODO-4)。
  4. 文件走 artifact —— 图纸经 artifacts.register() 登记,后续只传 artifact_id, 绝不把文件内容塞进消息状态(契约 2)。
门槛:GBK 样例正确解析 · 索引落盘后可复用 · 三类坏输入均返回合法 Envelope

深度上限:仅 DXF,不碰 DWG 二进制,不做 3D / BIM。

05任务分解 · 你的泳道

S1 · Safety Agent(约 2 人天 / CC 约 4h)

动手前先做一件事(T5 已记):pin 具体 kimi-k3 视觉型号,并实测它的图片大小/尺寸限制。 这个数直接决定压缩参数,不测就写等于埋雷。
  1. agents/safety/tools.py —— analyze_site_photo(artifact_id): 取 artifact → 超限先等比压缩(PHOTO_MAX_MB=10,Pillow 压到 API 限制内, 压不下去才友好拒绝,复审 D2 已定)→ 调 get_chat_model("vision") → 返回结构化 Envelope。
  2. prompt.md —— 要求模型输出结构化检查清单: {违规项[], 位置描述, 风险等级, 整改建议}。 提示词里给足工地语境(安全帽、反光衣、高空作业、临边防护、消防通道), 并明确「看不清或不确定时说不确定,不要猜」。
  3. __init__.py —— purpose="vision"(这条别写错,写成 text 会走到 DeepSeek,而它没有视觉能力)
  4. 挂载 + 评测 —— AGENT_REGISTRY 加一行;eval/ 下 30 图跑分脚本
门槛:30 图评测 ≥80% · 超限照片自动压缩后能通过 · 损坏图返回合法 Envelope
不达标怎么办(预案已定,别临时想): 挂一个开源安全帽检测模型做前置增强 —— 先用检测模型框出人/安全帽/反光衣, 把结构化结果连同原图一起喂给 kimi-k3,让它做判断和措辞。绝不自训模型(D6 上限)。

S2 · Schedule Agent(约 1 人天 / CC 约 2h)

最轻的一个,但有一处别忘:
  1. db/ —— SQLite 建表。预留 project_id 字段(成本≈0, 但赛后做多项目隔离时能省一半迁移工作量,TODO-3)。SQL 全参数化。
  2. tools.py —— create_task / list_tasks / update_status / query_by_date。 列表查询一次取全,禁止循环内逐条查(N+1)。
  3. 中文自然语言日期 —— 「下周三之前」「这个月底」要能解析。 这是纯逻辑,适合先写测试再写实现,边界用例写足(跨月、跨年、模糊表达)。
  4. prompt.md + 挂载
门槛:CRUD 四条 + 中文日期解析 + 空结果,单测全覆盖

深度上限:站内提醒即可,不做短信 / 日历推送。

06W2 验收门槛(周末对一次)

门槛负责人不达标怎么办
RAG 评测 ≥80%(20 组问答对,答案对 + 页码命中)队友先调切块大小与提示词,别加技术栈
Safety 评测 ≥80%(30 张标注图)你触发预案:挂开源安全帽检测模型做前置增强
CAD:GBK 样例解析正确 + 索引可复用队友W3 还有余量,但要在周末如实说出来
Schedule:CRUD + 中文日期单测全过你纯逻辑,不过就是没写完
CI 保持全绿,覆盖率 ≥80%两人红了当天修,不许攒
门槛的意义是「当周暴露」,不是「当周为难人」。 达不到就当周说出来、当周触发预案 —— 最怕的是「感觉差不多」一路自我安慰到演示前一周, 那时候没有任何工期可以救。这也是 D15 把评测门槛绑成里程碑验收条件的原因。

07协作规则(就这几条,记住)

文件规则为什么
graph.py 的 AGENT_REGISTRY唯一共享写入点。各加各的行,不重排别人的行,冲突了保留双方W2 两人各加一行,是本周唯一的冲突面
graph.py 其它部分只归你改Supervisor 与英雄链是你的活
core/ 四件套改动需两人一致同意,且不新增第 5 个文件D12 护栏:防止两个学习者把基座盖成自建框架
config.py各自常量加在自己那一段(带注释分区),不动别人的常量集中的代价就是共享写入,靠分区约定化解
ingest/全归队友新分工的直接好处:离线管道单人所有
提交前make lint + make test 必过;改过 workflow 还要 make lint-ciCI 红了大家都得停

每周交叉 review:你审队友一个 Agent,队友审你一个。新分工后两人技术面各缺一块, 这条从「好习惯」升级成「必要动作」。

08风险与预案

风险征兆预案
Safety 识别率上不去30 图评测卡在 60-70%已定:挂开源检测模型做前置增强,不自训
真实 DXF 千奇百怪,解析器覆盖不了换一张图纸就报错W2 前移就是为这个。收窄到演示用的 3-5 份图纸,把「支持哪些实体类型」写进文档,别追求通用
规范文档检索不准引用页码经常错先调切块(按条款切而非按固定长度),再调提示词。不要上 rerank / GraphRAG
评测集标注拖到周末周四还没开始标门槛无法验收 = W2 无法收尾。周一就开始,每天标一点
TODO-5 没收口没人认领断网兜底是空的,演示日一次 429 就翻车。W2 第一天解决
两人同时改 config.py 冲突每次拉取都冲突分区约定;冲突了保留双方,别删对方的常量
