01 / 机制

一次提问,消息逐跳去了哪

场景:点上传按钮发一张工地照片,说「查一下这张照片,顺便出份巡检记录」。这正是真机验收 C1/C2 断言的那句话。

为什么「保留兄弟 Agent 的发言」是命根子。Envelope 已经在回灌那一刀里被丢了。所以 FocusOnOwnWork 滤网只滤 supervisor 的派活腔,兄弟的那段人话是跨 Agent 数据流的全部载体——再滤一次就是零。第一版滤网连兄弟成果一起滤,巡检跑完用户说「把这些隐患记成整改任务」,schedule 两眼一抹黑,只能反问「你说的隐患具体是什么」。

02 / 形态

三种联动,可靠性与说服力正好相反

硬边

safety══▶report

写死的图边,不经 LLM。彩排一百次成功一百次,载荷全量双向、连合成交接消息都没有。

弱点:评委会问「这跟一段 if 有什么区别」——答案是没区别,而这正是故意的。用刻意去掉智能的环节去证明智能,是自相矛盾的。

动态跳

inspection→supervisor→schedule

supervisor 真决策。用户只说「把这些隐患记成整改任务,下周一之前搞定」,它转给一个跟照片毫无关系的同事,还把上一位的结论当标题带过去了。

两个 Agent 之间零联动代码。有库级铁证(D3:整改任务真实落库、期限=下周一)。

单跳

supervisor→safety / schedule

一问一答。schedule 的四工具(记/查/改/销)+ safety 的识图,是使用频次最高的形态。

负向也算能力:模糊请求会追问不乱派,超范围如实说做不了、且严禁再发交接工具(手嘴一致规则)。

演示别二选一。硬边证明「可靠」,动态跳证明「真的是多智能体」。分开演,任何一个都要挨一刀:硬边像流水线,动态跳像待办 App。合起来,转折点本身就是论证——顺序必须 硬边 → 动态跳,因为后者需要前者产出的隐患内容才成立。

05 / 化学反应

最平淡的那个 Agent,是整套系统的主心骨

看代码就明白了:safety / inspection / knowledge / cad 全是「读」,只有 schedule 是「写」。前四个都是一问一答、答完就散的无状态问答;db/tasks.py 是整个系统里唯一一处把东西留下来的地方。

① 事实 → 承诺

safety 的输出是一个事实判断(「这儿有临边无防护」),它本身不推动任何事情发生。schedule 给它接上了责任的时间维度——「8月10日之前」。这是从「知道」到「办了」之间唯一的桥。

② T 号 = 复检锚点

复检时最难的一句是「上次说的到底是哪几处」。T3 就是这个锚点,而且可以在电话里口头传递——刻意做成「T3」而不是 32 位 hex。工人在噪音里对着手机喊「T3 干完了」,系统认;喊一串十六进制,不可能。

③ 唯一能答「我今天该干什么」

其它四个只能被动应答;schedule 因为有 due_date 与 today 的比较,是唯一能主动指出优先级的——逾期的排最前。早上七点那张表第一行标着「已逾期」的,就是现在最该管的事。

结构性结论:没有 schedule,这套系统的多 Agent 协同只是「多问了几次」;有了它,才叫工作流。演示顺序上它应该同时出现在开头和结尾——开头查欠账定调,结尾销项收口,中间的照片和条文都是为了填这张表。

边界别在演示里许诺:台账没有责任人字段、没有任何提醒推送、粒度只到天(「明天上午」的「上午」会被剥掉)、没有周期任务。

06 / 增量

三个此前没被记录的问题 新

这三条不在任何注释、commit 或 TODOS 里。前两条已用假模型探针在本机实测验证(不联网、不花钱)。

发现 1走英雄链时,safety 的隐患明细根本不进顶层上下文——「保留兄弟发言」这条修复在这条路径上是无效的

机理:output_mode="last_message" 只回灌子图的最后一条消息,而 inspection 的最后一条是 report 的话。safety 的明细留在子图内部,从未写进顶层 messages。

实测:用假模型跑真 create_supervisor + safety→report 子图,顶层 7 条消息里 safety 那句「…临边无防护」完全不存在,只剩 report 的一句总结。

后果:C3(巡检后记整改任务)之所以能过,是因为断言只要求标题含「整改/隐患」;库里那条真实标题里的违规项,只可能来自 report 提示词要求的「点名重大项」——也就是说明细能不能传下去,取决于 report 那句话说得够不够全,这是概率性的,不是结构性的。

建议:给 inspection 用 full_history,或让 report 的信封 user_msg 显式带上完整 violations 列表(现在只报数量和最高级别)。

发现 2recursion_limit=8 与提示词直接冲突:实测顶层最多派 3 次活、子 Agent 最多 3 轮工具

实测(本机,langgraph 1.2.10):一次派活 = 2 个顶层超步,收尾 1 个 → 2N+1。三件事 7 步贴着上限,四件事 9 步当场熔断。而子 Agent 内部连续工具轮第 4 轮熔断。

冲突点:supervisor 提示词规则 2 要求「一句话里有多件事就拆开、一位一位派」;schedule 提示词要求「一条一条记,每条调一次工具」;上传钩子会把 4 张照片的编号全列出来而 safety 要求「一个一个来」。三处提示词都在鼓励模型去撞那个 8。

会炸的真实句子:「先看这张照片有没有隐患,再出份巡检记录,把隐患记成整改任务下周一之前,顺便把 T2 也改到周五」= 4 跳。或「记 4 条任务:…」= 4 轮工具。

连带发现:熔断不回滚已落库的写入——每个 db 操作独立连接独立提交,没有跨工具事务。「记 4 条」在第 4 轮炸掉时前 3 条已经真的进库了,而用户看到的是英文报错;重试一次就变成 6 条+3 条重复行。

还有:这一个数字同时绑了两个语义(顶层派活次数 / 子 Agent 工具轮数)。想让 schedule 支持一次记 5 条,就必须同时放宽 supervisor 的派活次数。应该拆成两个旋钮。

发现 3熔断在舞台上会出一个英文报错,后端零处理

已核实:grep GraphRecursionError backend/src/ 只命中 graph.py:377 的一句注释,没有任何 handler。而 Agent 路径的错误文案中文化是 TODO-9,未做。

用户实际看到:toast.error("An error occurred. Please try again.") + Recursion limit of 8 reached…。而这个 toast 在上游文件 thread/index.tsx 里,不是三个覆盖件之一——换机器重新生成前端也不会变。

合起来看:发现 2 说明三跳就到顶、四跳就炸,发现 3 说明炸了会出英文。演示时评委一句话里塞四件事,就能同时踩中这两条。

另外几条较轻但值得记

  • SUPERVISOR_NAME 两处手工同源,零测试守着(已核实:graph.py:144 与 focus.py:50 各定义一份,测试只断言「节点名在图里」)。改名 → 滤网静默失效 → 派活腔传染原样复发,而没有任何测试会红。
  • 滤网只按 name 判定,而流式期消息可能还没带 name。前端已为这个现象打过补丁(注释写着「只按 name 折叠的话这句英文会先裸奔一会儿,真机截图踩过」),同一个现象在后端未被考虑——若某条 supervisor 消息进入子 Agent 上下文时 name 为空,传染通道就重新打开。
  • 上传钩子只看 messages[-1]。若前端一次提交带两条 human 消息、或流式中断后重发,倒数第二条里的 image 块会原样留在 state 里,下一次任何模型调用都会 400——正是「点了发送没反应」那个现象。
  • pydantic 参数校验发生在 tool_guard 之前,英文报错会绕过信封契约直送 Agent,然后被「如实转述 user_msg」讲给工人听。
  • 内部绝对路径进了 LLM 上下文(report/tools.py:176 把 str(path) 放进 data)。三条硬约束只管住了 detail,data 不在约束范围内——不算违规,但与「不出现内部路径」的取向不同调。
  • 评测词表的指路牌指向错文件:scorers.py 和 eval/README.md 都写「同源位置 = safety/prompt.md」,而词表实际在 vision_prompt.md。照着指路牌去改的人会改错文件。

08 / 边界

用户一定会问、而系统做不到的三件事

危险度按「回答看起来有多像成功」排——报错不可怕,可怕的是看起来成功了。

N3「这条派给老张,明早八点提醒他」
最危险

会发生:「老张」被当成标题的一部分记进去,「早上」被日期解析剥掉、「八点」进不了库(粒度到天),提醒那半句被静默丢掉。

为什么最危险:三个里唯一一个看起来完全成功的。用户以为老张明早会收到提醒,老张什么都收不到,活就漏了。

建议:schedule 提示词加一条——听到「提醒/通知/派给某人」必须明说「台账只记事和期限,提不了醒也记不了责任人,你记完自己跟工友说一声」。

N2(贴整改后的照片)「你看看,这回整改好了没」
高

会发生:当成一张全新的、无上下文的照片独立判读,只会说「这张里没看到这 8 类问题」。不会说「上次那处临边已整改」,也不知道「上次」是哪张。

为什么危险:回答看起来是成功的,用户很容易读成「系统确认整改完成了」,而系统其实只是没在新照片里看见问题。这是一次语义偷换,不是一次报错。

根因:没有 compare_rectification(before,after) 这类工具;照片与 T 号之间零字段关联。TODO-21 列为「可选、约半天」,至今未做。

N1「今天的施工日报给我出一份」
中

会发生:大概率派给 inspection(summary 里有「出报告/留档」这些钩子),然后向用户要照片编号,拿到后仍然只能出单张照片的巡检记录;追问才会如实说「日报功能还没上线」。

根因:报告工具吃的是一张照片;日报需要隐患台账的多条聚合,而库里只有 tasks 表,没有隐患表。

建议:会诚实说做不了,但路由绕一圈才说,体验难看。演示前给一条「日报直接回绝」的短路。

评委必问的四个,答案要落到代码

①模型分档做不到单体:只有识图那一个工具内部直调 Kimi($3/M),其余全走 DeepSeek($0.14/M)。单体架构里图片必然进消息历史,每轮把几 MB base64 重发一遍。

怎么保证它不胡说?

四层,每层都能就地翻代码:提示词红线(编号页码尤其不许顺手补全)→ 结构件兜底(因为提示词只是概率生效)→ 确定性下沉(日期换算、隐患定级、报告内容全从模型手里拿走)→ 可量化且可证伪(评测集故意放 5 张非工地干扰项 + 7 张合规照)。

杀伤力最大的一句:「我们连不许悄悄修好都写进了代码。模型吐出受控词表以外的词,工具原样透传不做纠正——因为在这里修好,评测就永远发现不了提示词坏了。让错误可见,比让它消失更重要。」

90% 是怎么算的?会不会自己给自己判卷?

标准答案人定(铁律第一条:让 AI 生成标准答案再考 AI,分数没有任何意义);分母有硬闸(可判分行少于 30 就不跑模型直接判不通过);判分集合完全相等才算对,不给部分分。
