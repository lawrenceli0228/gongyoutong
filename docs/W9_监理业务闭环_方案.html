工友通 W9 · 实施方案

监理业务闭环
评估与实施方案 v3

把系统从「工友与安全员的随手工具」扩到监理工程师的法定职责链。 依据是《建设工程安全生产管理条例》(国务院令第 393 号)第十四条 —— 需求里描述的四步,在法条里其实是同一条的四句话。

v1、v2 均已作废,别照它们实施

v1 是评估稿;v2 吸收了 Claude 评审 15 个定案 + Claude 子代理 18 条; v3 吸收 Codex 复审 23 条(8 阻断 / 11 高 / 4 中),新增 D17、D18 两个定案。 建表语句、状态机、工具/端点划分在 v3 里都变了。

当前不能满足。十个动作里,一个全有、三个半有、六个全无。

缺口不是六个功能,而是一件地基:隐患在系统里没有身份。

现在的链条是「拍照 → 识别 → 渲染 docx → 完」。docx 落盘那一刻,这条隐患就从系统里消失了 —— 没有编号可追、没有状态可变,没法回答「上周那个临边无防护改了没」。

三层地基是现成的,缺的只有中间那层

感知层 safety 识别 8 类隐患 + severity.py 确定性定级 · 产出层 python-docx 渲染 + artifacts 落盘与编号 · 检索层 knowledge 带页码出处 + 全局/项目双作用域。缺的是它们之间的状态与流程。

0 / Verdict

覆盖度
1
全有 —— 巡查发现隐患
3
半有 —— 定级 / 要求整改 / 复查销项
6
全无 —— 方案审查、暂停令、报建设单位、报主管部门、汇总、专项报告

「半有」三条都差在关键处:定级差的是监理要的「一般/严重」二分,而那个二分决定后面走哪条路; 要求整改差的是《监理通知单》,现在的巡检记录与任务是两个孤岛;复查销项差的是证据 —— 现在一句话就能销。

为什么「隐患要有身份」是这条链的支点

环节为什么必须有身份
签发监理通知单通知单正文要引用隐患编号,否则无法指认改什么
签发工程暂停令停工要举证是哪一条严重隐患导致的
复查销项销的是那一条隐患,不是「一件事」
定期汇总统计的对象就是隐患集合
上报主管部门举证链 =「我通知过 + 期限到了 + 复查过 + 他没改」,全是隐患的历史状态

1 / Mapping

逐动作对照
#监理动作现状差什么
1事前审查专项方案是否符合强制性标准全无 knowledge 只能一问一答查条文,没有「审查」这个动作
2巡查发现隐患现成—
3隐患定级半有 有四档技术定级,没有监理口径的一般/严重二分
4一般隐患 → 要求整改半有 没有《监理通知单》;巡检记录与任务互不关联
5严重隐患 → 责令暂停施工全无 《工程暂停令》没有;更要命的是没有分级分岔
6及时报告建设单位全无无送达动作、无留痕
7复查销项半有 销的是「任务」不是「隐患」;销项不要求任何证据
8拒不整改 → 报主管部门全无无升级判定、无《监理报告》
9定期汇总全无report 只会做单张照片
10重大隐患专项报告留档全无—

2 / Prerequisites

两个前置

前置 A:语料是空的 —— 这是你或队友要做的事

《建设工程安全生产管理条例》现在不在库里

data/demo/docs/ 里只有一份 GB-50016-2014-建筑设计防火规范2018版.pdf。 现在拿监理职责问 knowledge,它会如实答「知识库里查不到」—— 这是正确行为,但意味着 F1 的依据是一片空白。

要补的 PDF用途
《建设工程安全生产管理条例》(国务院令 393 号)整条业务链的法定依据
《建设工程监理规范》GB/T 50319-2013通知单/暂停令/复工令/监理报告的标准表式在它附录里
《危险性较大的分部分项工程安全管理规定》(住建部 37 号令)F1 审查清单来源
《建筑施工安全检查标准》JGJ 59-2011隐患分级的行业依据
⚠️ 本文引用的条文号、表号一律以 PDF 原文为准,别照抄本文

写作时这四份都不在库里,条文映射是凭记忆写的 —— 而「凭记忆写规范」正是本项目从第一天就禁止的事。

前置 B:签发人没有身份 —— D15 已化解,不再阻塞

定位成「AI 出稿、总监理工程师签字生效」,不是「演示件」

每份文书固定印一句「本稿由工友通生成,经总监理工程师签字后生效」,签字栏留空。 这本来就是真实监理工作流,与 safety/report 已宣告的「初筛与记录,最终判定归持证人员」一脉相承。

代价要说清:这套系统因此只能声称实现了法定职责链的「记录与出稿」部分,不能声称实现了职责链本身。

CREATE TABLE IF NOT EXISTS hazards (
  hazard_no       TEXT NOT NULL UNIQUE,      -- GYT-H-YYYYMMDD-HHMMSS-4hex
  project_id      TEXT NOT NULL DEFAULT '',  -- D6:取不到就空串,不是 NULL
  photo_sha256    TEXT NOT NULL,             -- D14:内容哈希,不是 artifact_id
  item            TEXT NOT NULL,             -- 受控词表 8 选 1

  doc_no      TEXT NOT NULL UNIQUE,

CREATE TABLE IF NOT EXISTS hazard_ingest_failures (   -- Codex#10:只写日志的话进程一重启就失忆

🔴 有外键,所以 PRAGMA foreign_keys = ON 必须在 with conn: 之外

事务内是 no-op(db/projects.py:137 有原注释)。放进事务里 = 全库外键静默失效、零报错。

🔴 status 的语义边界

status=suspended 只证明暂停令已出稿,不证明工地真停了工; owner_report 只证明报告已生成,不证明建设单位收到了。

升级判定与汇总在措辞上必须如实:「已出具暂停令」而不是「已责令停工」。

was_suspended 这一列是 Codex#6 的修法

原设计里 notified 与 suspended 复查失败后都坍缩成 reinspect_failed, 再次合格时状态机分不清该直接关闭还是必须先出复工令 —— 漏发或滥发复工令。 用一列布尔记住「曾经停过工」,分支就恢复了。

🔴 ALLOWED_TRANSITIONS 放 db/hazards.py,不放 agents/supervision/

Codex#22:全仓 db/*.py 只 import gyt.config,而 agents/*/tools.py import gyt.db —— 方向严格是 agents → db。 反过来有循环导入风险,且存储层不能独立使用。

severity → grade 映射 D4

safety 定级gradeneeds_grading理由
重大(高空未系安全带、动火无监护)严重0直接威胁生命,应停工处理
较大(临边无防护、用电隐患、消防通道堵塞)严重0系统性缺陷,影响一片人
一般(未戴安全帽、未穿反光衣、材料堆放混乱)一般0个人防护单项缺失
待定级(词表外)一般1不知道 ≠ 不严重
🔴 needs_grading=1 时所有签发工具硬拒(Codex#11)

原设计只是「标注需人工定级」,但没有任何东西拦着它 —— 未知风险可以按一般隐患走完整闭环并被销项。 现在:必须先由人在界面上定级(改 grade + 清零 needs_grading)才能签发。

🔴 三条硬拦(全在服务端代码里,不靠提示词)

① notice 对 grade='严重' 拒绝并提示走 suspend —— Codex#3 抓到 v2 写「任何 grade 都可签」,于是严重隐患仍能只出通知单绕过三文书组合, 我声称已硬拦的漏处置其实还在。

② suspend 对 grade!='严重' 拒绝。

③ 任何签发对 needs_grading=1 拒绝。

🔴 due_date 必须解析成功(Codex#12)

端点收 due_phrase(用户原话),复用 agents/schedule/dates.py(314 行) 解析。 解析不出就 fail,不许留空 —— due_date 为空的隐患永远进不了超期清单, 也就永远不会被升级。

F3 复查销项 D11

复查照片上传 → POST /reinspect-suggest
    │ 调识别半 _recognize(不登记)
    ▼
  「改前/改后」两组判断并排 + 建议结论     ← 只是建议
    ▼
  人在界面点确认 → POST /reinspect-result {result: pass|fail}
    ▼
  pass 且 was_suspended=0 → closed
  pass 且 was_suspended=1 → resuming(等《复工令》)
  fail                    → reinspect_failed
🔴 after_photo_id 必填,拿不到照片就没有任何路径能改成 closed

真机已经抓到过模型不调工具、凭记忆编回执「销了:T1 已完成」而库里还是 open。 同样的失效换到监理场景,后果是「隐患已消除」被写进留档文书,而现场原样没动。

为什么结论由人下:复查照片角度光线取景都变了,「没拍到那个部位」和「问题已消除」 在模型眼里一样 —— 那是往「误判合格」方向错,而这一侧会死人。

F5 supervision Agent

🔴 销项与改期都只有一个出口 D13

tasks 加一列可空 hazard_no。带 hazard_no 的任务: finish_task 拒绝转走复查流程;reschedule_task 拒绝转去改隐患的 due_date(Codex#13:否则两边期限继续分叉)。

不这么做的后果:工友走 TODO-21 认可的对的路在 schedule 里销了项/改了期, hazards 还是 open/旧期限 → 超期 → 系统建议签发《监理报告》指控施工方拒不整改。

🔴 守卫只管子 Agent,管不到最后一跳(Codex#18)

最终用户回复由 supervisor 汇总,而 supervisor 只有提示词约束。 结构性修法是把编号的权威显示面放到前端卡片上 —— 卡片直读工具结果里的 doc_no, supervisor 的文字转述只是陪衬。用户点的是卡片,不是那段话。
