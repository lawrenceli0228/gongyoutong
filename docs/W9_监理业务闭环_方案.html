监理业务闭环
评估与实施方案 v2

把系统从「工友与安全员的随手工具」扩到监理工程师的法定职责链。 依据是《建设工程安全生产管理条例》(国务院令第 393 号)第十四条 —— 需求里描述的四步,在法条里其实是同一条的四句话。

v1 已作废,别照它实施

v1 是评估稿。经 /plan-eng-review 四章节评审 + 一轮独立外部挑错(18 条,核实 7 条全部属实), 15 个议题定案已全部回写。v1 的 DDL、编号表、状态机图都是决定之前的旧版。

当前不能满足。十个动作里,一个全有、三个半有、六个全无。

缺口不是六个功能,而是一件地基:隐患在系统里没有身份。

现在的链条是「拍照 → 识别 → 渲染 docx → 完」。docx 落盘那一刻,这条隐患就从系统里消失了 —— 没有编号可追、没有状态可变,没法回答「上周那个临边无防护改了没」。

三层地基是现成的,缺的只有中间那层

感知层 safety 识别 8 类隐患 + severity.py 确定性定级 · 产出层 python-docx 渲染 + artifacts 落盘与编号 · 检索层 knowledge 带页码出处 + 全局/项目双作用域。缺的是它们之间的状态与流程。

0 / Verdict

覆盖度
1
全有 —— 巡查发现隐患
3
半有 —— 定级 / 要求整改 / 复查销项
6
全无 —— 方案审查、暂停令、报建设单位、报主管部门、汇总、专项报告

「半有」三条都差在关键处:定级差的是监理要的「一般/严重」二分,而那个二分决定后面走哪条路; 要求整改差的是《监理通知单》,现在的巡检记录与任务是两个孤岛;复查销项差的是证据 —— 现在一句话就能销。

为什么「隐患要有身份」是这条链的支点

环节为什么必须有身份
签发监理通知单通知单正文要引用隐患编号,否则无法指认改什么
签发工程暂停令停工要举证是哪一条严重隐患导致的
复查销项销的是那一条隐患,不是「一件事」
定期汇总统计的对象就是隐患集合
上报主管部门举证链 =「我通知过 + 期限到了 + 复查过 + 他没改」,全是隐患的历史状态

1 / Mapping

逐动作对照
#监理动作现状差什么
1事前审查专项方案是否符合强制性标准全无 knowledge 只能一问一答查条文,没有「审查」这个动作
2巡查发现隐患现成—
3隐患定级半有 有四档技术定级,没有监理口径的一般/严重二分
4一般隐患 → 要求整改半有 没有《监理通知单》;巡检记录与任务互不关联
5严重隐患 → 责令暂停施工全无 《工程暂停令》没有;更要命的是没有分级分岔
6及时报告建设单位全无无送达动作、无留痕
7复查销项半有 销的是「任务」不是「隐患」;销项不要求任何证据
8拒不整改 → 报主管部门全无无升级判定、无《监理报告》
9定期汇总全无report 只会做单张照片
10重大隐患专项报告留档全无—

《建筑施工安全检查标准》JGJ 59-2011隐患分级的行业依据grade 映射表没人背书
⚠️ 本文引用的条文号、表号一律以 PDF 原文为准,别照抄本文

写作时这四份都不在库里,条文映射是凭记忆写的 —— 而「凭记忆写规范」正是本项目从第一天就禁止的事。

前置 B:签发人没有身份 —— D15 已化解,不再阻塞

定位成「AI 出稿、总监理工程师签字生效」,不是「演示件」

每份文书固定印一句「本稿由工友通生成,经总监理工程师签字后生效」,签字栏留空。 这本来就是真实监理工作流,与 safety/report 已宣告的「初筛与记录,最终判定归持证人员」一脉相承。

代价要说清:这套系统因此只能声称实现了法定职责链的「记录与出稿」部分,不能声称实现了职责链本身。 身份体系(TODO-3)从硬前置降为欠账。

4 / Foundation

F0 —— hazards 隐患台账 + 状态机

新模块 backend/src/gyt/db/hazards.py。先做 D9 的前置重构再写它。

CREATE TABLE IF NOT EXISTS hazards (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  hazard_no       TEXT NOT NULL UNIQUE,      -- GYT-H-YYYYMMDD-HHMMSS-4hex
  project_id      TEXT NOT NULL DEFAULT '',  -- D6:取不到就空串,不是 NULL
  photo_sha256    TEXT NOT NULL,             -- D14:内容哈希,不是 artifact_id
  photo_id        TEXT NOT NULL,             -- 首次发现那张照片的 artifact_id(展示用)
  item            TEXT NOT NULL,             -- 受控词表 8 选 1
  severity        TEXT NOT NULL,             -- 重大/较大/一般/待定级 ← safety 直出
  grade           TEXT NOT NULL CHECK (grade IN ('一般','严重')),
  grading_version TEXT NOT NULL,             -- D4:定级规则版本快照
  status          TEXT NOT NULL CHECK (status IN
                    ('open','notified','suspended','reinspect_failed','resuming','closed','escalated')),
  due_date        TEXT,                      -- 整改期限(HK 日历日)
  found_at        TEXT NOT NULL,
  closed_at       TEXT,
  created_at      TEXT NOT NULL,
  updated_at      TEXT NOT NULL,
  UNIQUE (photo_sha256, item)              -- D14:幂等键
);

CREATE TABLE IF NOT EXISTS hazard_docs (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  hazard_no   TEXT NOT NULL,
  doc_type    TEXT NOT NULL CHECK (doc_type IN
                ('notice','suspension','resumption','owner_report','authority_report','reinspect')),
  doc_no      TEXT NOT NULL UNIQUE,           -- 外部意见 #9
  artifact_id TEXT,   photo_id TEXT,   result TEXT,
  created_at  TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_hazard_docs_no ON hazard_docs(hazard_no);
🔴 status 的语义边界(外部意见 #3)

status=suspended 只证明暂停令已出稿,不证明工地真停了工; owner_report 只证明报告已生成,不证明建设单位收到了。

升级判定与汇总在措辞上必须如实:「已出具暂停令」而不是「已责令停工」。 送达与执行确认不在本批范围。

状态机 D3 D5

                    safety 判出违规项

                          │
              ┌───────────┴───────────┐   ← 分岔由 grade 决定,代码判,不是 LLM 判

              │                       │
       《监理通知单》         《监理通知单》+《工程暂停令》+《致建设单位报告》
              │                       │      ↑ 三份由一次工具调用原子产出
          notified                suspended
              │                       │
              └──────────┬────────────┘
                         │  复查(必须挂复查照片;模型给建议,人下结论 — D11)
              ┌──────────┴──────────┐
          人确认合格            人确认不合格 / 超期未改
              │                       │
      ┌───────┴───────┐         reinspect_failed
   原为 notified   原为 suspended        │  再复查 ┄┄┄┄┄┘
      │               │                  │  或升级
   closed        resuming ──《工程复工令》──► closed

ALLOWED_TRANSITIONS 写在 agents/supervision/states.py,是这张图的唯一真相; db 层每个迁移函数的 WHERE status IN (...) 从它派生,靠 rowcount 判成败, 不许信先读的快照(同 db/tasks.py:136-138 的写前守卫)。

severity → grade 映射 D4

safety 定级grade理由
重大(高空未系安全带、动火无监护)严重直接威胁生命,应停工处理
较大(临边无防护、用电隐患、消防通道堵塞)严重系统性缺陷,影响一片人
一般(未戴安全帽、未穿反光衣、材料堆放混乱)一般个人防护单项缺失
待定级(词表外)一般 + 需人工定级不知道 ≠ 不严重,但也不能自动触发停工

模块级常量 GRADING_VERSION,改表必须 +1(单测盯住)。写入 hazards 时快照。

5 / F2 · F3 · F5

文书 · 复查 · Agent 挂载

F2 分级处置文书

工具产物触发条件(代码强制)
issue_notice(hazard_no, due_phrase)《监理通知单》任何 grade
issue_suspension(hazard_no, due_phrase) 《监理通知单》+《工程暂停令》+《致建设单位报告》三份原子产出 grade=严重 才允许,一般隐患直接 fail
issue_resumption(hazard_no)《工程复工令》仅 resuming 态
🔴 两条红线

① if grade != '严重': return fail(...) 必须硬拦。「一般隐患签了暂停令」与 「严重隐患只发通知单」是两个方向相反的事故 —— 本项目三次栽在「用提示词管住模型行为」上。

② due_phrase 收用户原话,不收日期。agents/schedule/dates.py 用 314 行证明了模型换算中文日期不可靠,红线是「模型只传原话,代码来算」。 算错的是法定整改期限,而超期升级直接读它。

谁能按下停工按钮:走 HTTP 端点 + 前端确认,不走 Agent 工具

Agent 只能「建议签发」,实际签发要人在界面上点。与 W7 打卡「写入不走 LLM」同构 —— 那次理由是防编造,这次更硬:法律行为不能由概率性系统单方面触发。

F3 复查销项 D11 D14

reinspect_hazard(hazard_no, after_photo_id)
    │ 调识别半(不登记 — D14)看复查照片
    ▼
  把「改前/改后」两组判断并排给人看 + 给出建议结论
    ▼
  人在界面上确认:合格 / 不合格     ← 结论由人下,照片是证据不是判据
🔴 after_photo_id 必填,拿不到照片就没有任何路径能改成 closed

真机已经抓到过模型不调工具、凭记忆编回执「销了:T1 已完成」而库里还是 open。 同样的失效换到监理场景,后果是「隐患已消除」被写进留档文书,而现场原样没动。

为什么结论由人下:复查照片角度光线取景都变了,「没拍到那个部位」和「问题已消除」 在模型眼里一样 —— 那是往「误判合格」方向错,而这一侧会死人。

F5 supervision Agent

🔴 销项只有一个出口 D13

hazards 保持独立表,但 schedule.finish_task 对由隐患派生的任务不直接销 —— 它转去走 supervision 的复查流程(要照片、要人确认)。tasks 加一列可空 hazard_no。

不这么做的后果:TODO-21 认可的协同一手是「巡检 → 一句话记整改任务」。工友走那条对的路 在 schedule 里销了项,hazards 还是 open → 超期 → 系统建议签发《监理报告》指控施工方拒不整改 —— 一份建立在我们自己记乱账上的对外指控。措辞划界拦不住这个。

🔴 防假账守卫要写第三种判据(外部意见 #5)

现成两件都不适用:首答判据会把「建议签发暂停令,请点界面上的按钮」这句最重要的正确回答顶替掉; 编号溯源判据会把用户自己打进来的 GYT-H-… 判成编造(_sourced 只扫 ToolMessage)。

第三种:扩展 _sourced 让它同时扫本回合的 HumanMessage —— 用户自己报的编号是合法出处。

analyze 内部拆两半:

    _recognize(artifact_id) -> 五键判断        ← 纯函数,零副作用
         ↑                            ↑
   analyze_site_photo            reinspect / eval/hooks

  • 幂等键 = UNIQUE(photo_sha256, item),不是 artifact_id —— core/artifacts.py:208 是 uuid4().hex,同一张照片重传就是新号,彩排三轮会得三批

时间与编号 D7

唯一时间权威 = attendance/receipt.py 的 HK = ZoneInfo("Asia/Hong_Kong")。 found_at / due_date / closed_at / 超期判定 / 所有文书编号,全部走它。 不许用 datetime.now(UTC).astimezone() —— 那是宿主时区(report/tools.py:151 现在就踩着,容器是 Shanghai、数值一致纯属巧合,已记 TODO-41)。

对象编号对象编号
隐患GYT-H-…工程复工令GYT-FG-…
监理通知单GYT-TZ-…致建设单位报告GYT-JS-…
工程暂停令GYT-ZT-…监理报告(报主管部门)GYT-JB-…

形式 GYT-<类型>-YYYYMMDD-HHMMSS-4hex,后缀用 secrets.token_hex(2)。 用随机后缀而不是日内序号 —— 序号要先数再加一,check-then-act 竞态,而批量签发正是会撞的场景。

熔断与原子性(外部意见 #10)

config.py:210 是 supervisor_recursion_limit = 8。严重隐患若要三次工具调用出三份文书, 加上先查一次 = 9 步,顶穿熔断;炸在第三份之前时前两份已落盘、hazard_docs 已插行、 状态已改,没有任何一步能回滚。

定案:三份文书由 issue_suspension 一次调用原子产出,一个事务写三行。 不提高 recursion_limit(那只是把问题往后推)。
