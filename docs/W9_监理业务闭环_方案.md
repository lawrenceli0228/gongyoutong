# W9 监理业务闭环 —— 现状评估与实施方案

> 起因:要把系统从「工友/安全员的随手工具」扩到**监理工程师的法定职责链**。
> 依据是《建设工程安全生产管理条例》(国务院令第 393 号)**第十四条**。
>
> **2026-08-16 v3** —— v1 评估稿、v2 吸收 Claude 评审 15 定案 + Claude 子代理 18 条。
> v3 吸收 **Codex 复审 23 条**(8 阻断 / 11 高 / 4 中),新增 D16–D18 三个定案。
> **v1、v2 均已作废**,照本文实施。定案清单见 §7。

## 0. 一页纸结论

**当前不能满足。** 十个动作里,一个全有、三个半有、六个全无。

缺口不是六个功能,而是**一件地基**:隐患在系统里没有身份。

现在的链条是「拍照 → 识别 → 渲染 docx → 完」。docx 落盘那一刻,这条隐患就从系统里
消失了 —— 没有编号可追、没有状态可变、没法回答「上周那个临边无防护改了没」。

而监理这条链的每一环都建立在「隐患有身份」之上:

| 环节 | 为什么必须有身份 |
|---|---|
| 签发监理通知单 | 通知单正文要引用隐患编号,否则无法指认改什么 |
| 签发工程暂停令 | 停工要举证是**哪一条**严重隐患导致的 |
| 复查销项 | 销的是那一条隐患,不是「一件事」 |
| 定期汇总 | 统计的对象就是隐患集合 |
| 上报主管部门 | 举证链 =「我通知过 + 期限到了 + 复查过 + 他没改」,全是隐患的历史状态 |

三层地基是现成的:**感知层**(safety 识别 + `severity.py` 确定性定级)、
**产出层**(python-docx 渲染 + artifacts 落盘与编号)、
**检索层**(knowledge 带页码出处 + 全局/项目双作用域)。缺的只是中间那层 —— **状态与流程**。

## 1. 逐动作对照

法条第十四条的四句话,依次就是需求描述的四步。

| # | 监理动作 | 现状 | 现在有什么 | 差什么 |
|---|---|---|---|---|
| 1 | 事前审查专项方案是否符合强制性标准 | ❌ | knowledge 一问一答查条文;项目级 PDF 可上传进向量库 | 没有「审查」这个动作 |
| 2 | 巡查发现隐患 | ✅ | safety 识别 8 类受控隐患 | — |
| 3 | 隐患定级 | 🟡 | `severity.py` 四档确定性定级 | 没有监理口径的**一般/严重**二分,而这个二分决定后续走哪条路 |
| 4 | 一般隐患 → 要求整改 | 🟡 | report 出巡检记录;schedule 能记带期限的任务 | 没有《监理通知单》;**巡检记录与任务互不关联** |
| 5 | 严重隐患 → 责令暂停施工 | ❌ | 无 | 《工程暂停令》没有;**没有分级分岔** |
| 6 | 及时报告建设单位 | ❌ | 无 | 无送达动作、无留痕 |
| 7 | 复查销项 | 🟡 | schedule 的 `finish_task` | 销的是「任务」不是「隐患」;**销项不要求任何证据** |
| 8 | 拒不整改 → 报主管部门 | ❌ | 无 | 无升级判定、无《监理报告》 |
| 9 | 定期汇总 | ❌ | report 只会做单张照片 | 无跨时间统计 |
| 10 | 重大隐患专项报告留档 | ❌ | 无 | — |

## 2. 两个前置

### 前置 A:语料是空的 —— 这是**用户或队友**要做的事

`data/demo/docs/` 里只有一份 `GB-50016-2014-建筑设计防火规范2018版.pdf`。
现在拿监理职责问 knowledge,它会如实答「知识库里查不到」—— 这是**正确行为**,
但也意味着 F1 的「依据」是一片空白。

| 要补的 PDF | 用途 | 缺了会怎样 |
|---|---|---|
| 《建设工程安全生产管理条例》(国务院令 393 号) | 整条业务链的法定依据 | 所有文书都引不出条文出处 |
| 《建设工程监理规范》GB/T 50319-2013 | **通知单/暂停令/复工令/监理报告的标准表式**在它附录里 | 文书排版只能自创 |
| 《危险性较大的分部分项工程安全管理规定》(住建部 37 号令) | F1 审查清单来源 | 审查清单没有依据 |
| 《建筑施工安全检查标准》JGJ 59-2011 | 隐患分级的行业依据 | grade 映射表没人背书 |

⚠️ **本文引用的条文号、表号一律以 PDF 原文为准,别照抄本文。** 写作时这四份都不在库里,
条文映射是凭记忆写的 —— 而「凭记忆写规范」正是本项目从第一天就禁止的事。

### 前置 B:签发人没有身份 —— **已由 D15 化解,不再阻塞**

**D15 定案:文书定位成「AI 出稿、总监理工程师签字生效」,不是「演示件」。**
每份文书固定印一句「本稿由工友通生成,经总监理工程师签字后生效」,签字栏留空。
这本来就是真实监理工作流,与 safety/report 已宣告的「初筛与记录,最终判定归持证人员」一脉相承。

代价要说清:**这套系统因此只能声称实现了法定职责链的「记录与出稿」部分,不能声称实现了职责链本身。**
身份体系(TODO-3)从硬前置降为欠账。

## 4. F0 —— hazards 隐患台账 + 状态机

### 4.1 建表

```sql
CREATE TABLE IF NOT EXISTS hazards (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  hazard_no       TEXT NOT NULL UNIQUE,      -- GYT-H-YYYYMMDD-HHMMSS-4hex(§6.3)
  project_id      TEXT NOT NULL DEFAULT '',  -- D6:取不到就空串,不是 NULL
  photo_sha256    TEXT NOT NULL,             -- D14:内容哈希,不是 artifact_id
  photo_id        TEXT NOT NULL,             -- 首次发现那张照片的 artifact_id(展示用)
  item            TEXT NOT NULL,             -- 受控词表 8 选 1(词表外原样透传,同 safety)
  severity        TEXT NOT NULL,             -- 重大/较大/一般/待定级 ← safety 直出,不改写
  grade           TEXT NOT NULL CHECK (grade IN ('一般','严重')),
  grading_version TEXT NOT NULL,             -- D4:定级规则版本快照
  needs_grading   INTEGER NOT NULL DEFAULT 0,-- Codex#11:severity='待定级' 时置 1,签发前必须人工定级
  was_suspended   INTEGER NOT NULL DEFAULT 0,-- Codex#6:曾进过 suspended,复查合格后必须先出复工令
  status          TEXT NOT NULL CHECK (status IN
                    ('pending','open','notified','suspended','reinspect_failed','resuming',
                     'closed','escalated')),
  due_date        TEXT,                      -- 整改期限(HK 日历日);进 notified 时必须非空(§5.1)
  found_at        TEXT NOT NULL,
  confirmed_at    TEXT,                      -- D17:人确认从 pending 转 open 的时刻
  closed_at       TEXT,
  created_at      TEXT NOT NULL,
  updated_at      TEXT NOT NULL,
  UNIQUE (project_id, photo_sha256, item)    -- D14 + Codex#9:必须带 project_id
);
CREATE INDEX IF NOT EXISTS idx_hazards_proj_status ON hazards(project_id, status);

CREATE TABLE IF NOT EXISTS hazard_docs (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  hazard_no   TEXT NOT NULL REFERENCES hazards(hazard_no),   -- Codex#19:外键
  doc_type    TEXT NOT NULL CHECK (doc_type IN
                ('notice','suspension','resumption','owner_report','authority_report','reinspect')),
  doc_no      TEXT NOT NULL UNIQUE,
  artifact_id TEXT,                          -- reinspect 行可空;文书行必须有(应用层校验,§5.1)
  photo_id    TEXT,                          -- 仅 reinspect 行
  result      TEXT CHECK (result IS NULL OR result IN ('pass','fail')),   -- Codex#19
  created_at  TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_hazard_docs_no ON hazard_docs(hazard_no);

-- Codex#10:写库失败要能事后统计,不能只有日志(进程一重启就失忆)
CREATE TABLE IF NOT EXISTS hazard_ingest_failures (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  project_id  TEXT NOT NULL DEFAULT '',
  photo_id    TEXT NOT NULL,
  item        TEXT NOT NULL,
  reason      TEXT NOT NULL,
  created_at  TEXT NOT NULL
);
```

**⚠️ `hazard_docs` 有外键,所以连接必须 `PRAGMA foreign_keys = ON`,而它**必须在 `with conn:` 之外**
执行(事务内是 no-op —— `db/projects.py:137` 有原注释)。

**为什么拆表:** 一条隐患挂多份文书,一对多。且 `hazard_docs` 天然就是**证据链** ——
上报主管部门要证明「我通知过、期限到了、复查过、他没改」,按 `hazard_no`
一次取回即可(`WHERE hazard_no IN (...)`,**禁止循环内逐行查**,CLAUDE.md 红线)。

**🔴 `status` 的语义边界。** `status=suspended` 只证明**暂停令已出稿**,不证明工地真停了工;
`owner_report` 只证明报告已生成,不证明建设单位收到了。升级判定与汇总在措辞上必须如实:
「**已出具暂停令**」而不是「已责令停工」。送达与执行确认不在本批范围(§8)。

### 4.2 状态机(D3 + D5 + **D17**)

```
                    safety 判出违规项
                          │
                 登记 hazards(<pending>)          ← D17:自动写入,但**不算进整改率、
                          │                          不进超期清单、不能被升级**
                 监理在界面上批量确认 ──(否决)──► 删除 / 标为误报
                          │ 确认
                       <open>
                          │
              ┌───────────┴───────────┐   ← 分岔由 grade 决定,代码判,不是 LLM 判
          grade=一般               grade=严重
              │                       │
       《监理通知单》         《通知单》+《工程暂停令》+《致建设单位报告》
              │                       │      ↑ 三份一次原子产出(§6.4);was_suspended=1
         <notified>              <suspended>
              │                       │
              └──────────┬────────────┘
                         │  复查(必须挂复查照片;模型给建议,人下结论 — D11)
              ┌──────────┴──────────┐
          人确认合格            人确认不合格 / 超期未改
              │                       │
   ┌──────────┴──────────┐    <reinspect_failed>
was_suspended=0   was_suspended=1     │  再复查 ┄┄┄┄┄┄┘(回到复查分支)
   │                     │            │  或升级
<closed>          <resuming> ──《复工令》──► <closed>
                                      └──► <escalated> ──《监理报告》报主管部门
```

**`was_suspended` 这一列是 Codex#6 的修法。** 原设计里 `notified` 与 `suspended` 复查失败后
都坍缩成 `reinspect_failed`,再次合格时状态机分不清该直接关闭还是必须先出复工令 ——
**漏发或滥发复工令**。用一列布尔记住「曾经停过工」,分支就恢复了。

**`ALLOWED_TRANSITIONS: dict[str, frozenset[str]]` 定义在 `db/hazards.py` 模块顶部**
(Codex#22:**不能放 `agents/supervision/`** —— 全仓 `db/*.py` 只 import `gyt.config`,
而 `agents/*/tools.py` import `gyt.db`,方向严格是 agents → db。反过来会有循环导入风险,
且存储层不能独立使用)。写法参照 `agents/safety/severity.py`:表在代码里、纯函数、单测锁死。
db 层每个迁移函数的 `WHERE status IN (...)` 从它派生,靠 `rowcount` 判成败,
**不许信先读的快照**(同 `db/tasks.py:136-138` 的写前守卫)。

### 4.3 severity → grade 映射(D4)

`agents/supervision/grading.py`,照 `safety/severity.py` 的写法:确定性、纯函数、单测锁死。

| safety 定级 | grade | `needs_grading` | 理由 |
|---|---|---|---|
| 重大(高空未系安全带、动火无监护) | **严重** | 0 | 直接威胁生命,应停工处理 |
| 较大(临边无防护、用电隐患、消防通道堵塞) | **严重** | 0 | 系统性缺陷,影响一片人 |
| 一般(未戴安全帽、未穿反光衣、材料堆放混乱) | 一般 | 0 | 个人防护单项缺失 |
| 待定级(词表外) | 一般 | **1** | 不知道 ≠ 不严重 |

**🔴 `needs_grading=1` 时所有签发工具硬拒(Codex#11)。** 原设计只是「标注需人工定级」,
但没有任何东西拦着它 —— 未知风险可以按一般隐患走完整闭环并被销项。
现在:必须先由人在界面上定级(改 `grade` + 清零 `needs_grading`)才能签发。

模块级常量 `GRADING_VERSION`,**改表必须 +1**(单测盯住)。写入 hazards 时快照。
这张表是初版默认值,上线前应由总监理工程师过目校准。

## 5. F2 / F3 / F5

### 5.1 F2 分级处置文书

**🔴 Agent 工具与 HTTP 端点必须分清(Codex#4 —— v2 在这里自相矛盾)。**

| 层 | 名称 | 干什么 |
|---|---|---|
| **Agent 工具(只读 + 建议)** | `list_hazards(project_id, status)` | 列隐患,含「未归属 N 条」「待确认 N 条」 |
| | `get_hazard(hazard_no)` | 单条详情 + 证据链 |
| | `suggest_disposal(hazard_no)` | 讲清该怎么处置、要签哪几份 —— **只出话,不出文书** |
| **HTTP 端点(写入 + 出文书)** | `POST /api/supervision/confirm` | pending → open(D17 的人工确认,支持批量) |
| | `POST /api/supervision/grade` | 人工定级(清 `needs_grading`) |
| | `POST /api/supervision/notice` | 《监理通知单》(grade=一般) |
| | `POST /api/supervision/suspend` | **三份原子产出**(grade=严重) |
| | `POST /api/supervision/reinspect-result` | 复查结论(pass/fail) |
| | `POST /api/supervision/resume` | 《工程复工令》(仅 `resuming`) |
| | `POST /api/supervision/escalate` | 《监理报告》报主管部门 |

**任何产出文书或改状态的动作都不是 Agent 工具。** Agent 只能查、只能建议。
与 W7 打卡「写入不走 LLM」同构 —— 那次理由是防编造,这次更硬:法律行为不能由概率性系统单方面触发。

**🔴 三条硬拦(全在服务端代码里,不靠提示词):**

1. `notice` 对 `grade='严重'` **拒绝**并提示走 `suspend`(Codex#3:v2 写「任何 grade 都可签」,
   于是严重隐患仍能只出通知单绕过三文书组合 —— 我声称已硬拦的漏处置其实还在)。
2. `suspend` 对 `grade!='严重'` 拒绝。
3. 任何签发对 `needs_grading=1` 拒绝。

**`due_date` 必须解析成功(Codex#12)。** `notice` / `suspend` 收 `due_phrase`(用户原话),
**复用 `agents/schedule/dates.py`(314 行)** 解析。解析不出就 fail,不许留空 ——
`due_date` 为空的隐患**永远进不了超期清单,也就永远不会被升级**。
(`dates.py` 用 314 行证明了模型换算中文日期不可靠,红线是「模型只传原话,代码来算」。)

**🔴 Envelope 的 `data` 形状必须冻结(Codex#16),三文书一并返回:**

```python
{"ok": True, "data": {
    "hazard_no": "GYT-H-…",
    "status": "suspended",
    "documents": [                       # 顺序固定:notice → suspension → owner_report
      {"doc_type": "notice",       "doc_no": "GYT-TZ-…", "artifact_id": "…", "filename": "…"},
      {"doc_type": "suspension",   "doc_no": "GYT-ZT-…", "artifact_id": "…", "filename": "…"},
      {"doc_type": "owner_report", "doc_no": "GYT-JS-…", "artifact_id": "…", "filename": "…"}],
  }, "user_msg": "…", "error_code": None}
```

前端按 `documents` 数组渲染 N 张下载卡 —— 定死数组形状是为了**避免再次静默丢件**。

### 5.2 F3 复查销项 + 升级(D11 + D14)

```
复查照片上传 → HTTP: POST /api/supervision/reinspect-suggest
    │ 调**识别半** _recognize(不登记,见 §6.2)
    ▼
  「改前/改后」两组判断并排 + 建议结论  ← 只是建议
    ▼
  人在界面点确认 → POST /api/supervision/reinspect-result {result: pass|fail}
    ▼
  pass 且 was_suspended=0 → closed
  pass 且 was_suspended=1 → resuming(等《复工令》)
  fail                    → reinspect_failed
```

**🔴 `after_photo_id` 必填,拿不到照片就没有任何路径能改成 closed。**
真机已经抓到过模型不调工具、凭记忆编回执「销了:T1 已完成」而库里还是 open。
同样的失效换到监理场景,后果是**「隐患已消除」被写进留档文书,而现场原样没动**。

**为什么结论由人下(D11):** 复查照片角度光线取景都变了,「**没拍到那个部位**」和「问题已消除」
在模型眼里一样 —— 那是往「误判合格」方向错,而这一侧会死人。

**超期升级:** `list_overdue(project_id)` 纯 Python 日期比较(照 schedule 的做法,
不往 SQL 里塞「今天」)。**`pending` 与 `needs_grading=1` 的不进超期清单**(D17 + Codex#11)。
`escalate` 生成《监理报告》,正文附 `hazard_docs` 完整证据链。

### 5.3 F5 supervision Agent

**正域**锚在查询与建议:「这条隐患复查了吗」「本月还剩几条没销」「这个该怎么处置」「待确认的有几条」。
**免责句**:「只排个期限、不出文书的,派 schedule」。

**🔴 销项只有一个出口(D13 + Codex#13)。** `tasks` 加一列可空 `hazard_no`。带 `hazard_no` 的任务:

| 动作 | 行为 |
|---|---|
| `finish_task` | **拒绝**,转去走 supervision 复查流程(要照片、要人确认) |
| `reschedule_task` | **拒绝**,转去改隐患的 `due_date`(否则两边期限继续分叉) |
| 创建 | 由 supervision 在签发通知单时同步创建,`due_date` 与隐患一致 |

不这么做的后果:TODO-21 认可的协同一手是「巡检 → 一句话记整改任务」。工友走那条**对的路**
在 schedule 里销了项/改了期,hazards 还是 open/旧期限 → 超期 → 系统建议签发《监理报告》
**指控施工方拒不整改** —— 一份建立在我们自己记乱账上的对外指控。措辞划界拦不住这个。

**🔴 防假账守卫要写第三种判据。** `core/require_tool.py` 现成的两件都不适用:
- **首答判据不行** —— 「这条属于严重隐患,建议签发暂停令,请点界面上的按钮」是纯文本首答,
  而且是这个 Agent 最重要的一句正确回答,fail 档会把它顶替掉(与 attendance 那次同款误伤);
- **编号溯源判据不行** —— 用户自己把 `GYT-H-…` 打进来、模型原样带上,而 `_sourced` 只扫
  `ToolMessage`,会判成编造。

**第三种:** 扩展 `_sourced`,让它同时扫**本回合的 `HumanMessage`**。

**🔴 但守卫只管子 Agent,管不到最后一跳(Codex#18)。** 最终用户回复由 supervisor 汇总,
而 supervisor 只有提示词约束(`graph.py` 汇报规则第 3 条)。**结构性修法是把编号的权威显示面
放到前端卡片上** —— 卡片直读工具结果里的 `doc_no`,supervisor 的文字转述只是陪衬。
用户点的是卡片,不是那段话。

## 6. 跨切面定案

### 6.1 D9 db 样板重构 —— **D18 定案:降为并行项,不阻塞主线**

三处连接 contextmanager 的 docstring 逐字相同(`db/tasks.py:85` / `db/attendance.py:266` /

做法:`db/hazards.py` **先照 `tasks.py` 的现有样板写(第四份拷贝)**,重构单开一条泳道并行做,
做完四处一起换。⚠️ 重构时 `PRAGMA foreign_keys = ON` 必须留在 `with conn:` **之外**。

### 6.2 D14 登记路径 + D17 待确认态

```
analyze 内部拆两半:

    _recognize(artifact_id) -> 五键判断        ← 纯函数,零副作用
         ↑                            ↑
   analyze_site_photo            reinspect-suggest / eval/hooks
   (工具:识别 + 登记 pending)      (<只识别,不登记>)
```

- 幂等键 = `UNIQUE(project_id, photo_sha256, item)`,**不是 artifact_id**
  (`core/artifacts.py:208` 是 `uuid4().hex`,同一张照片重传就是新号,彩排三轮会得三批)。
  **必须带 `project_id`**(Codex#9):同一张照片用于不同项目时,不带它会复用首个项目的隐患 —— 跨项目串账。
- `reinspect` 与 `eval/hooks.py` 只调 `_recognize`,不写库
  (否则:复查一次多一条隐患;`make eval SUITE=safety` 每跑一次往生产台账灌 30 条幽灵)
- `analyze_site_photo` 加 `*, config: RunnableConfig` 注入取 project_id。
  **注解必须恰好是 `RunnableConfig`**,写成 `RunnableConfig | None` 会漏掉、config 永远拿不到
- **登记成 `pending`(D17)** —— 自动写入,但不算进整改率、不进超期清单、不能被升级。
  监理在界面上批量确认才转 `open`。

**返回值必须给出编号(Codex#2 —— v2 只有一个 `registered` 布尔,后面所有要 `hazard_no` 的
动作都没有入口):**

```python
data = {..., "hazards": [{"hazard_no": "GYT-H-…", "item": "未戴安全帽", "grade": "一般",
                          "status": "pending", "needs_grading": False}, …],
             "failed_items": ["临边无防护"]}    # Codex#10:部分成功要能表达
```

**写库失败(D10 + Codex#10):** Envelope 仍是 ok(不堵死「看照片」这条已上线的演示主路径),
失败项进 `failed_items`,同时**写一行 `hazard_ingest_failures`** —— 只写日志的话进程一重启
就统计不出来了。若连失败表都写不进(整个 sqlite 挂了),退化为只有日志,这一点如实记在此处。

⚠️ `data` 从五键变多键 = **改了 safety → report 的交接契约**,要同步 report 侧与文档。

**⚠️ 残余风险(Codex#8,已知未消除):** `agents/safety/__init__.py:45` 的
`create_gyt_agent(...)` **没有传 `extra_middleware`** —— safety 一件工具调用守卫都没挂。
模型纯文本作答("这张照片看着没什么问题")时工具不触发,隐患**静默漏记**。
D17 的「待确认列表」让漏记**可见**(监理对照现场能发现列表少了),但**没有消除它**。
要真堵住得给 safety 挂 `RequireToolCall` —— 本批未定案,列入 §8。

### 6.3 时间与编号(D7)

**唯一时间权威 = `attendance/receipt.py` 的 `HK = ZoneInfo("Asia/Hong_Kong")`。**
`found_at` / `due_date` / `closed_at` / 超期判定 / 所有文书编号,全部走它。
**不许用 `datetime.now(UTC).astimezone()`** —— 那是宿主时区(`report/tools.py:151` 现在就踩着,
容器是 Shanghai、数值一致纯属巧合,已记 TODO-41)。

形式 `GYT-<类型>-YYYYMMDD-HHMMSS-4hex`,后缀 `secrets.token_hex(2)`:

| 对象 | 编号 | 对象 | 编号 |
|---|---|---|---|
| 隐患 | `GYT-H-…` | 工程复工令 | `GYT-FG-…` |
| 监理通知单 | `GYT-TZ-…` | 致建设单位报告 | `GYT-JS-…` |
| 工程暂停令 | `GYT-ZT-…` | 监理报告(报主管部门) | `GYT-JB-…` |

**🔴 必须写撞库重试(Codex#23)。** `receipt.py:78-79` 的原注释写得很清楚:
「兜底靠库里 `UNIQUE` + **调用方撞库重试**(重试就是再调一次本函数 —— 每次随机尾都是新的)」。
v2 抄了随机后缀却没抄重试 —— 那样并发签发时偶发冲突会**让整次法律文书操作直接失败**。

**每类文书要挂编号守卫的话,必须各写各的正则。** attendance 的与 report 的
**互不匹配是实测过的**(`test_checkin_api.py` 有守门断言),拿错正则会**一个都认不出、静默全放行**。

### 6.4 原子性 —— 文件先落盘,库后写(Codex#7)

v2 说「一个事务原子产出三份文书」是**想当然**:事务盖不住 `artifacts.register` 的文件与
sidecar 写入。定死顺序:

```
① 渲染三份 docx 到内存(纯函数,不落盘)
② artifacts.register ×3 → 拿到三个 artifact_id     ← 文件写失败:整个操作 fail,库一行没动,零孤儿行
③ 一个事务:写 hazard_docs ×3 + 改 hazards.status  ← 库写失败:留三个孤儿文件,可接受
```

**取舍说明:** 孤儿文件(有文件无记录)比孤儿记录(有记录无文件)安全得多 ——
后者会让证据链里出现一份点不开的「文书」。孤儿文件靠 `attendance/cleanup.py` 同款的到期清理捡走。

**为什么不是三次工具调用:** `config.py:210` 是 `supervisor_recursion_limit = 8`,
三次调用加上先查一次 = 9 步顶穿熔断,而炸在第三份之前时前两份已落盘、状态已改,无法回滚。
现在整条都在一个 HTTP 端点里,根本不经过 supervisor 的步数预算。
