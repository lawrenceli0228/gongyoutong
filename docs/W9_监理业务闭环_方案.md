# W9 监理业务闭环 —— 现状评估与实施方案

> 起因:要把系统从「工友/安全员的随手工具」扩到**监理工程师的法定职责链**。
> 依据是《建设工程安全生产管理条例》(国务院令第 393 号)**第十四条**。
>
> **2026-08-16 v2** —— v1 是评估稿。经 `/plan-eng-review` 四章节评审 + 一轮独立外部挑错,
> **15 个议题定案已全部回写进本文**。v1 的 DDL、编号表、状态机图都是决定之前的旧版,已作废。
> 定案清单见 §7,照本文实施即可。

## 0. 一页纸结论

**当前不能满足。** 十个动作里,一个全有、三个半有、六个全无。

缺口不是六个功能,而是**一件地基**:隐患在系统里没有身份。

现在的链条是「拍照 → 识别 → 渲染 docx → 完」。docx 落盘那一刻,这条隐患就从系统里
消失了 —— 没有编号可追、没有状态可变、没法回答「上周那个临边无防护改了没」。

而监理这条链的每一环都建立在「隐患有身份」之上:

| 环节 | 为什么必须有身份 |
|---|---|
| 签发监理通知单 | 通知单正文要引用隐患编号,否则无法指认改什么 |
| 签发工程暂停令 | 停工要举证是**哪一条**严重隐患导致的 |
| 复查销项 | 销的是那一条隐患,不是「一件事」 |
| 定期汇总 | 统计的对象就是隐患集合 |
| 上报主管部门 | 举证链 =「我通知过 + 期限到了 + 复查过 + 他没改」,全是隐患的历史状态 |

三层地基是现成的:**感知层**(safety 识别 + `severity.py` 确定性定级)、
**产出层**(python-docx 渲染 + artifacts 落盘与编号)、
**检索层**(knowledge 带页码出处 + 全局/项目双作用域)。缺的只是中间那层 —— **状态与流程**。

## 1. 逐动作对照

法条第十四条的四句话,依次就是需求描述的四步。

| # | 监理动作 | 现状 | 现在有什么 | 差什么 |
|---|---|---|---|---|
| 1 | 事前审查专项方案是否符合强制性标准 | ❌ | knowledge 一问一答查条文;项目级 PDF 可上传进向量库 | 没有「审查」这个动作 |
| 2 | 巡查发现隐患 | ✅ | safety 识别 8 类受控隐患 | — |
| 3 | 隐患定级 | 🟡 | `severity.py` 四档确定性定级 | 没有监理口径的**一般/严重**二分,而这个二分决定后续走哪条路 |
| 4 | 一般隐患 → 要求整改 | 🟡 | report 出巡检记录;schedule 能记带期限的任务 | 没有《监理通知单》;**巡检记录与任务互不关联** |
| 5 | 严重隐患 → 责令暂停施工 | ❌ | 无 | 《工程暂停令》没有;**没有分级分岔** |
| 6 | 及时报告建设单位 | ❌ | 无 | 无送达动作、无留痕 |
| 7 | 复查销项 | 🟡 | schedule 的 `finish_task` | 销的是「任务」不是「隐患」;**销项不要求任何证据** |
| 8 | 拒不整改 → 报主管部门 | ❌ | 无 | 无升级判定、无《监理报告》 |
| 9 | 定期汇总 | ❌ | report 只会做单张照片 | 无跨时间统计 |
| 10 | 重大隐患专项报告留档 | ❌ | 无 | — |

## 4. F0 —— hazards 隐患台账 + 状态机

新模块 `backend/src/gyt/db/hazards.py`。**先做 D9 的前置重构**(见 §6.1)再写它。

### 4.1 建表(已含 D4 / D6 / D14 的定案)

```sql
CREATE TABLE IF NOT EXISTS hazards (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  hazard_no       TEXT NOT NULL UNIQUE,   -- GYT-H-YYYYMMDD-HHMMSS-4hex(§6.3)
  project_id      TEXT NOT NULL DEFAULT '',  -- D6:取不到就空串,不是 NULL
  photo_sha256    TEXT NOT NULL,          -- D14:内容哈希,不是 artifact_id
  photo_id        TEXT NOT NULL,          -- 首次发现时那张照片的 artifact_id(展示用)
  item            TEXT NOT NULL,          -- 受控词表 8 选 1(词表外原样透传,同 safety)
  severity        TEXT NOT NULL,          -- 重大/较大/一般/待定级 ← safety 直出,不改写
  grade           TEXT NOT NULL CHECK (grade IN ('一般','严重')),
  grading_version TEXT NOT NULL,          -- D4:定级规则版本快照
  status          TEXT NOT NULL CHECK (status IN
                    ('open','notified','suspended','reinspect_failed','resuming','closed','escalated')),
  due_date        TEXT,                   -- 整改期限(HK 日历日,§6.3)
  found_at        TEXT NOT NULL,
  closed_at       TEXT,
  created_at      TEXT NOT NULL,
  updated_at      TEXT NOT NULL,
  UNIQUE (photo_sha256, item)             -- D14:幂等键
);

CREATE TABLE IF NOT EXISTS hazard_docs (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  hazard_no   TEXT NOT NULL,
  doc_type    TEXT NOT NULL CHECK (doc_type IN
                ('notice','suspension','resumption','owner_report','authority_report','reinspect')),
  doc_no      TEXT NOT NULL UNIQUE,       -- 外部意见 #9:必须有 UNIQUE
  artifact_id TEXT,                       -- 生成的 docx 产物编号
  photo_id    TEXT,                       -- 仅复查记录:复查照片
  result      TEXT,                       -- 仅复查记录:pass / fail
  created_at  TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_hazard_docs_no ON hazard_docs(hazard_no);
```

**为什么拆两张表:** 一条隐患挂多份文书,一对多。且 `hazard_docs` 天然就是**证据链** ——
上报主管部门要证明「我通知过、期限到了、复查过、他没改」,按 `hazard_no`
一次取回即可(`WHERE hazard_no IN (...)`,**禁止循环内逐行查**,CLAUDE.md 红线)。

**🔴 `status` 的语义边界(外部意见 #3)。** `status=suspended` 只证明**暂停令已出稿**,
不证明工地真停了工;`owner_report` 只证明报告已生成,不证明建设单位收到了。
升级判定与汇总在措辞上必须如实:「已出具暂停令」而不是「已责令停工」。
送达与执行确认不在本批范围,写进 §8「不在范围」。

### 4.2 状态机(D3 + D5)

```
                    safety 判出违规项
                          │
                    登记 hazards(open)
                          │
              ┌───────────┴───────────┐   ← 分岔由 grade 决定,代码判,不是 LLM 判
          grade=一般               grade=严重
              │                       │
       《监理通知单》         《监理通知单》+《工程暂停令》+《致建设单位报告》
              │                       │      ↑ 三份由**一次工具调用**原子产出(§6.4)
          notified                suspended
              │                       │
              └──────────┬────────────┘
                         │  复查(必须挂复查照片;模型给建议,人下结论 —— D11)
              ┌──────────┴──────────┐
          人确认合格            人确认不合格 / 超期未改
              │                       │
      ┌───────┴───────┐         reinspect_failed
   原为 notified   原为 suspended        │  再复查 ┄┄┄┄┄┘
      │               │                  │  或升级
   closed        resuming ──《工程复工令》──► closed
                                          └──► escalated ──《监理报告》报主管部门
```

`ALLOWED_TRANSITIONS: dict[str, frozenset[str]]` 写在 `agents/supervision/states.py`,
**是这张图的唯一真相**;`db/hazards.py` 每个迁移函数的 `WHERE status IN (...)` 从它派生,
靠 `rowcount` 判成败,**不许信先读的快照**(同 `db/tasks.py:136-138` 的写前守卫)。

### 4.3 severity → grade 映射(D4)

`agents/supervision/grading.py`,照 `safety/severity.py` 的写法:确定性、纯函数、单测锁死。

| safety 定级 | grade | 理由 |
|---|---|---|
| 重大(高空未系安全带、动火无监护) | **严重** | 直接威胁生命,应停工处理 |
| 较大(临边无防护、用电隐患、消防通道堵塞) | **严重** | 系统性缺陷,影响一片人 |
| 一般(未戴安全帽、未穿反光衣、材料堆放混乱) | 一般 | 个人防护单项缺失 |
| 待定级(词表外) | 一般 + 标注「需人工定级」 | 不知道 ≠ 不严重,但也不能自动触发停工 |

模块级常量 `GRADING_VERSION`,**改表必须 +1**(单测盯住)。写入 hazards 时快照。
这张表是初版默认值,上线前应由总监理工程师过目校准。

## 5. F2 / F3 / F5

### 5.1 F2 分级处置文书

| 工具 | 产物 | 触发条件(代码强制) |
|---|---|---|
| `issue_notice(hazard_no, due_phrase)` | 《监理通知单》 | 任何 grade |
| `issue_suspension(hazard_no, due_phrase)` | 《监理通知单》+《工程暂停令》+《致建设单位报告》**三份原子产出** | **grade=严重 才允许**,一般隐患直接 fail |
| `issue_resumption(hazard_no)` | 《工程复工令》 | 仅 `resuming` 态 |

**🔴 `if grade != '严重': return fail(...)` 必须硬拦,不能靠提示词。**「一般隐患签了暂停令」
与「严重隐患只发通知单」是两个方向相反的事故。本项目三次栽在「用提示词管住模型行为」上。

**`due_phrase` 收用户原话,不收日期(外部意见 #6)。** `agents/schedule/dates.py`
用 314 行证明了模型换算中文日期不可靠,红线是「模型只传原话,代码来算」。
签发工具**复用 `dates.py`**,不自己解析。算错的是法定整改期限,而超期升级直接读它。

**谁能按下停工按钮:走 HTTP 直连接口 + 前端确认按钮,不走 Agent 工具。**
Agent 只能「建议签发」并把要点讲清楚,实际签发要人在界面上点。与 W7 打卡
「写入不走 LLM」(D15)同构 —— 那次理由是防编造,这次更硬:法律行为不能由概率性系统单方面触发。
端点 `POST /api/supervision/suspend`,鉴权照 `checkin_api.py` 同款。

### 5.2 F3 复查销项 + 升级(D11 + D14)

```
reinspect_hazard(hazard_no, after_photo_id)
    │ 调**识别半**(不登记,见 D14)看复查照片
    ▼
  把「改前/改后」两组判断并排给人看 + 给出建议结论
    ▼
  人在界面上确认:合格 / 不合格        ← 结论由人下,照片是证据不是判据
```

**🔴 `after_photo_id` 是必填参数,拿不到照片就没有任何路径能改成 closed。**
真机已经抓到过模型不调工具、凭记忆编回执「销了:T1 已完成」而库里还是 open
(见 `core/require_tool.py`)。同样的失效换到监理场景,后果是**「隐患已消除」被写进留档文书,
而现场原样没动**。

**为什么结论由人下(D11):** 复查照片角度光线取景都变了,「**没拍到那个部位**」和
「问题已消除」在模型眼里一样 —— 那是往「误判合格」方向错,而这一侧会死人。
与 report 的 `_DISCLAIMER` 同一口径:复查销项是**判定**,不是初筛。

**超期升级:** `list_overdue(project_id)` 纯 Python 日期比较(照 schedule 的做法,
不往 SQL 里塞「今天」)。`escalate_hazard(hazard_no)` 生成《监理报告》,
正文附 `hazard_docs` 完整证据链。

### 5.3 F5 supervision Agent 挂载

同步清单见 §6.5。**正域锚在文书与法定动作**:「签发通知单」「下暂停令」「这条隐患复查了吗」
「审一下这个」;免责句写「只排个期限、不出文书的,派 schedule」。

**🔴 销项只有一个出口(D13)。** hazards 保持独立表,但 `schedule.finish_task` 对
**由隐患派生的任务**不直接销 —— 它转去走 supervision 的复查流程(要照片、要人确认)。
`tasks` 加一列可空 `hazard_no` 做关联。

不这么做的后果:TODO-21 认可的协同一手是「巡检 → 一句话记整改任务」,工友走那条对的路
在 schedule 里销了项,hazards 还是 open → 超期 → 系统建议签发《监理报告》
**指控施工方拒不整改** —— 一份建立在我们自己记乱账上的对外指控。措辞划界拦不住这个。

**🔴 防假账守卫要写第三种判据(外部意见 #5)。** `core/require_tool.py` 现成的两件都不适用:
- **首答判据不行** —— 「这条属于严重隐患,建议签发暂停令,请点界面上的按钮」是纯文本首答,
  而且是这个 Agent 最重要的一句正确回答,fail 档会把它顶替掉(与 attendance 那次同款误伤);
- **编号溯源判据不行** —— 用户自己把 `GYT-H-…` 打进来、模型原样带上,而
  `RequireReceiptSource._sourced` 只扫 `ToolMessage`,会判成编造。

**第三种判据:** 扩展 `_sourced`,让它同时扫**本回合的 `HumanMessage`** ——
用户自己报出来的编号是合法出处。改动小、语义正确,且 report 侧行为不变(用户不会打巡检记录号)。

## 6. 跨切面定案

### 6.1 D9 前置重构(单独提交,先于一切)

`db/tasks.py:85` / `db/attendance.py:266` / `db/projects.py:130` 的连接 contextmanager
**docstring 逐字相同**,`_now_iso()` 在 tasks 与 projects 也逐字相同。抽到 core,四处共用。

**🔴 抽的时候有一颗地雷:`PRAGMA foreign_keys = ON` 必须在 `with conn:` 之外执行**
(事务内是 no-op —— `db/projects.py:137` 有原注释)。放进事务里 = 全库外键静默失效、零报错。
且这次要动**线上已有真实打卡数据的 attendance**,改完必须跑一遍真机打卡。

### 6.2 D14 登记路径

```
analyze 内部拆两半:

    _recognize(artifact_id) -> 五键判断        ← 纯函数,零副作用
         ↑                    ↑
   analyze_site_photo     reinspect / eval/hooks
   (工具:识别 + 登记)      (只识别,不登记)
```

- 登记幂等键 = `UNIQUE(photo_sha256, item)`,**不是 artifact_id**
  (`core/artifacts.py:208` 是 `uuid4().hex`,同一张照片重传就是新号 —— 彩排三轮会得三批)
- `reinspect` 与 `eval/hooks.py` 只调 `_recognize`,不写库
  (否则:复查一次多一条 open 隐患;`make eval SUITE=safety` 每跑一次往生产台账灌 30 条幽灵)
- `analyze_site_photo` 加 `*, config: RunnableConfig` 注入取 project_id。
  **注解必须恰好是 `RunnableConfig`**,写成 `RunnableConfig | None` 会漏掉、config 永远拿不到
- **写库失败(D10):** Envelope 仍是 ok,`data` 多一个 `registered: bool`,
  失败时 `logger.error` 并计数,supervision 的清单/汇总显式报「本期 N 次登记失败」。
  不堵死「看照片」这条已上线的演示主路径,也不静默
- ⚠️ `data` 从五键变六键 = **改了 safety → report 的交接契约**,要同步 report 侧与文档

### 6.3 时间与编号(D7)

**唯一时间权威 = `attendance/receipt.py` 的 `HK = ZoneInfo("Asia/Hong_Kong")`。**
`found_at` / `due_date` / `closed_at` / 超期判定 / 所有文书编号,全部走它。
**不许用 `datetime.now(UTC).astimezone()`** —— 那是宿主时区(`report/tools.py:151` 现在就踩着,
容器是 Shanghai、数值一致纯属巧合)。

新建共用编号生成器,形式 `GYT-<类型>-YYYYMMDD-HHMMSS-4hex`,后缀用 `secrets.token_hex(2)`:

| 对象 | 编号 |
|---|---|
| 隐患 | `GYT-H-…` |
| 监理通知单 | `GYT-TZ-…` |
| 工程暂停令 | `GYT-ZT-…` |
| 工程复工令 | `GYT-FG-…` |
| 致建设单位报告 | `GYT-JS-…` |
| 监理报告(报主管部门) | `GYT-JB-…` |

**用随机后缀而不是日内序号** —— 序号要先数再加一,check-then-act 竞态;
而批量签发(一次巡检多条隐患)正是会撞的场景。

**每类文书要挂编号守卫的话,必须各写各的正则。** attendance 的
`GYT-A-日期-时刻-4hex` 与 report 的 `REPORT_RECEIPT_PATTERN` **互不匹配是实测过的**
(`test_checkin_api.py` 有守门断言),拿错正则会**一个都认不出、静默全放行**。

### 6.4 熔断与原子性(外部意见 #10)

`config.py:210` 是 `supervisor_recursion_limit = 8`。严重隐患若要三次工具调用出三份文书,
加上先查一次 = 9 步,**顶穿熔断**,而且炸在第三份之前时前两份已落盘、`hazard_docs` 已插行、
状态已改,**没有任何一步能回滚**。

**定案:三份文书由 `issue_suspension` 一次调用原子产出**,一个事务写 `hazard_docs` 三行。
不提高 `recursion_limit`(那只是把问题往后推)。
