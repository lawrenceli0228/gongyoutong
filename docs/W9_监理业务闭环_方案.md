# W9 监理业务闭环 —— 现状评估与 feat 清单

> 起因:要把系统从「工友/安全员的随手工具」扩到**监理工程师的法定职责链**。
> 依据是《建设工程安全生产管理条例》(国务院令第 393 号)**第十四条**。
> 2026-08-16 评估,评估对象 = 当前 main。

---

## 0. 一页纸结论

**不能满足。** 十个动作里,一个全有、三个半有、六个全无。

但缺口不是六个功能,而是**一件地基**:隐患在系统里没有身份。

现在的链条是「拍照 → 识别 → 渲染 docx → 完」。docx 落盘那一刻,这条隐患就从系统里
消失了 —— 没有编号可追、没有状态可变、没法回答「上周那个临边无防护改了没」。

而监理这条链的每一环都建立在「隐患有身份」之上:

| 环节 | 为什么必须有身份 |
|---|---|
| 签发监理通知单 | 通知单正文要引用隐患编号,否则无法指认改什么 |
| 签发工程暂停令 | 停工要举证是**哪一条**严重隐患导致的 |
| 复查销项 | 销的是那一条隐患,不是「一件事」 |
| 定期汇总 | 统计的对象就是隐患集合 |
| 上报主管部门 | 举证链 = 「我通知过 + 期限到了 + 复查过 + 他没改」,全是隐患的历史状态 |

所以顺序不能反:**先做 hazards 台账 + 状态机,其余全挂上去**。
反过来先做文书生成,得到的是六个互不连通的 docx 生成器 —— 演示能过,业务闭不上。

好消息是三层地基都是现成的:**感知层**(safety 识别 + 确定性定级)、
**产出层**(python-docx 渲染 + artifacts 落盘 + 编号)、
**检索层**(knowledge 带页码出处 + 全局/项目双作用域)。
缺的只是中间那层 —— **状态与流程**。

## 1. 逐动作对照

法条第十四条的四句话,依次就是用户描述的四步。拆成可实现的动作:

| # | 监理动作 | 现状 | 现在有什么 | 差什么 |
|---|---|---|---|---|
| 1 | 事前审查专项方案是否符合强制性标准 | ❌ | knowledge 一问一答查条文;项目级 PDF 可上传进向量库 | 没有「审查」这个动作:不能拿一份方案逐条比对出意见 |
| 2 | 巡查发现隐患 | ✅ | safety 识别 8 类受控隐患 | — |
| 3 | 隐患定级 | 🟡 | severity.py 四档确定性定级(重大/较大/一般/待定级) | 没有监理口径的**一般/严重**二分,而这个二分决定了后续走哪条路 |
| 4 | 一般隐患 → 要求整改 | 🟡 | report 出巡检记录 docx;schedule 能记一条带期限的任务 | 没有《监理通知单》;**巡检记录与任务互不关联**,两个孤岛 |
| 5 | 严重隐患 → 责令暂停施工 | ❌ | 无 | 《工程暂停令》没有;更要命的是**没有分级分岔** —— 现在不管什么级别都只出同一份巡检记录 |
| 6 | 及时报告建设单位 | ❌ | 无 | 无送达动作、无留痕 |
| 7 | 复查销项 | 🟡 | schedule 的 `finish_task` | 销的是「任务」不是「隐患」;而且**销项不要求任何证据** —— 一句话就能销 |
| 8 | 拒不整改/不停工 → 报主管部门 | ❌ | 无 | 无升级判定、无《监理报告》 |
| 9 | 定期汇总 | ❌ | report 只会做单张照片 | 无跨时间、跨照片的统计 |
| 10 | 重大隐患专项报告留档 | ❌ | 无 | — |

## 3. feat 清单

### F0 —— hazards 隐患台账 + 状态机(地基,其余全部依赖它)

新模块 `backend/src/gyt/db/hazards.py`,照 `db/tasks.py` 的写法(同步 sqlite3、
每操作一条独立连接、幂等建表、全参数化、列表一次取回)。

```sql
CREATE TABLE IF NOT EXISTS hazards (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  hazard_no   TEXT NOT NULL UNIQUE,   -- GYT-H-20260816-0001
  project_id  TEXT,                   -- ⚠️ 与 tasks 不同:这里必须真写,不能恒 NULL
  photo_id    TEXT NOT NULL,          -- 发现时那张照片的 artifact_id
  item        TEXT NOT NULL,          -- 受控词表 8 选 1(词表外原样透传,同 safety)
  severity    TEXT NOT NULL,          -- 重大/较大/一般/待定级 ← safety 直出,不改写
  grade       TEXT NOT NULL CHECK (grade IN ('一般','严重')),   -- 监理口径,由 severity 映射
  status      TEXT NOT NULL CHECK (status IN
                ('open','notified','suspended','reinspect_failed','closed','escalated')),
  due_date    TEXT,                   -- 整改期限
  found_at    TEXT NOT NULL,
  closed_at   TEXT,
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS hazard_docs (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  hazard_no   TEXT NOT NULL,
  doc_type    TEXT NOT NULL CHECK (doc_type IN
                ('notice','suspension','owner_report','authority_report','reinspect')),
  doc_no      TEXT NOT NULL,          -- 各类文书各自的编号(见 §4.3)
  artifact_id TEXT,                   -- 生成的 docx 产物编号
  photo_id    TEXT,                   -- 仅复查记录:复查照片
  result      TEXT,                   -- 仅复查记录:pass / fail
  created_at  TEXT NOT NULL
);
```

**为什么拆两张表:** 一条隐患会挂多份文书(通知单 → 暂停令 → 复查记录 ×N → 上报),
是一对多。而且 `hazard_docs` 天然就是**证据链** —— 上报主管部门时要证明
「我通知过、期限到了、复查过、他没改」,这份证明就是按 `hazard_no` 把
`hazard_docs` 全查出来,不需要另建一套。

**⚠️ `project_id` 必须真写。** `tasks` 表的 `project_id` 是「建表即预留、写入恒 NULL」
(W3 定案 #11)—— hazards 不能这么干:监理汇总报表是**按项目**出的,
项目维度从第一天就得是真的,补做要迁移历史数据。

#### 状态机

```
                    safety 判出违规项
                          │
                    登记 hazards(open)
                          │
              ┌───────────┴───────────┐   ← 这个分岔由 grade 决定,
          grade=一般               grade=严重      **代码判,不是 LLM 判**
              │                       │
       《监理通知单》         《监理通知单》+《工程暂停令》+ 报建设单位
              │                       │
          notified                suspended
              │                       │
              └──────────┬────────────┘
                         │  复查(**必须挂复查照片 artifact_id**)
              ┌──────────┴──────────┐
          复查合格              复查不合格 / 超期未改
              │                       │
           closed              reinspect_failed
                                      │  再复查 ┄┄┄┄┄┄┘
                                      │  或升级
                                      └──► escalated ──《监理报告》报主管部门
```

`severity → grade` 的默认映射(新建 `agents/supervision/grading.py`,
照 `safety/severity.py` 的写法:确定性、纯函数、单测锁死):

| safety 定级 | 监理 grade | 理由 |
|---|---|---|
| 重大(高空未系安全带、动火无监护) | 严重 | 直接威胁生命,应停工处理 |
| 较大(临边无防护、用电隐患、消防通道堵塞) | 严重 | 系统性缺陷,影响一片人 |
| 一般(未戴安全帽、未穿反光衣、材料堆放混乱) | 一般 | 个人防护单项缺失 |
| 待定级(词表外) | 一般 + 标注「需人工定级」 | 不知道 ≠ 不严重,但也不能自动触发停工 |

这张表和 `severity.py` 一样是**初版默认值,上线前应由总监理工程师过目校准**。
放代码不放模型的三个理由完全照搬 severity.py:可解释、可校准(改一处生效,
不动提示词就不烧视觉缓存)、可测试。

### F1 —— 事前方案审查(这就是「结合 knowledge」的正解)

**做法:清单驱动的形式审查。** 完全复用 knowledge 现有的双作用域,不需要新检索能力。

```
                     ┌─ global scope ──► 检索对应强条 ──► 规范出处(文件名+页码)
一张检查项表 ×N 项 ──┤
                     └─ project scope ─► 在方案 PDF 里检索 ──► 方案出处(第 X 页)
                                              │
                        ┌─────────────────────┴─────────────────────┐
                    找得到                                       找不到
                        │                                           │
                    「已包含」+ 两处出处                        「未提及」
                        │
                  数值可比对的再比一次 ──► 「符合」/「存疑」
                                              │
                                     《专项方案审查意见》docx
```

检查项表(`SCHEME_CHECKLIST`,来源 = 住建部 37 号令,PDF 进库后逐条核):
编制人签字 / 施工单位技术负责人审批 / 总监理工程师签字 / 是否需专家论证 /
应急处置措施 / 监测监控措施 / 计算书 / 验收要求 …

**🔴 这条边界必须像 report 的 `_DISCLAIMER` 一样印在每一份审查意见书上:**

> AI 判的是「写没写」,不是「写得对不对」。
> 能答:专项方案里有没有写应急预案、有没有专家论证签字、这个数值和强条对不对得上。
> 不能答:这个支撑体系设计得对不对、这个工况下的荷载取值合不合理。
> **实质性技术审查以注册监理工程师判定为准。**

这个定位和 safety 的「初筛与记录」是同一句话,不是新增让步。

### F2 —— 分级处置文书

三个工具 + 一套 docx 模板(**表式照 GB/T 50319-2013 附录,别自创**):

| 工具 | 产物 | 触发条件(代码强制) |
|---|---|---|
| `issue_notice(hazard_no, due_date)` | 《监理通知单》 | 任何 grade 都可签 |
| `issue_suspension(hazard_no)` | 《工程暂停令》 | **grade=严重 才允许**,一般隐患调用直接 fail |
| `report_to_owner(hazard_no)` | 《致建设单位报告》 | 伴随暂停令,一并生成 |

**🔴 「一般隐患签了暂停令」和「严重隐患只发了通知单」是两个方向相反的事故,
都不能靠提示词拦。** 这条判定必须在工具里用 `if grade != '严重': return fail(...)`
硬拦,理由和本项目三次栽在「用提示词管住模型行为」上完全一致
(收工信号、表格复读、台账回执 —— 最后都是靠结构件解决的)。

#### 谁能按下停工按钮 —— 需要你拍板

暂停令的后果是真金白银的停工。有两条路:

**方案甲(推荐,有先例):走 HTTP 直连接口 + 前端确认按钮,不走 Agent 工具。**
Agent 只能「建议签发」并把要点讲清楚,实际签发要人在界面上点。
这与 W7 打卡「写入不走 LLM」(D15)完全同构 —— 那次的理由是防编造,
这次的理由更硬:法律行为不能由概率性系统单方面触发。
代价:多一件前端覆盖件 + 一条 `/api/supervision/suspend` 端点。

**方案乙(演示简化):Agent 可直接签发,但文书页脚固定印「演示件 · 非正式文书」。**
代价:结构上没有拦截,只靠文案自证。

### F3 —— 复查销项 + 超期升级

```
reinspect_hazard(hazard_no, after_photo_id)
    │ 重新调 analyze_site_photo(复查照片)     ← 复用 safety,零新增识别能力
    ▼
该 item 还在 ──► fail:复查不合格 → status=reinspect_failed
该 item 没了 ──► pass:复查合格   → status=closed + closed_at
```

**🔴 复查销项必须挂复查照片的 artifact_id,不许纯文本销项。**

这是 `RequireReceiptSource` 思路的自然延伸,而且这次赌注更大。真机已经抓到过
模型不调工具、凭记忆编回执「销了:T1 已完成」而库里还是 open
(见 `core/require_tool.py`)。同样的失效换到监理场景,后果是
**「隐患已消除」被写进留档文书,而现场原样没动** —— 这是要出人命的假账。

结构上的保证:`reinspect_hazard` 的 `after_photo_id` 是必填参数,
编号不合法/照片不存在直接 fail(照片编号是 32 位 hex,模型编不出一个能通过
`artifacts.resolve` 的);拿不到照片就没有任何路径能把状态改成 closed。

**超期升级**:`list_overdue(project_id)` 纯 Python 日期比较(照 schedule 的做法,
不往 SQL 里塞「今天」)。超期未闭环 → Agent 提示可签发《监理报告》报主管部门,
`escalate_hazard(hazard_no)` 生成文书并把 `hazard_docs` 的完整证据链附进正文。

## 4. 三条设计红线

### 4.1 状态迁移与文书类型由代码判定,不由 LLM 判定

理由同 `severity.py`,但这次更硬:签发暂停令是法律行为。
LLM 只负责搬运编号和讲人话,分岔一律走 `grading.py` 的纯函数。

### 4.2 销项必须有证据(见 F3)

### 4.3 每类文书各写各的编号正则 —— 不许复用

CLAUDE.md 已经记过这个教训:attendance 的 `GYT-A-日期-时刻-4hex` 与 report 的
`REPORT_RECEIPT_PATTERN` **互不匹配是实测过的**,`test_checkin_api.py` 有守门断言。
反向约束就写在 `attendance/receipt.py` 头注里:哪天要挂编号守卫,必须写自己的正则,
拿 report 那条会**一个都认不出、静默全放行**。

新增五种编号,同一条约束照样成立:

| 对象 | 编号 |
|---|---|
| 隐患 | `GYT-H-YYYYMMDD-NNNN` |
| 监理通知单 | `GYT-TZ-YYYYMMDD-NNN` |
| 工程暂停令 | `GYT-ZT-YYYYMMDD-NNN` |
| 监理报告(报主管部门) | `GYT-JB-YYYYMMDD-NNN` |
| 方案审查意见 | `GYT-SC-YYYYMMDD-NNN` |

## 5. 建议顺序与演示价值

| 批次 | 内容 | 为什么排这里 |
|---|---|---|
| **一** | F0 台账 + 状态机 + grading 映射 | 地基。做完之后隐患才有身份,别的都能挂上去 |
| **二** | F2 通知单 + 暂停令 + F3 复查销项 | **演示最亮的一条链**:拍照 → 判严重 → 出暂停令 → 整改 → 复查照片 → 销项。全程有文书、有证据、有编号 |
| **三** | F4 汇总 + 专项报告 | `hazard_docs` 的投影,做起来快 |
| **四** | F1 方案审查 | 最能体现「结合 knowledge」,但**质量高度依赖语料** —— 四份 PDF 没进库之前做它是空转 |

所以 F1 排在最后不是因为它不重要,而是因为**它的前置在你手上**(前置 A)。
四份 PDF 一进库,F1 就可以往前提。
