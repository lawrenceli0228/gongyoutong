01 / 起因

为什么要有这一轮

W4 那一轮验收 19/25。挂掉的 6 条里,4 条是日期字面量过期(测试自己的毛病), 另外 2 条是产品的真问题:

C2 —— 英雄链会概率性漏掉「出报告」那一环

用户: 查一下这张照片,顺便出份巡检记录(照片编号 xxx)
  │
  ├─ supervisor ──transfer_to_inspection──► 英雄链子图
  │                                            │
  │                                   START ──► safety ──硬边──► report ──► END
  │                                                                 │
  │                                          硬边保证 report 被叫起来 ✅
  │                                          但没人保证 report 真调工具 ❌
  │                                                                 │
  └─ [report] 「巡检记录出好了,编号 GYT-20260809-153739」  ← 没调 render_inspection_report
                                                              磁盘上没有那份 docx

当初把 safety → report 写成硬边,解决的是「supervisor 有时不派第二跳」。 漏的位置换了:硬边把 report 叫起来了,但 report 自己凭上下文编了段话。

这跟 schedule 那次「不调工具凭记忆编回执」是同一种病。当时的解法是 agents/schedule/guard.py 的 RequireLedgerTool —— 而 report 是裸的。

观察样本只有 2 次(一次挂一次过)。这不是发生率,是个信号,但它长在演示主路径上。

A8 —— 红了,但查不出是哪种红

A8 断「乱日期报人话带举例」。我去查工具层:

「猴年马月」这个期限我没看懂。可以这样说:明天 / 后天 / 3天后 / 周三 / 下周三 / 月底 / 9月1号 / 2026-08-15。

含「明天」✅ 不含「开小差」✅ —— 断言在工具层必然通过。所以红在上一层。 只剩两种可能:模型根本没调工具,或者调了但把文案改写了。

而分不出是哪种 —— 脚本只记 PASS/FAIL,不留消息轨迹。想查就得重跑真调模型, 而重跑很可能不复现(C2 就是这样)。

03 / 决策

七个决策
#决策选定
D1防假账结构件放哪下沉 core/require_tool.py,做成可配置
D2重试仍不调工具时 report 怎么办已被 D6 推翻硬错 —— 不让编造的编号出去
D3验收断言挂了留不留轨迹失败就 dump 完整消息轨迹
D4验收脚本的「今天」从哪取从后端取(读 list_tasks 的 data.today)
D5A10 一周三天必红按星期分支,两边都断
T1knowledge/cad 也接结构件记 TODO,不现在做(无实测证据)
T2「断措辞」改「断事实」记 TODO,要逐条拿捏
⚠️ D2 已被 D6 推翻(2026-08-10 落地时纠正)

D2 原文是「report 沿用 schedule 的首答必须调工具判据,只把失败语义改成硬错」。 落地后对抗复核实测出两条 HIGH,证明这个判据两头都不对:

  1. 一次都不触发 —— 英雄链是写死的图边,report 首答前最后一条是 safety 的纯文本 AIMessage,既不是用户发言也不是 transfer_to_* 回执,_is_turn_start 恒为 False; 而 AGENT_REGISTRY 里没有独立的 report,transfer_to_report 这条路压根不存在。
  2. 一旦触发反而打断合法流程 —— report/prompt.md 第 23/45 行明文要求两种 该纯文本回答的回合(反问「给哪张出记录?」、如实拒答日报),会被顶替成答非所问的话。

D6 定案:改用「编号溯源」判据 —— 输出里报出的 GYT-… 编号,必须在本回合的工具 结果里真的出现过。编号由工具生成(tools.py:151),模型没有合法理由自己造; 而反问与拒答压根不含编号,零误伤;且不依赖首答判定,英雄链里真会触发。

下面 §3~§7 里凡是写「首答必须调工具 / on_give_up / fail_msg」的地方,report 那一侧 都以本框为准;schedule 侧不受影响,RequireToolCall 保持原判据与 pass 档。 实现见 core/require_tool.py 顶部「两种判据,别混用」。

D2 值得展开:为什么 report 和 schedule 的失败语义不一样

schedule 放行的后果        report 放行的后果
─────────────────────    ─────────────────────
嘴上销了、库里没销    →   工友拿到编号 GYT-xxx
      ↓                        ↓
D 组直查库,当场揭穿      磁盘上没有那份 docx
      ↓                        ↓
  有人兜底 ✅            没有任何人会发现 ❌

「没出成」工友看得见也重试得了,「以为出成了」无法补救,而且那个假编号会 污染后续所有引用(打印、转发、报给管理员)。

D4 值得展开:后端本来就在吐今天

schedule/tools.py::list_tasks 的返回体:

return ok(data={"tasks": …, "undated": …, "today": today_iso, …})
                                            ↑ 后端 date.today(),容器时区算出来的

验收 A2(「下周三之前还有哪些任务没完成」)本来就会调 list_tasks。 从那条 ToolMessage 里读 data.today 即可 —— 零新增接口、零额外模型调用。

⚠️ 这条选择的已知弱点:容器时区若配错,脚本会跟着错、静默全绿。
缓解(不推翻决策):把取到的 today 原样打印,并与 Asia/Shanghai 比一下, 不一致时打一条醒目的警告但不判红 —— 判红会让部署在别的时区时误报, 而警告能让人一眼看见 2026-08-10 那种「容器裸 UTC」的配置事故。

10 / 落地记录

2026-08-10 收工

六条全部落地,commit 809a890(Lane B)+ 前序 Lane A。但本方案有两条决策被实测推翻, 推翻的过程比结论有用,原文一律保留在上面、只在这里记纠正。

被推翻决策一:D2「report 也用首答必须调工具」

方案里写「schedule 的判据下沉给 report 复用,只换文案换失败语义」。对抗复核证明两头都不对。
英雄链是图边直连(graph.py:185),report 首答前最后一条是 safety 的 AIMessage
        ↓  既不是用户发言,也不是 transfer_to_* 回执
   _is_turn_start 恒为 False  →  守卫在生产路径上一次都不触发

而它一旦真触发,又会打断 report/prompt.md 明文要求的两种合法纯文本回合 (多照片时反问「给哪张出记录?」、如实拒答日报)—— 反问被吞掉就是对话死锁。

改成 RequireReceiptSource(编号溯源):输出里报出的 GYT-… 必须在本回合工具结果里 真的出现过。编号是工具生成的(report/tools.py:151),模型没有合法理由自己造; 反问和拒答压根不含编号,零误伤。不依赖首答判定,所以英雄链里真会触发。

被推翻决策二:T3 的「30 秒判据 = 本轮业务工具」

初版把「本轮调了哪些业务工具」放在轨迹头部当判据,空的就断言「模型凭记忆编的,先查提示词和 guard」。对抗复核用同版本库起了一张真的 create_supervisor 图(参数与 graph.py 逐字相同),让子 Agent 确实调了 add_task —— 那条 tool_call 消息在顶层 messages 里依然不见。

根因:

# langgraph_supervisor/supervisor.py  _process_output
elif output_mode == "last_message":
    if isinstance(messages[-1], ToolMessage):
        messages = messages[-2:]
    else:
        messages = messages[-1:]      # 子 Agent 回合末尾恒是它自己的纯文本 AIMessage

带 tool_calls 的 AI 消息连同 ToolMessage 一起被砍。那一行在真机上是常量。

改成:删掉假判据 + 把局限当面写清 + 判据换成台账快照(dump 时直查 tasks 表)。 「回执说什么不算,库里有没有才算」—— 与 D 组同一条哲学,而且离线可验证。

捞子图消息的两条路(runs/stream 带 subgraphs / POST /threads/{id}/history) 只在 Pregel 层验过、HTTP 层未实测,记成 TODO-26,不在这一轮赌。

方案没预见、由变异注入抓出来的四条假绿灯

复核没有停在读代码,写了桩后端把回归注进去看断言抓不抓得住:

变异修前修后
改期根本没发生周四 25/25 假绿(A1「明天」与 A3「周五」撞同一天)七天全 23/25
T2 期限错记周三 25/25 假绿(A3==A4)抓住
整改任务错记周六 25/25 假绿(A4==C3)抓住
同标题重复行七天全 25/25 假绿(read_ledger 用标题当 key,库里 6 行报「恰好 3 条」)七天全 24/25

前三条的根治办法不是逐日打补丁,是立一条不变量:A1/A3/A4/C3 四个日期在任何一天 两两不等,按日历选短语去满足它,五年全量测试钉死。原先那条 test_后天与下周一只在周六撞车 是把撞车固化成了期望,已反转。

方法论:这一轮的三条错,主 agent 全占

D2 判据错、T3 判据错、A10 撞车没预见 —— 三条都出在规划,不是执行。 共同点是「在脑子里推演消息形状」,而三次都被「真起一张图 / 真注一个回归」推翻。 下次涉及框架行为的判据,先写一个二十行的探针跑一遍,比推演便宜得多。

第三条更值得记:验收脚本自己也会有假绿灯,而且没人验收它。
这一轮是靠变异注入(故意把功能改坏,看断言红不红)才发现的 —— 这套手法应该 固定下来,别等下次演示前才发现验收在陪跑。
