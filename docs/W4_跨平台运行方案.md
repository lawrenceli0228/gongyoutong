## 0. 结论

**两人都用 Docker 启动,代码仍在本机编辑(挂源码热重载)。**

这不是新建架构。项目在 T1 就建好了四阶段 Dockerfile(BGE-M3 权重预烤 + `HF_HUB_OFFLINE=1` 断网可用)
和 docker-compose。挡路的是**五处路径与依赖问题**,修完就通。

**VPS 不做**(§7)。它解决的是另一类问题,而且本方案是它的前置。

### 为什么统一 Docker 对队友是净收益,不是牺牲

| | 他现在的本机路径 | 统一 Docker 之后 |
|---|---|---|
| 装依赖 | sentence-transformers + torch ≈ 几 GB | 镜像里已装好 |
| BGE-M3 权重 | 本机下 2.2GB | 镜像层已烤好 |
| 建知识库 | 本机跑 15 分钟 | 容器里跑,一次 |
| 改代码 | 编辑器直接改,热重载 | **一样**(dev override 挂源码) |
| 启动命令 | `make dev` | `make dev-docker` |

他付出的只有「换一条启动命令 + 首次构建等一次」,换来的是不用在本机维护一套重依赖。

### 你的 Intel Mac 在这条路上是优势

| 平台 | 容器架构 | torch 2.13.0 轮子 |
|---|---|---|
| **你的 Mac(Intel x86_64)** | **原生 linux/amd64,无翻译层** | 容器内 manylinux_x86_64 ✓ |
| 队友 Windows(WSL2) | 原生 linux/amd64 | 同上 ✓ |
| (对照)M 系列 Mac | 要 QEMU 模拟,慢 | — |
| (对照)本机原生装 | — | **macOS x86_64 轮子不存在 ✗** |

torch 那条 BLOCKER 在容器里根本不存在。换 M 系列 Mac 这条路反而更慢。

## 2. 目标架构

```
   Mac (Intel)                                         Windows + WSL2
   ┌──────────┐        ┌─────────────────────────┐      ┌──────────┐
   │ 编辑器   │───挂源码►│ gyt-backend  :2024      │◄─挂源码──│ 编辑器   │
   │ 改代码   │        │  5 Agent 全可用          │      │ 改代码   │
   └──────────┘        │  BGE-M3 已烤进镜像       │      └──────────┘
                       └───────────┬─────────────┘
                                   │ 挂载 ./data:/app/data
                       ┌───────────▼─────────────┐
                       │ <repo>/data/            │  ← 统一到这一个目录(D2)
                       │   demo/      源资产(进git)│
                       │   artifacts/ 巡检记录     │
                       │   chroma/    规范向量库   │
                       │   cache/     视觉缓存     │  ← 焐热一次,处处命中
                       │   gyt.sqlite3 任务台账    │
                       └─────────────────────────┘

  docker-compose.yml          交付/演示态 —— 纯镜像,不挂源码
  + docker-compose.dev.yml    开发态 —— 追加挂 ./backend/src,热重载

  本机 backend/data/ 基本退役(只剩 make test 用 tmp_path,不碰它)
```

**为什么分两份 compose:** 演示要的是「镜像里是什么就跑什么」。挂源码会让镜像与实际运行的代码
不一致,出问题时分不清是镜像坏了还是本机代码坏了。两种用途,两份配置。

## 3. 已定的决策

| # | 决策 | 选择 | 理由 |
|---|---|---|---|
| D1 | 跨平台策略 | **全面统一 Docker 启动** | 一套环境;队友净收益(不用本机维护几 GB 重依赖) |
| D2 | 数据目录 | **统一到仓库根 `data/`** | 缓存/台账/知识库/产物四样共享;**顺带让 D4 从「加配置项」缩成「改默认值」** |
| D3 | 建库信号 | **分开退出码 + 明确原因** | 「没找到 PDF」和「已入库」现在是同一句话+同一个退出码,是所有路径 bug 的放大器 |
| D4 | 资产路径 | **随 D2 自动解决** | 统一后 demo 资产就是 `data_dir/"demo"`,本机与容器自动对齐 |
| D5 | 镜像体积 | **CPU-only torch** | 砍 2.4GB CUDA(代码已 `device="cpu"`),镜像/CI/首次构建三处提速 |
| D6 | 开发回路 | **dev override 挂源码** | 否则改一行要重建;这也是队友肯换过来的前提 |
| D7 | 验收覆盖 | **补 E/F 两组 + 路径铁证** | 路径 bug 的失败方式是静默的,必须有断言而不是手点 |

### 阶段一 · 依赖与体积(D5)

```toml

name = "pytorch-cpu"

explicit = true

[tool.uv.sources]
torch = [{ index = "pytorch-cpu", marker = "sys_platform == 'linux'" }]
```

```bash
cd backend && uv lock && uv lock --check
```

> ⚠️ `uv.lock` 是队友刚提交的。动之前跟他说一声,别两边同时改。
> ⚠️ 若 `sentence-transformers` 对 torch 有版本下限冲突,**实测报错再调版本号,不要凭记忆填**。

### 阶段二 · 统一数据目录(D2 + D4)

**`backend/src/gyt/config.py`** —— 只改一个默认值:

```python
def _default_data_dir() -> Path:
    """数据根目录的默认值。

    本文件是 <repo>/backend/src/gyt/config.py:
        parents[0]=gyt  [1]=src  [2]=backend  [3]=<仓库根>

    ⚠️ 原来是 Path("data"),按**进程工作目录**解析 —— 而 make dev 在 backend/ 下跑,
       数据落在 backend/data;容器里 GYT_DATA_DIR=/app/data(compose 挂的是仓库根 ./data)。
       两条路径因此有两份数据:缓存、台账、知识库、产物全部分裂。
       统一到仓库根之后,demo 资产就是 data_dir/"demo",本机与容器自动对齐,
       不需要再为演示资产单开一个配置项。
    """
    return Path(__file__).resolve().parents[3] / "data"


data_dir: Path = Field(default_factory=_default_data_dir)
```

同一个文件加一个派生属性(**不要 `_ensure_dir`** —— 它是源资产,自动创建反而会掩盖「资产丢了」):

```python
@property
def demo_assets_dir(self) -> Path:
    """演示源资产(照片/图纸/规范 PDF)。随仓库走、进 git。

    与运行期数据同在 data_dir 下:容器 /app/data/demo,本机 <repo>/data/demo —— 自动对齐。
    刻意不建目录:目录不存在本身就是要报出来的错(见 ingest 的退出码)。
    """
    return self.data_dir / "demo"
```

**`agents/knowledge/ingest.py:40`** 与 **`agents/cad/demo_registry.py:37`** 改成读配置。
别在模块级调 `get_settings()`(import 时固化,测试改环境变量就失效):

```python
# 之前:_REPO_ROOT = Path(__file__).resolve().parents[5]
#       DEFAULT_DOCS_DIR = _REPO_ROOT / "data" / "demo" / "docs"
def _docs_dir() -> Path:
    return get_settings().demo_assets_dir / "docs"
```

两处文件顶部那句「`parents[5]` = 仓库根」的注释一并改掉。**陈旧注释比没注释更害人**,这是 CLAUDE.md 里的规矩。

**一次性搬迁**(本机现有数据):

```bash
cd <repo>
mkdir -p data
mv backend/data/* data/ 2>/dev/null || true    # demo/ 已在 data/ 下,不冲突
rmdir backend/data 2>/dev/null || true
```

> 视觉缓存搬过去照样命中 —— 缓存键算在**图片内容**上,不含路径。台账 sqlite 同理。
> `.gitignore` 不用改:现有的 `/data/*` + `!/data/demo/` 正好就是对的规则。

### 阶段三 · 建库信号(D3)

`agents/knowledge/ingest.py` 的 `main()`,把两种失败从 `build_index` 提上来并给 exit 1:

```python
def main() -> int:
    docs_dir = _docs_dir()
    if not docs_dir.is_dir():
        print(f"[错误] 规范目录不存在:{docs_dir}")
        print("       容器里确认 compose 挂了 ./data:/app/data;本机确认已把 backend/data 搬到仓库根 data/。")
        return 1
    pdfs = sorted(docs_dir.glob("*.pdf"))
    if not pdfs:
        print(f"[错误] {docs_dir} 里一份 PDF 都没有 —— 建出来的知识库会是空的。")
        return 1

    result = build_index(rebuild="--rebuild" in sys.argv)
    if not result:
        print(f"全部已入库、无需重建(共 {len(pdfs)} 份规范)。")   # ← 这才是真的成功
        return 0
    print("已建库:")
    ...
```

**为什么这条优先级高:** 它是所有路径类 bug 的**放大器**。修完之后,D2 的搬迁、
容器挂载写错、队友换机器——任何一种路径问题都会当场报错,而不是等到演示时
knowledge 说「规范里查不到」(而那句话跟真查不到长得一模一样)。

### 阶段四 · 开发回路(D6)

新增 **`docker-compose.dev.yml`**:

```yaml
# 开发态叠加层。用法(仓库根):
#   docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build
# 或 make dev-docker
#
# 为什么单独一份:演示要「镜像里是什么就跑什么」。挂源码会让镜像与实际运行的代码
# 不一致,出问题时分不清是镜像坏了还是本机代码坏了。两种用途,两份配置。
services:
  backend:
    volumes:
      - ./backend/src:/app/src:ro
```

`Makefile`:

```make
COMPOSE_DEV    := -f docker-compose.yml -f docker-compose.dev.yml

dev-docker: ## 容器内起后端并挂本机源码(热重载;日常开发用这个)
	$(COMPOSE) $(COMPOSE_DEV) up --build
```

### 阶段五 · 收尾(无决策空间)

- `ARTIFACTS_DIR ?= $(DATA_DIR)/artifacts` —— D2 统一后本来就对齐了,只需去掉 `backend/` 前缀
- `.PHONY` 补 `build-knowledge`(合并残留)
- `TOOL_NAMES` 补队友那 7 个工具名:`list_drawings` / `parse_drawing` / `query_dimension` /
  `list_components` / `layer_stats` / `render_preview` / `search_regulation`,否则界面显示英文函数名

### 阶段六 · 真机验收扩容(D7)

`backend/scripts/live_acceptance.py` 加两组:

```
E 组 · cad(3 条)
  E1  「有哪些图纸」          → 派给 cad,且返回图纸数 > 0    ← 路径铁证
  E2  「首层平面图有哪些图层」→ 列出图层,不报「一张图都没有」
  E3  库级:cad_index/ 下 json 数 == 演示图纸数

F 组 · knowledge(3 条)
  F1  「消防车道最小净宽是多少」→ 派给 knowledge
  F2  回答必须带《文件名》+ 页码(不带 = 判失败,它是 RAG 的全部价值)
  F3  库级:chroma 里文档数 > 0                              ← 路径铁证
```

> F1 的问法直接取自队友手册的测试用例,期望答「不小于 4 米」+ GB50016 页码。
> **E3/F3 是重点:** 路径错了这两条当场变红,而不是让系统静默地说「查不到」。

## 7. VPS:能解决,但不该做主路径

| 场景 | VPS 是否解决 |
|---|---|
| Intel Mac 装不上 torch | ✅(Docker 也解决,且不花钱) |
| 两人环境不一致 | ✅ 最彻底 |
| 队友首次构建等 30 分钟 | ✅ |
| 评委扫码自己体验 | ✅ **只有 VPS 能做**(TODO-1 的原始动机) |
| 演示机故障兜底 | ✅ 第四层 |
| **演示现场主路径** | ❌ **不该用** |

**为什么不做主路径:**

- 项目 **D9 决策**是「本地主跑 + 三层兜底」。把主路径押在会场 WiFi 上与既定决策冲突。
- **视觉缓存跟着机器走** —— 本机焐热的 22 分钟,VPS 上不认。

**硬前置 = TODO-7(鉴权):** `:2024` 是**零鉴权**的 Agent 执行端点,而两把 API Key 就在容器里。
`docker-compose.yml` 钉死 `127.0.0.1` 正是为了挡这个。**公网裸奔 = 账单敞开给人刷。**

最小安全集:① `backend/auth.py` + `langgraph.json` 声明 auth;② Caddy 反代 + 访问口令;
③ `/runs/*` 限流(`recursion_limit` 只限单次 run 的步数,不限次数);④ 2C4G 起,BGE-M3 吃内存。

**建议:现在别做。** 本方案做完后 VPS 只是「把同一份 compose 跑在别人机器上」,约 1 小时;
反过来不成立。已写进 TODO-1。

## 9. 失败模式

| 失败 | 测试 | 用户看到 | 判定 |
|---|---|---|---|
| 容器里 demo 资产路径错 | **E3/F3 + D3 的 exit 1** | 当场报错 | ✅ 已封 |
| 建库时目录不存在 | **D3 的 exit 1** | `[错误] 规范目录不存在: /xxx` | ✅ 已封 |
| knowledge 库空但目录在 | F3 断言库非空 | 「规范里没这条」 | ⚠️ **仍静默** → 见下 |
| `make up` 不带 `--build` | 无 | 功能正常但少 Agent | ⚠️ 靠 checklist |
| torch 版本冲突 | `uv lock --check` | 构建失败,明确 | ✅ 可接受 |
| 挂源码后 uid 不一致 | 无 | Linux 上权限拒绝 | ✅ Docker Desktop 自动处理 |
| BGE-M3 首次加载 2.2GB | 无超时 | 第一次问规范卡几十秒 | ⚠️ 靠预热 |
| 搬迁后忘了旧数据 | 无 | 台账/缓存"消失" | ⚠️ 其实是换了目录,checklist 提醒 |

**三个 ⚠️ 的处理:**

1. **库空 vs 真查不到** —— 本方案没解决(属队友泳道)。已列入 §6 告知清单。

## 12.2 计划外发现:容器跑在裸 UTC 上(已修)

做 T6 时顺出来的,**跟跨平台改造无关,但比它更该修**。

`backend/Dockerfile` 没设 `TZ`,容器跑在 UTC 上,而工地在中国(CST = UTC+8)。
`agents/schedule/tools.py:66` 用 `date.today()` 取「今天」,再由 `dates.py` 把
「明天/后天/下周三」算成具体日期 —— 时区错了,整条日期链跟着错。

**错的是哪一段:** UTC 落后 CST 8 小时,所以**中国时间每天 00:00–07:59**,容器还停在前一个日历日。
工友一早交班说「明天绑扎钢筋」,系统按前一天 +1,记成的是**今天**。而它一句错都不报。
剩下 16 小时两边同日 —— 所以这个洞专挑早班时段发作,白天的测试撞不见。

已在 Dockerfile 加 `ENV TZ=Asia/Shanghai`(基础镜像自带 zoneinfo,不用装 tzdata)。
修完实测:容器 `date.today()` == 中国时间的今天。

> **自我纠正记一笔。** 这条我第一版的注释是**错的** —— 写成「中国时间 16:00 之后容器停在前一天」,
> 方向反了(正确是 00:00–07:59);还把「宿主 08-10 / 容器 08-09」当成证据,
> 可那个差值取决于**宿主**在哪个时区(本机 AEST=UTC+10),那一刻 CST 也是 08-09、容器其实没错。
> 判据只有一条:容器的日期必须等于**中国时间**的日期。
> 记在这儿是因为它和 §12.1 里抓 agent 的那五条假注释是同一类错误 —— 谁写都会犯,所以要靠复核而不是靠自觉。
