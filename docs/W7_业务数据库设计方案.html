01

先回答:挂主 Agent 还是子 Agent

这个问题本身要拆成三层才答得准。

前提

主 Agent 这条路是堵死的。 supervisor 的系统提示词写死了它「自己不干活」:不凭知识回答、不自己判断照片、 不自己编清单、不自己算尺寸,只做判断派给谁和把结果转成人话两件事。 一旦破例让它直接读写数据库,整套路由纪律和汇报红线会跟着塌。

正确的分法是数据、能力、路由三层各归各位——数据层根本不属于任何一个 Agent:

层放哪归属
数据
表结构		 backend/src/gyt/db/<域>.py 共享地基。不属于任何一个 Agent,多个 Agent 可以读同一张表
能力
工具		 agents/<域>/tools.py 挂在子 Agent 上。一个业务域一个 Agent,全部走信封契约
路由
一行登记		 graph.py 的 AGENT_REGISTRY 主 Agent 只是多认识一位同事,它自己不碰库

已经有活样板可抄:schedule 子 Agent 记任务,底下压着 db/tasks.py—— 同步 sqlite3、每个操作一条独立连接、上层用 asyncio.to_thread 包。 打卡和排班照这个模子复制即可,不需要发明新架构。

建表语句

照 db/tasks.py 的成规写:幂等 IF NOT EXISTS、 NOT NULL / CHECK 约束下沉到表级、时间戳一律 ISO 文本。

-- 项目主表:分项目的根
CREATE TABLE IF NOT EXISTS projects (
  id         TEXT PRIMARY KEY,          -- 短码,如 'gyt-a3'
  name       TEXT NOT NULL,
  code       TEXT,
  created_at TEXT NOT NULL
);

-- 人员花名册
CREATE TABLE IF NOT EXISTS workers (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  project_id TEXT NOT NULL REFERENCES projects(id),
  name       TEXT NOT NULL,
  phone      TEXT,
  trade      TEXT,                       -- 工种
  active     INTEGER NOT NULL DEFAULT 1,
  created_at TEXT NOT NULL
);

-- 排班:一人一天一条班次
CREATE TABLE IF NOT EXISTS shifts (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  project_id TEXT NOT NULL REFERENCES projects(id),
  worker_id  INTEGER NOT NULL REFERENCES workers(id),
  work_date  TEXT NOT NULL,               -- ISO YYYY-MM-DD
  shift_type TEXT NOT NULL CHECK (shift_type IN ('day','night','off')),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  UNIQUE (worker_id, work_date)              -- 同一天不许排两个班
);

-- 打卡流水:上下班两个时间戳同行
CREATE TABLE IF NOT EXISTS attendance (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  project_id   TEXT NOT NULL REFERENCES projects(id),
  worker_id    INTEGER NOT NULL REFERENCES workers(id),
  work_date    TEXT NOT NULL,
  clock_in_at  TEXT,                        -- ISO 时间戳,NULL = 还没上班打卡
  clock_out_at TEXT,
  created_at   TEXT NOT NULL,
  updated_at   TEXT NOT NULL,
  UNIQUE (worker_id, work_date)              -- 一人一天一条,重复打卡走 UPDATE
);

-- 图纸索引:平立剖靠 view_type 区分,内容只存 artifact_id
CREATE TABLE IF NOT EXISTS drawings (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  project_id  TEXT NOT NULL REFERENCES projects(id),
  artifact_id TEXT NOT NULL,                -- 32 位 id,文件本身落盘
  view_type   TEXT NOT NULL CHECK (view_type IN ('plan','elevation','section')),
  floor       TEXT,
  title       TEXT NOT NULL,
  created_at  TEXT NOT NULL
);

设计红线

全部照现有 db/tasks.py 的成规,别另起炉灶:

  1. db 层要薄。 只管两件事:存取保真、表级约束。业务校验——空值、日期解析、 「已下班不许重复打卡」——一律归工具层,因为那里才能说中文人话、才能进信封契约。 搅进 db 层会把 SQL 和话术绑死,两头都难测。
  2. 同步 sqlite3 + asyncio.to_thread。 工具跑在 langgraph 事件循环里,同步 sqlite3 属阻塞 IO, blockbuster 会直接抛 BlockingError。丢线程池就地根治,不赖 --allow-blocking 这根拐棍。
  3. 大文件只走 artifact_id。 任务书 docx、图纸 PNG、将来的 3D 模型文件,一律落盘,库里只存 32 位 id。 这是项目的硬契约,不是本方案的偏好。
  4. 值全走 ? 占位。 SQL 文本里只许拼模块级常量片段,任何运行期的值(姓名、日期、id)绝不进入 SQL 文本。
  5. 暂时不上 Postgres。 工地就几十上百号人,SQLite 够用。真到「多工地并发写」那天再迁—— 那是一个明确的阈值,不是现在就要付的复杂度。
04

需要先拍板的三件事

这三个答案会实质改变上面的方案,不是细节偏好。

打卡怎么输入? 影响 attendance 形态

师傅对 Agent 说「我到了」、拍现场照(可复用 safety 的视觉线)、扫码、还是 GPS 定位? 这决定 attendance 是纯文本工具,还是要接多模态。后者的工作量是前者的数倍。

「3D 化」要到什么程度? 量级不同,须单独立项

这一个和其他不是一个量级。若是真 BIM / IFC 建模,那是独立的几何引擎工程 (ifcopenshell 那一层),不是「cad Agent 加个工具」能收的; 若只是「平面图拉伸出示意体块」或「多视图切换看」,那才轻。 别把它和打卡排班混在同一个迭代里估工。

多项目是真并发,还是演示期先单项目? 影响是否现在做隔离

真多工地并发,现在就得上项目隔离和权限; 演示期单项目的话,project_id 填个默认值先跑通即可, 表结构照上面建,字段留着但不做隔离逻辑——和 tasks 当初预留 project_id 是同一个策略。
