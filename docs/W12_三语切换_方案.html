三语切换

需求是两件:界面能切三语、模型按用户输入的语言回话。 四轮探针 155 次真调用之后,顺序跟直觉相反 —— 答话排在界面前面。

第一批只做一件:繁體答话,靠前端渲染层的字形转换
第一批   繁體答话      前端末端转换(简→繁 s2hk)     零后端、零提示词、零缓存影响
第二批   英文答话      提示词管道 + 修引用格式
         + 界面三语    英文用户读不懂简体界面,两者必须一起
推迟     监理面板      等 W11 术语定案

为什么答话反而排在界面前面(这与本文件 v1 的推荐相反): 探针实测繁體靠提示词走不通(25%–60%,门槛 80%),唯一解是 输出侧字形转换 —— 那是确定性结构件,不是概率性提示词。 而字形转换不需要术语表,所以它不依赖 W11。

繁體用户读得懂简体界面(简繁互通度高),所以只做答话就有实质价值; 英文用户读不懂,所以英文那批必须带界面。对话是产品,界面是框。

01 · 需求与分层

三层,三层的规矩完全不同

把「三语」当成一件事去做,是这个需求最容易踩的坑。 它其实是三件独立的事,风险差着数量级。

界面文案 —— 约 542 条中文短语,散在 16 个前端覆盖件里。 纯体力活,抽成三语词典。
风险 低
可拆着上

模型答话 —— 9 份 prompt.md 加 supervisor 提示词。 靠中间件在请求期注入一行语言指令。这一层没有结构件兜得住。

需前置探针
L3
数据与文书 —— 库里存的中文、六种法定文书。 绝不翻译,只在显示层做映射。
风险 中
动数据 = 坏索引

02 · 会咬人的事实

五条,每条都有实测依据

2.1 库里存的是中文,而且进了唯一索引和 CHECK 约束

item   TEXT NOT NULL,                                    -- 存「临边无防护」
grade  TEXT NOT NULL CHECK (grade IN ('一般', '严重')),
UNIQUE (project_id, photo_sha256, item)                  ← item 在唯一键里
在存储层做任何翻译 = 唯一索引当场失效

同一张照片的同一条隐患,简体一条、繁體一条,重复登记,而且不会报错。

定案:库里那 8 个词当「代码」用,只在显示层查三语词表。 hazards.item 一个字不动。

顺带:agents/safety/severity.py 的定级表已经用这 8 个词当键, 并且有一条测试盯着它与受控词表完全同步。三语表照抄这个守卫形状,不用重新发明。

2.2 视觉缓存不能碰,而它跟文本提示词共用一个键

prompt_version 是全局的(config.py → llm.py,路径甲乙共用)。按老规矩「改提示词就 bump prompt_version」——

一次改语言 = 视觉缓存全废 = 22 分钟 + 真花钱(TODO-11 演示铁律)

定案:语言指令走运行时注入,不写进 prompt.md 文件、 不 bump prompt_version。

文本缓存:messages 变了 → 自然失效(正确且便宜)。
视觉缓存:键 =(模型, prompt_version, vision messages, extra), 一个都没变 → 完好。

🔴 vision_prompt.md 一个字都不许动。 它产出的是那 8 个数据代码,不是给人看的话。

但文本缓存挡不住 —— 见 2.6,那是这个需求唯一真实的性能代价。

2.6 性能:量过了,只有一项是真的

「不能影响性能」是负责人给的硬约束。以下全是 2026-08-17 实测,不是估算。

项实测判定
语言判定 CPU(最坏:扫穿 20 轮全判不出)24.7 µs 一轮累计 0.124 ms,占模型调用 0.00165%
单条消息判定9.7 µs—
Prompt token 增量+19 token 占提示词 0.8–3.9%(平均 1.1%)
每轮多花的钱¥0.000095—
前端三语词典gzip 2.3 KB预算 300 KB,占 0.8%
视觉缓存 kimi-k3 163 条完好 ✅ 最贵的那部分保住了
文本缓存 deepseek-v4-flash 1102 条 失效 值 ¥2.03,全是开发期的 —— 见下方两段

判定基准的复现方式:158 字判别集、20 轮线程、每轮 15–60 字,20000 次取均值。

⚠️ 修正:那 1102 条没有第一版说的那么值钱

第一版把「1102 条全废」写成唯一真实影响 —— 这句只对「简体是主力」成立

缓存键里含用户的问题本身(meta.messages_digest)。实测: 1102 条里有 1060 个不同的 digest —— 几乎每条都是不同的问题。

简体用户提问  →  1102 条里可能有命中        ← 语言行会打掉它,真影响
繁體用户提问  →  字都不一样,digest 不同
                 本来就一条都不命中          ← 语言行不改变任何事

而 2026-08-17 负责人定案:界面默认繁體(判断是本地工友为主)。 那么繁體是主力答话语种,这 1102 条简体缓存对主力用户本来就是死的。

那 1102 条到底是什么(打开数过)

类型条数占比
带工具调用的响应54750%
纯文本答话(Agent 把工具结果念成人话)48544%
supervisor 的派活说明文字706%

工具调用里最多的是交接决策 —— transfer_to_schedule 141、 transfer_to_safety 85、transfer_to_inspection 50、 list_tasks 46、add_task 27、 analyze_site_photo 27。一条长这样:

"content": "用户要看照片里有没有人没戴安全帽,这是查现场照片的问题,派给 safety。"
"tool_calls": [transfer_to_safety]

就是 supervisor 在做「这句话该派给谁」的判断。 那 141 条 transfer_to_schedule 基本是 routing 评测 33 行 + 真机验收 25 断言 反复跑攒下来的。

累计省下  输入 1,902,826 token / 输出 64,426 token
按 DeepSeek-flash 估 ≈ ¥2.03
两块钱,而且全是开发期的

生产上每个工友问的话都不一样,这些一条都不会命中。

作废它们,受影响的是三件开发侧的事:make eval SUITE=routing (CLAUDE.md 说「第二轮起命中缓存则秒级」)、真机验收 25 断言、手工联调。 make test 全 mock,不受影响。

而 06 节已经写明:加一行语言指令 = 改了 supervisor 提示词 = routing 留档数当场失效、本来就必须重跑。所以这一项代价与语言改动是 重叠的,不是新增的。

结论:拿两块钱 + 一次本来就要跑的评测,去换「主力语种的指令要靠覆盖指令 压过前一句」这种脆性,不划算。甲 / 甲′ 的权衡到此压平, 甲′ 的理由从「推测」变成了「数出来的」。

那 1102 条怎么办 —— 原计划里有一步是多余的

缓存键是 langchain 的 (prompt, llm_string) (llm.py:707 的 lookup 签名),而 prompt 里含 system prompt。多一行 = 全部 miss。

原计划要把 9 份 prompt.md 末尾那句「用简体中文,说人话,句子短」 抽掉,改成三语都运行时注入。别抽:

简体请求   → system_message 一字不变 → 1102 条缓存 100% 命中   ✅
繁體/英文  → 追加一行覆盖指令        → 各自新缓存空间
默认语种零成本

而且 9 份 prompt.md 一个字不用改 —— 少一批 diff、少一处同源风险, 第一版评审里「头注会变成过期注释」那条发现直接消失。

三个方案,由探针定

「默认语种不注入」这条对哪个语种生效,取决于 prompt.md 末尾那行写的是什么。于是有三条路:

免费语种(零注入)那 1102 条主力语种的指令
甲 prompt.md 保持简体简体 保住 繁體靠覆盖指令,脆
甲′ prompt.md 那行改繁體繁體 作废(对主力本来无用) 零注入,最干净 ✅
乙 抽掉语言行无 作废三语平等注入
甲′ 是负责人选繁體之后推出来的最优解

主力语种拿到最干净的指令(= L2 那个最大未知数上最有利的一档), 而作废的缓存对主力本来就不命中。

改动量:9 个文件各改一行 —— 末尾「用简体中文,说人话,句子短」改成繁體。 提示词正文不用翻译(那是给模型的指令,简体写没问题), 只有「用什么语言回答」那句要改。

唯一真实代价:改 prompt.md 正文属于会动缓存键的改动, 简体那 1102 条一次性作废(= ¥2.03 + 一次本来就要跑的 routing)。

→ 由第 0 步探针出三组数据再定(见 05)。

还有一条:缓存空间碎片化 3 倍

同一个问题用三种语言问 = 三条缓存。这不是「变慢」,是命中率下降。 对演示预热的影响:要焐三遍才能三语都秒回。方案甲把它降成「焐两遍」—— 默认语种直接复用现有的 1102 条。

2.3 语言指令必须走 system_message,绝不许追加 HumanMessage

ModelRequest 字段实测:

['model', 'messages', 'system_message', 'tool_choice', 'tools',
 'response_format', 'state', 'runtime', 'model_settings']

override(**overrides) 收 system_message   ✅ 源码确认
system_message: SystemMessage | None      ✅

而 core/require_tool.py 的 _is_turn_start 实测:

last = messages[-1]
if isinstance(last, HumanMessage):
    return True
追加 HumanMessage → 最后一条永远是它 → _is_turn_start 恒为 True

后果是守卫每一轮都误判成回合首答,把模型正在念工具结果的合法纯文本 当成「没调工具」打回重试。

第二处:RequireReceiptSource._sourced(W9 加的第三种判据) 会把用户发言当合法出处扫。

定案:request.override(system_message=...), messages 一个字节不动。

2.4 繁简自动转换会静默出错

一简对多繁:干→幹/乾/干,发→發/髮, 面→麵/面,里→裡/里。工地场景里 干活/乾燥、发现/头发 都会撞。

已有规矩(D12,W7 立的)必须继承:姓名任何情况下不转换。再加两条: 工地名不转(人给的)、法定文书标题不转(见第 07 节)。

定案:词表人工维护,落成静态表进 git。运行时不做转换。

2.5 简繁判定对短句判不出来

「好」「收到」「拍好了」在简繁里逐字相同。8 类违规项里也有一半相同 (未戴安全帽、消防通道堵塞)。

现成方案([Layer 1],搜索确认): hanzidentifier(Python,返回 SIMPLIFIED / TRADITIONAL / BOTH / UNKNOWN / MIXED,它的 BOTH 正是这一档)、 traditional-or-simplified(npm)。 权威数据源是 Unihan 的 kSimplifiedVariant / kTraditionalVariant。

定案:不引库,两边共用一张小判别字集

① 引 Python 包 → uv.lock 变 → 镜像重建。TODO-40 记着 30GB 的 VPS 装不下一次后端全量重建,失败还会把镜像记录 GC 掉。为判别功能付这个代价不值。

② 判别不需要完整转换表。工地对话的高频判别字就那些:们/們、这/這、个/個、 问/問、时/時、开/開、点/點、现/現、报/報、后/後、边/邊、无/無、电/電、动/動、 护/護、检/檢、单/單、员/員、场/場、图/圖…… 一张 200 字的对照表够用。

③ 前后端各一份 → 照 ROUNDTRIP_VECTORS ↔ checkin-lib.test.ts 那个已有的同源模式,两边注释互指, 后端改判据前端测试先红。

诚实标出的风险:手工字集一定会漏。但漏了的表现是「落回上一条 / 落回默认」, 不是乱码 —— 这是个安全的失败方向。

03 · 架构定案

语言从哪来,指令挂哪层

3.1 两层,两层都要

显式 UI 选择(经 context_schema)        ← 用户按过切换器就以它为准
        │ 用户从没碰过切换器
        ▼
往回扫本线程的 HumanMessage              ← 「第二句只打好」靠它
        │ 全线程判不出来(纯图片开局等)
        ▼
GYT_DEFAULT_LANG(config.py 常量)

为什么两层都要 —— 这条是对抗复审推翻第一版得到的(见第 08 节)。 只有第二层的话,这个场景会错:

用户全程简体聊了十轮
    ↓ 点了界面上的 English 切换器        ← 显式意图
    ↓ 打字:「ok」
    ↓ 往回扫 → 找到十轮简体 → 用简体答    ← 把用户的显式选择覆盖掉

用户按了按钮而系统当没看见,比语言判错更糟。

3.2 管道成本 —— 一行,不是七处

grep create_agent( backend/src/gyt/  →  core/base_agent.py:210   (只有一处)

create_gyt_agent 是唯一工厂,八个 Agent 全过它。加 context_schema= 是一个文件一行,不是「七个 Agent 的构造全改」。

3.3 中间件挂哪层

create_gyt_agent 里是 middleware=[FocusOnOwnWork(name), *extra_middleware], 列表前面的包在外面。

语言中间件必须在 Focus 里面 —— 它要判的是「用户说了什么」,而未裁的 messages 里混着 supervisor 的派活腔(那是另一个模型生成的文本, 语言不受用户控制),拿它去判就是判错。

create_agent 的中间件洋葱(外 → 内)

  FocusOnOwnWork(name)          裁掉 supervisor 纯文本
    └── SpeakUserLanguage       ← 新增,判定用裁后的 messages
          └── RequireLedgerTool / RequireReceiptSource
                └── 真正的 model call

放 extra_middleware 的第一位:这样守卫重试时语言指令 已经在 system_message 上了,重试路径透明。

3.4 supervisor 那层走另一条路

Prompt = SystemMessage | str | Callable[[StateSchema], ...] | Runnable

create_supervisor 的 prompt 接受 callable(实测), 所以 supervisor 直接传函数,不用中间件。

3.5 401 / 429 拒绝句永久不国际化

backend/auth.py:115
DENY_MESSAGE: Final[str] = "访问被拒绝,请联系发你链接的人。"
"""三种失败(没带头 / 带了空串 / 令牌不对)回的是一模一样的一句话,
这是故意的:任何差异都是送给爆破脚本的信号。"""
两个理由,第二个更硬

① 401 发生在鉴权之前 —— 没有会话、没有用户、没有偏好, 服务端根本不知道该用哪种语言。

② 唯一可用的信号是 Accept-Language,而那是 攻击者完全可控的头。一旦实现里出现任何分支(哪怕是「令牌有效 → 用用户语言; 无效 → 用 Accept-Language」),就是一个账号 / 令牌存在性预言机 —— 正是这条注释花力气防的东西。

定案:DENY_MESSAGE / RATE_LIMITED_MESSAGE / errors.py 的 UNAUTHORIZED 三处保持中文、保持一字不差, 并加注释说明「本条刻意不国际化,理由见 auth.py 头注」。

乙(schedule 8 题)   37.5%  →   50%

同样的提示词、同样的问题、temperature=0,两轮差 2 行(25pt)。 DeepSeek 的温度 0 不是确定性的(MoE 路由 + 批处理导致)。

所以第一轮那三个数(70/55/75)的差异也在噪声里,分不出高下。 这与 TODO-13 记的视觉端「±1 行固有噪声」是同一件事,这边更大。

钉死的结论

① 五个档位(甲 / 甲′ / 乙 / 丙 / 丁)没有一个把 schedule 拉过 60%, 门槛是 80%。判据「三个都 < 80% → 回来重想 L2 形状,别硬上」压倒性地触发了。

② 靠提示词让模型换语言,在需要调工具的 Agent 上不成立。 CLAUDE.md 高危陷阱那条的第四次应验 —— 这次是真金白银测出来的。

③ 结构件在哪:输出侧转换。模型输出简体,渲染前做 简→繁。 它是确定性的,不是概率性的。

2.4 那条定案要分家

2.4 写着「繁简自动转换会静默出错,定案:运行时不做转换」。 那条对 UI 词表成立,对模型输出不成立 —— 原来把两者混为一谈了:

集合人工维护不转换的后果
UI 文案有限(166 条)可行,质量最高—
模型输出无限不可能 100% 是简体

对模型输出,自动转换哪怕有 1% 的字形选错(干/幹/乾 那类), 也远好过「不转换 = 100% 错」。这不是同一个权衡。

香港场景要用 s2hk(简体 → 香港繁體)那档配置,不是 s2t。 放前端渲染层做:零后端依赖、零镜像重建。

本仓的传统:docs/W5_…方案.md 第 10 节记着 「两条方案决策被实测推翻」。这一节同理。

8.1 「先做 L2,风险最小」

L2 是 1.5 天,风险最小,应该先做。

L2 整个建立在一行提示词上,而这正是 CLAUDE.md 点名的那类做法。 主流中文模型训练语料以简体为主,繁體输出会中途漂回简体,尤其是专业名词。而这一层 没有结构件兜得住 —— 简→繁自动转换有一简对多繁的问题(2.4 自己写的), 所以没法在输出侧纠正。不对称在于:English 大概率没问题, 繁體是风险项且无回退。
→ 加了第 0 步探针。

8.2 「砍掉整条管道」

砍掉 gyt_lang 管道,只往回扫线程;要读到得给每个 Agent 声明 context_schema,那是七个 Agent 的构造全改。

create_agent( 全仓只有 base_agent.py:210 一处。 加 context_schema= 是一个文件一行 —— 成本估高了一个数量级。 更糟的是,砍掉管道之后「用户点了 English 切换器却被扫描拉回简体」(3.1 那个场景)。 第一版的两个目标自相矛盾,而我没发现。
→ 改成两层,显式优先。

8.3 「追加 HumanMessage 会让 test_require_tool.py 红」

变异表里把它列成「应该红」的已有测试。

实测下来它不会红 —— 那些测试直接构造 message list 测函数, 不叠中间件栈;唯一跑真栈的 test_report.py 只走正常路径。 这正是 learnings 里 red-line-satisfiable-without-being-honored 那条的形状: 「有守卫」不等于「守卫被这个改动触发」。
→ 06 节第一行标成必须新写的集成测试。
