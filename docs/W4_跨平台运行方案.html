02 / 架构

一个镜像,两份 compose,一个数据目录
   Mac (Intel)                                         Windows + WSL2
   ┌──────────┐        ┌─────────────────────────┐      ┌──────────┐
   │ 编辑器   │───挂源码►│ gyt-backend  :2024     │◄─挂源码──│ 编辑器   │
   │ 改代码   │        │  5 Agent 全可用          │      │ 改代码   │
   └──────────┘        │  BGE-M3 已烤进镜像       │      └──────────┘
                       └───────────┬─────────────┘
                                   │ 挂载 ./data:/app/data
                       ┌───────────▼─────────────┐
                       │ <repo>/data/            │ ◄── 统一到这一个目录(D2)
                       │   demo/       源资产(进git)│
                       │   artifacts/  巡检记录     │
                       │   chroma/     规范向量库   │
                       │   cache/      视觉缓存     │ ◄── 焐热一次,处处命中
                       │   gyt.sqlite3 任务台账     │
                       └─────────────────────────┘

  docker-compose.yml          交付/演示态 —— 纯镜像,不挂源码
  + docker-compose.dev.yml    开发态 —— 追加挂 ./backend/src,热重载

  本机 backend/data/ 基本退役(只剩 make test 用 tmp_path,不碰它)

为什么分两份 compose:演示要的是「镜像里是什么就跑什么」。挂源码会让镜像与实际运行的代码不一致,出问题时分不清是镜像坏了还是本机代码坏了。两种用途,两份配置。

03 / 决策

七个已定的选择
#决策选择理由
D1跨平台策略全面统一 Docker 启动一套环境;队友净收益(不用本机维护几 GB 重依赖)
D2数据目录统一到仓库根 data/缓存/台账/知识库/产物四样共享;顺带让 D4 从「加配置项」缩成「改默认值」
D3建库信号分开退出码 + 明确原因「没找到 PDF」和「已入库」现在是同一句话+同一个退出码,是所有路径 bug 的放大器
D4资产路径随 D2 自动解决统一后 demo 资产就是 data_dir/"demo",本机与容器自动对齐
D5镜像体积CPU-only torch砍 2.4GB CUDA(代码已 device="cpu")
D6开发回路dev override 挂源码否则改一行要重建;这也是队友肯换过来的前提
D7验收覆盖补 E/F 两组 + 路径铁证路径 bug 的失败方式是静默的

04 / 实施

六个阶段

阶段一 · 依赖与体积(D5)

[[tool.uv.index]]
name = "pytorch-cpu"
url = "https://download.pytorch.org/whl/cpu"
explicit = true

[tool.uv.sources]

⚠️ uv.lock 是队友刚提交的,动之前跟他说一声,别两边同时改。
⚠️ 若 sentence-transformers 对 torch 有版本下限冲突,实测报错再调版本号,不要凭记忆填。

阶段二 · 统一数据目录(D2 + D4)

config.py —— 只改一个默认值:

def _default_data_dir() -> Path:
    """数据根目录的默认值。

    本文件是 <repo>/backend/src/gyt/config.py:
        parents[0]=gyt  [1]=src  [2]=backend  [3]=<仓库根>

    ⚠️ 原来是 Path("data"),按**进程工作目录**解析 —— 而 make dev 在 backend/ 下跑,
       数据落在 backend/data;容器里 GYT_DATA_DIR=/app/data(compose 挂仓库根 ./data)。
       两条路径因此有两份数据:缓存、台账、知识库、产物全部分裂。
       统一到仓库根之后,demo 资产就是 data_dir/"demo",本机与容器自动对齐,
       不需要再为演示资产单开一个配置项。
    """
    return Path(__file__).resolve().parents[3] / "data"

data_dir: Path = Field(default_factory=_default_data_dir)

同文件加一个派生属性(刻意不 _ensure_dir —— 它是源资产,自动创建反而掩盖「资产丢了」):

@property
def demo_assets_dir(self) -> Path:
    """演示源资产(照片/图纸/规范 PDF)。随仓库走、进 git。
    容器 /app/data/demo,本机 <repo>/data/demo —— 自动对齐。"""
    return self.data_dir / "demo"

knowledge/ingest.py:40 与 cad/demo_registry.py:37 改成读配置。别在模块级调 get_settings()(import 时固化,测试改环境变量就失效):

def _docs_dir() -> Path:
    return get_settings().demo_assets_dir / "docs"

一次性搬迁:

cd <repo>
mkdir -p data
mv backend/data/* data/ 2>/dev/null || true    # demo/ 已在 data/ 下,不冲突
rmdir backend/data 2>/dev/null || true

视觉缓存搬过去照样命中——缓存键算在图片内容上,不含路径。台账 sqlite 同理。
.gitignore 不用改:现有的 /data/* + !/data/demo/ 正好就是对的规则。
两处文件顶部那句「parents[5] = 仓库根」的注释要一并改掉——陈旧注释比没注释更害人。

阶段三 · 建库信号(D3)

def main() -> int:
    docs_dir = _docs_dir()
    if not docs_dir.is_dir():
        print(f"[错误] 规范目录不存在:{docs_dir}")
        print("       容器里确认 compose 挂了 ./data:/app/data;本机确认已把 backend/data 搬到仓库根。")
        return 1
    pdfs = sorted(docs_dir.glob("*.pdf"))
    if not pdfs:
        print(f"[错误] {docs_dir} 里一份 PDF 都没有 —— 建出来的知识库会是空的。")
        return 1

    result = build_index(rebuild="--rebuild" in sys.argv)
    if not result:
        print(f"全部已入库、无需重建(共 {len(pdfs)} 份规范)。")   # ← 这才是真的成功
        return 0

为什么这条优先级高:它是所有路径类 bug 的放大器。修完之后,D2 的搬迁、容器挂载写错、队友换机器——任何一种路径问题都会当场报错,而不是等到演示时 knowledge 说「规范里查不到」(而那句话跟真查不到长得一模一样)。

阶段六 · 真机验收扩容(D7)

他那份手册要改的地方

《本地启动手册_Mac.md》基本可以复用——踩过的坑都记了(--allow-blocking、hf-mirror 失效、端口红线、overrides 不能直接改)。但有两处必须改。

位置现状改成
