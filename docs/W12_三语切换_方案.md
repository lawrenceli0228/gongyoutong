# W12 三语切换(简体 / 繁體 / English)技术方案

> 2026-08-17 · v1(含评审与对抗复审)· 交付物:本文件 + `W12_三语切换_方案.html`

## 0. 一句话结论(四轮探针 + 两轮评审后重写)

需求是两件事:**界面能切三语**、**模型按用户输入的语言回话**。

**第一批只做一件:繁體答话,靠前端渲染层的字形转换。**

```
第一批   繁體答话      前端末端转换(简→繁 s2hk)     零后端、零提示词、零缓存影响
第二批   英文答话      提示词管道 + 修引用格式
         + 界面三语    英文用户读不懂简体界面,两者必须一起
推迟     监理面板      等 W11 术语定案
```

**为什么答话反而排在界面前面**(这条与本文件 v1 的推荐相反):

- 探针实测(155 次真调用,§4.5):**繁體靠提示词走不通**(25%–60%,门槛 80%),
  唯一解是输出侧字形转换 —— 而那是**确定性结构件**,不是概率性提示词
- 而字形转换**不需要术语表**(「臨邊無防護」零风险),所以它**不依赖 W11**
- **繁體用户读得懂简体界面**(简繁互通度高),所以只做答话就有实质价值;
  **英文用户读不懂**,所以英文那批必须带界面
- 对话是产品,界面是框。第一批先把对话做原生。

## 1. 需求与分层

用户原话:「做网站的简体繁体和英文的切换,然后根据用户的输入回答简体繁体和英文的答案。」

拆成三层,**三层的规矩完全不同**:

```
L1  界面文案      ~542 条中文短语,16 个覆盖件         纯前端,风险低
L2  模型答话      9 份 prompt.md + supervisor 提示词   中间件注入,风险 ★ 未知
L3  数据与文书    库里存的中文 + 六种法定文书           绝不翻译,只做显示映射
```

### 1.1 实测的量(2026-08-17 全仓扫描)

| 位置 | 数量 | 说明 |
|---|---:|---|
| 前端覆盖件含中文的**代码行** | 816 | 上限口径 |
| 前端**中文短语片段**(非注释区) | ~542 | 中间口径 |
| 前端能自动抓到的**字符串字面量** | 201 | 下限口径(JSX 跨行文本抓不全) |

| 后端 `detail=`(只进日志) | 26 | **不翻** |

| 提示词文件 | 9 份 | 每份末尾都有一句「用简体中文,说人话」 |

⚠️ **三个口径差得远。** 2026-08-17 已按「第一批范围」数清楚:**181 条,去重 166 条**

三语对他的边际价值远低于对工友的。这是分批的第一个理由;第二个理由见 §7。

## 2. 五条会咬人的事实

### 2.1 库里存的是中文,而且进了唯一索引和 CHECK 约束

```sql
item   TEXT NOT NULL,                                    -- 存「临边无防护」
grade  TEXT NOT NULL CHECK (grade IN ('一般', '严重')),
UNIQUE (project_id, photo_sha256, item)                  -- ← item 在唯一键里
```

**在存储层做任何翻译 = 唯一索引当场失效** —— 同一张照片的同一条隐患,简体一条、
繁體一条,重复登记,而且不会报错。

**定案:库里那 8 个词当「代码」用,只在显示层查三语词表。`hazards.item` 一个字不动。**

顺带:`agents/safety/severity.py` 的定级表**已经**用这 8 个词当键,并且有一条测试
盯着它与受控词表完全同步。三语表照抄这个守卫形状,不用重新发明。

### 2.2 视觉缓存不能碰,而它跟文本提示词共用一个键

`prompt_version` 是**全局**的(`config.py` → `llm.py`,路径甲乙共用)。按老规矩
「改提示词就 bump prompt_version」——

> **一次改语言 = 视觉缓存全废 = 22 分钟 + 真花钱**(TODO-11 演示铁律)

**定案:语言指令走运行时注入,不写进 `prompt.md` 文件、不 bump `prompt_version`。**

- 文本缓存:messages 变了 → 自然失效(正确且便宜)
- 视觉缓存:键 = (模型, prompt_version, **vision messages**, extra),**一个都没变** → 完好

🔴 **`vision_prompt.md` 一个字都不许动。** 它产出的是那 8 个数据代码,不是给人看的话。

**但文本缓存挡不住 —— 见 §2.6,那是这个需求唯一真实的性能代价。**

### 2.6 性能:量过了,只有一项是真的

「不能影响性能」是硬约束。2026-08-17 实测,不是估算:

| 项 | 实测 | 判定 |
|---|---:|---|
| 语言判定 CPU(最坏:扫穿 20 轮全判不出) | **24.7 µs** | 一轮累计 **0.124 ms**,占模型调用 **0.00165%** |
| 单条消息判定 | 9.7 µs | — |
| Prompt token 增量 | **+19 token** | 占提示词 0.8–3.9%(平均 **1.1%**) |
| 每轮多花的钱 | **¥0.000095** | — |
| 前端三语词典 | **gzip 2.3 KB** | 预算 300 KB,占 0.8% |
| 视觉缓存 `kimi-k3` 163 条 | **完好** | ✅ 最贵的那部分保住了 |
| **文本缓存 `deepseek-v4-flash` 1102 条** | **对简体主力才是真影响** | 见下方「⚠️ 修正」 |

判定基准的复现方式:158 字判别集、20 轮线程、每轮 15–60 字,20000 次取均值。

#### ⚠️ 修正:那 1102 条没有第一版说的那么值钱

第一版把「1102 条全废」写成**唯一真实影响**。**这句只对「简体是主力」成立。**

缓存键里**含用户的问题本身**(`meta.messages_digest`)。实测:**1102 条里有
1060 个不同的 digest** —— 几乎每条都是不同的问题。于是:

```
简体用户提问  →  1102 条里可能有命中        ← 语言行会打掉它,真影响
繁體用户提问  →  字都不一样,digest 不同
                 本来就一条都不命中          ← 语言行不改变任何事
```

**而 2026-08-17 负责人定案:界面默认繁體(判断是本地工友为主)。**
那么繁體是主力答话语种,这 1102 条简体缓存**对主力用户本来就是死的**。

#### 那 1102 条到底是什么(打开数过)

| 类型 | 条数 | 占比 |
|---|---:|---:|
| 带工具调用的响应 | 547 | 50% |
| 纯文本答话(Agent 把工具结果念成人话) | 485 | 44% |
| supervisor 的派活说明文字 | 70 | 6% |

工具调用里最多的是**交接决策** —— `transfer_to_schedule` 141、`transfer_to_safety` 85、
`transfer_to_inspection` 50、`list_tasks` 46、`add_task` 27、`analyze_site_photo` 27。
一条长这样:

```json
"content": "用户要看照片里有没有人没戴安全帽,这是查现场照片的问题,派给 safety。"
"tool_calls": [transfer_to_safety]
```

**就是 supervisor 在做「这句话该派给谁」的判断。** 那 141 条 `transfer_to_schedule`
基本是 routing 评测 33 行 + 真机验收 25 断言反复跑攒下来的。

**值多少:**

```
累计省下  输入 1,902,826 token / 输出 64,426 token
按 DeepSeek-flash 估 ≈ ¥2.03
```

**两块钱,而且全是开发期的** —— 生产上每个工友问的话都不一样,这些一条都不会命中。

作废它们,受影响的是三件**开发侧**的事:`make eval SUITE=routing`(CLAUDE.md 说
「第二轮起命中缓存则秒级」)、真机验收 25 断言、手工联调。
**`make test` 全 mock,不受影响。**

而 §6.3 已经写明:加一行语言指令 = 改了 supervisor 提示词 = **routing 留档数
当场失效、本来就必须重跑**。所以这一项代价与语言改动是重叠的,不是新增的。

**结论:拿两块钱 + 一次本来就要跑的评测,去换「主力语种的指令要靠覆盖指令
压过前一句」这种脆性,不划算。** 甲 / 甲′ 的权衡到此压平,甲′ 的理由从
「推测」变成了「数出来的」。

#### 那 1102 条怎么办 —— 原计划里有一步是多余的

缓存键是 langchain 的 `(prompt, llm_string)`(`llm.py:707` 的 `lookup` 签名),
而 `prompt` 里含 system prompt。**多一行 = 全部 miss。**

原计划要把 9 份 `prompt.md` 末尾那句「用简体中文,说人话,句子短」抽掉,
改成三语都运行时注入。**别抽:**

```
简体请求   → system_message 一字不变 → 1102 条缓存 100% 命中   ✅
繁體/英文  → 追加一行覆盖指令        → 各自新缓存空间
```

**默认语种零成本。** 而且 9 份 `prompt.md` 一个字不用改 —— 少一批 diff、
少一处同源风险,第一版评审里「头注会变成过期注释」那条发现直接消失。

#### 三个方案,由探针定

「默认语种不注入」这条对哪个语种生效,取决于 `prompt.md` 末尾那行写的是什么。
于是有三条路:

| | 免费语种(零注入) | 那 1102 条 | **主力语种**的指令 |
|---|---|---|---|
| **甲** `prompt.md` 保持简体 | 简体 | 保住 | 繁體靠覆盖指令,**脆** |
| **甲′** `prompt.md` 那行改繁體 | **繁體** | 作废(对主力本来无用) | **零注入,最干净** ✅ |
| **乙** 抽掉语言行 | 无 | 作废 | 三语平等注入 |

**甲′ 是负责人选繁體之后推出来的最优解**:主力语种拿到最干净的指令
(= L2 那个最大未知数上最有利的一档),而作废的缓存对主力本来就不命中。

- **改动量:9 个文件各改一行** —— 末尾「用简体中文,说人话,句子短」改成繁體。
  **提示词正文不用翻译**(那是给模型的指令,简体写没问题),只有「用什么语言回答」那句要改。
- **唯一真实代价:** 改 `prompt.md` 正文属于会动缓存键的改动,简体那 1102 条一次性作废。

**→ 由第 0 步探针出三组数据再定(§5)。**

#### 还有一条:缓存空间碎片化 3 倍

同一个问题用三种语言问 = 三条缓存。这不是「变慢」,是**命中率下降**。
对演示预热的影响:**要焐三遍才能三语都秒回**。方案甲把它降成「焐两遍」
(默认语种直接复用现有的 1102 条)。

### 2.3 语言指令必须走 `system_message`,绝不许追加 HumanMessage

`ModelRequest` 字段实测:

```
['model', 'messages', 'system_message', 'tool_choice', 'tools',
 'response_format', 'state', 'runtime', 'model_settings']

override(**overrides) 收 system_message   ✅(源码确认)
system_message: SystemMessage | None      ✅
```

而 `core/require_tool.py` 的 `_is_turn_start` 实测:

```python
last = messages[-1]
if isinstance(last, HumanMessage):
    return True
```

**追加 HumanMessage → 最后一条永远是它 → `_is_turn_start` 恒为 True。**
后果是守卫每一轮都误判成回合首答,把模型正在念工具结果的合法纯文本当成
「没调工具」打回重试。

第二处:`RequireReceiptSource._sourced`(W9 加的第三种判据)**会把用户发言当合法出处扫**。

**定案:`request.override(system_message=...)`,messages 一个字节不动。**

### 2.4 繁简自动转换会静默出错

一简对多繁:`干`→幹/乾/干,`发`→發/髮,`面`→麵/面,`里`→裡/里。
工地场景里 `干活`/`乾燥`、`发现`/`头发` 都会撞。

已有规矩(D12,W7 立的)必须继承:**姓名任何情况下不转换**。再加两条:
**工地名不转**(人给的)、**法定文书标题不转**(见 §7)。

**定案:词表人工维护,落成静态表进 git。运行时不做转换。**

### 2.5 简繁判定对短句判不出来

「好」「收到」「拍好了」在简繁里逐字相同。8 类违规项里也有一半相同
(`未戴安全帽`、`消防通道堵塞`)。

现成方案(**[Layer 1]**,搜索确认):

- [hanzidentifier](https://github.com/tsroten/hanzidentifier)(Python)—— 返回
  `SIMPLIFIED / TRADITIONAL / BOTH / UNKNOWN / MIXED`,它的 `BOTH` 正是这一档
- [traditional-or-simplified](https://github.com/nickdrewe/traditional-or-simplified)(npm)
- 权威数据源是 Unihan 的 `kSimplifiedVariant` / `kTraditionalVariant`

**定案:不引库,两边共用一张小判别字集。** 三条理由:

1. 引 Python 包 → `uv.lock` 变 → **镜像重建**。TODO-40 记着 30GB 的 VPS 装不下一次
   后端全量重建,失败还会把镜像记录 GC 掉。为判别功能付这个代价不值。
2. **判别不需要完整转换表。** 工地对话的高频判别字就那些:们/們、这/這、个/個、
   问/問、时/時、开/開、点/點、现/現、报/報、后/後、边/邊、无/無、电/電、动/動、
   护/護、检/檢、单/單、员/員、场/場、图/圖…… 一张 200 字的对照表够用。
3. 前后端各一份 → 照 `ROUNDTRIP_VECTORS` ↔ `checkin-lib.test.ts` 那个**已有的
   同源模式**,两边注释互指,后端改判据前端测试先红。

**诚实标出的风险:手工字集一定会漏。** 但漏了的表现是「落回上一条 / 落回默认」,
不是乱码 —— **这是个安全的失败方向**。

## 3. 架构定案

### 3.1 语言从哪来 —— 两层,两层都要

```
显式 UI 选择(经 context_schema)        ← 用户按过切换器就以它为准
        │ 用户从没碰过切换器
        ▼
往回扫本线程的 HumanMessage              ← 「第二句只打好」靠它
        │ 全线程判不出来(纯图片开局等)
        ▼
GYT_DEFAULT_LANG(config.py 常量)
```

**为什么两层都要**(这条是对抗复审推翻第一版方案得到的,见 §8.2):

只有第二层的话,这个场景会错 ——

```
用户全程简体聊了十轮
    ↓ 点了界面上的 English 切换器        ← 显式意图
    ↓ 打字:「ok」
    ↓ 往回扫 → 找到十轮简体 → 用简体答    ← 把用户的显式选择覆盖掉
```

**用户按了按钮而系统当没看见,比语言判错更糟。**

### 3.2 管道成本 —— 一行,不是七处

`create_agent(` 全仓只有**一个**调用点:

```
grep create_agent( backend/src/gyt/  →  core/base_agent.py:210
```

`create_gyt_agent` 是唯一工厂,八个 Agent 全过它。加 `context_schema=` 是
**一个文件一行**,不是「七个 Agent 的构造全改」。

### 3.3 中间件挂哪层

`create_gyt_agent` 里是 `middleware=[FocusOnOwnWork(name), *extra_middleware]`,
列表**前面的包在外面**。

**语言中间件必须在 Focus 里面** —— 它要判的是「用户说了什么」,而未裁的 messages
里混着 supervisor 的派活腔(那是**另一个模型**生成的文本,语言不受用户控制),
拿它去判就是判错。

```
create_agent 的中间件洋葱(外 → 内)

  FocusOnOwnWork(name)          裁掉 supervisor 纯文本
    └── SpeakUserLanguage       ← 新增,判定用裁后的 messages
          └── RequireLedgerTool / RequireReceiptSource
                └── 真正的 model call
```

放 `extra_middleware` 的**第一位**:这样守卫重试时语言指令已经在 `system_message`
上了,重试路径透明。

### 3.4 supervisor 那层走另一条路

`create_supervisor(prompt: Prompt | None)` 的 `Prompt` 实测:

```python
Prompt = SystemMessage | str | Callable[[StateSchema], ...] | Runnable
```

**接受 callable**,所以 supervisor 直接传函数,不用中间件。

### 3.5 401 / 429 拒绝句永久不国际化

`backend/auth.py:115`:

```python
DENY_MESSAGE: Final[str] = "访问被拒绝,请联系发你链接的人。"
"""三种失败(没带头 / 带了空串 / 令牌不对)回的是**一模一样**的一句话,
这是故意的:任何差异都是送给爆破脚本的信号。"""
```

两个理由,第二个更硬:

1. **401 发生在鉴权之前** —— 没有会话、没有用户、没有偏好,服务端**根本不知道**
   该用哪种语言。
2. 唯一可用的信号是 `Accept-Language`,而那是**攻击者完全可控的头**。一旦实现里
   出现任何分支(哪怕是「令牌有效 → 用用户语言;无效 → 用 Accept-Language」),
   就是一个**账号/令牌存在性预言机** —— 正是这条注释花力气防的东西。

**定案:`DENY_MESSAGE` / `RATE_LIMITED_MESSAGE` / `errors.py` 的 `UNAUTHORIZED`
三处保持中文、保持一字不差,并加注释说明「本条刻意不国际化,理由见 auth.py 头注」。**

| 甲(原文简体 + 覆盖指令) | 14 | 2 | 4 | **70%** |

| 乙(抽掉语言行 + 覆盖指令) | 15 | 1 | 4 | **75%** |

**三个都没过 80% 门槛。** 而 §9.1 的 #4 预期是甲′ —— **它是最差的那个。**

### 4.5.2 失败分布 —— 这才是值钱的部分

```
schedule    8 题 × 3 = 24 次   →  19 次不合规   (79% 失败)
safety      6 题 × 3 = 18 次   →   1 次不合规
knowledge   6 题 × 3 = 18 次   →   0 次不合规
```

失败的形状高度一致:

```
「好的,我这就记上。请稍等,我调一下工具。」
「我先查一下台账里带「钢筋复检」的任务。」      ← 用户打的是「鋼筋複檢」
「记上了:T1 补齐安全带,期限是下周一之前。」
```

**模型一进入「我要调工具」的模式,就整个切回简体。**
knowledge 是纯问答 → 0 失败;safety 偶尔要调 → 1 失败;
schedule 每句都要查台账 → 79% 失败。这条线非常干净。

### 4.5.3 第二轮:验根因 —— 假设被证伪

猜测是 schedule 提示词里那三个**简体措辞示例**(「记上了」「销了」「还剩两条没干」)
被模型照抄。加跑两档验证(schedule 8 题 × 4 = 32 次):

| 档 | 说明 | 合规率 |
|---|---|---:|
| 甲 | 原文简体 + 覆盖指令 | 50% |
| 乙 | 抽掉语言行 + 覆盖指令 | 50% |
| **丙** | 语言行 + **示例句**都改繁體 | **25%** |
| **丁** | 整个「说话方式」段全繁體 + 覆盖指令 | **25%** |

**丙、丁反而更差。示例句假设证伪。**

### 4.5.4 🔴 更要命的:两轮之间的噪声有 25 个百分点

```
                    第一轮    第二轮
甲(schedule 8 题)    25%   →   50%
乙(schedule 8 题)   37.5%  →   50%
```

**同样的提示词、同样的问题、`temperature=0`,两轮差 2 行(25pt)。**
DeepSeek 的温度 0 不是确定性的(MoE 路由 + 批处理导致)。

**所以 4.5.1 那三个数(70/55/75)的差异也在噪声里,分不出高下。**
这与 TODO-13 记的视觉端「±1 行固有噪声」是同一件事,这边更大。

### 4.5.5 钉死的结论

1. **五个档位(甲 / 甲′ / 乙 / 丙 / 丁)没有一个把 schedule 拉过 60%**,门槛是 80%。
   方案里写的判据「三个都 < 80% → 回来重想 L2 形状,别硬上」**压倒性地触发了**。
2. **靠提示词让模型换语言,在需要调工具的 Agent 上不成立。** 这是 CLAUDE.md
   高危陷阱那条(「提示词只是概率性生效,结构件才兜得住」)的**第四次**应验 ——
   而且这次是真金白银测出来的,不是引用规矩。
3. **结构件在哪:输出侧转换。** 模型输出简体,渲染前做 简→繁。
   它是**确定性的**,不是概率性的。

### 4.5.6 §2.4 那条定案要分家

§2.4 写着「繁简自动转换会静默出错,**定案:运行时不做转换**」。
**那条对 UI 词表成立,对模型输出不成立** —— 我原来把两者混为一谈了:

| | 集合 | 人工维护 | 不转换的后果 |
|---|---|---|---|
| **UI 文案** | 有限(166 条) | 可行,质量最高 | — |
| **模型输出** | 无限 | 不可能 | **100% 是简体** |

对模型输出,自动转换哪怕有 1% 的字形选错(干/幹/乾 那类),
也远好过「不转换 = 100% 错」。**这不是同一个权衡。**

香港场景要用 `s2hk`(简体 → 香港繁體)那档配置,不是 `s2t`。
放**前端渲染层**做:零后端依赖、零镜像重建。

### 4.5.7 第三轮:English 走的不是同一条路

**繁體和 English 的机制根本不同**,第一二轮只测了繁體:

```
繁體    模型输出简体 → 渲染前做 简→繁 字形转换      确定性结构件
English 简体 → 英文不是字形转换,是翻译
        只能靠提示词让模型直接用英文答             概率性
```

第三轮:同一批 20 题翻成英文,提示词 = 原文 + 英文覆盖指令。

### 4.5.8 第四轮:修好判分 —— 两个数都是 80%,但性质完全不同

第三轮的判分把**工具调用语法**也算进「回答」里了。而那里面的中文
(`search_regulation(query: "消防车道 最小 净宽")`)是**正确行为** ——
规范库本来就是中文的。剔掉工具语法块重判:

| | 合规率 | schedule | safety | knowledge |
|---|---:|---:|---:|---:|
| **繁體**(乙档) | **80%** | 50% | 100% | 100% |
| **English** | **80%** | **100%** | 83% | 50% |

**分布是反的,而且失败原因不是一回事:**

| | 失败在哪 | 性质 | 能修吗 |
|---|---|---|---|
| **繁體** | schedule 的散文(「我这就记上」「记上了:T1」) | **模型自发切回简体** | ❌ 五档试遍改不动 → 要输出侧转换 |
| **English** | knowledge 的引用格式(`—— 依据《…》第 X 页`) | **提示词自己写死的中文** | ✅ 改 `knowledge/prompt.md` 几行,预计上 90%+ |

**注意 schedule:繁體最难的那一档(50%),英文是 100%。**
中英是硬边界,模型跟得住;简繁是同一种语言,它会飘。

## 4.6 转换点的位置 —— 定死在最末端,挪一层就静默坏

第二轮评审的核心发现。前端有**三处靠中文串精确匹配**的逻辑,转换点早一层就全打断:

```

      徽章 ✗(它匹配的是转换后的文本)

      徽章 ✓(组件层已按简体匹配完)
      编号 ✓(human.tsx 已抽取完)
      姓名 ✗  ← 走 §9.0 #5 的定案(接受)
```

三处受害,逐字核过:

| 位置 | 匹配什么 | 转换后 |
|---|---|---|
| `markdown-text.tsx:95` `STATUS_CHIPS`(注释:**只认整格精确匹配**) | 已逾期 / 未完成 / 已完成 / **没定期限** | 「没定期限」→「沒定期限」**失配** |

**后果全是零报错**:徽章不上色、照片退回一段裸 hex。

🔴 **这张图必须画进 `markdown-text.tsx` 的头注。** 不画的话下一个人一定会图省事挪到
(a) 或 (b),而挪了之后**纯函数测试全绿、界面静默变哑**(见 §6.2)。

### 5.1 T4 实测:不裁子集,改成 lazy load(2026-08-17)

`opencc-js@1.4.1` 实测:

| 模块 | 原始 | gzip |
|---|---:|---:|

### 5.3 界面繁體化(第一批之二,2026-08-18)

负责人定案:**「读繁體,契合中建国际的现实使用场景」**。中建国际在港施工,
现场语言是繁體 —— 这个依据比「默认值该设成什么」硬得多。

于是**两条规则,互不影响**:

| | 规则 | 靠什么实现 |
|---|---|---|
| 答话 | **跟着用户打的字走**(简体问→简体答) | `resolveLang` + `useHantText`,§5.2 已实测 |
| 界面 | **恒繁體**,与用户打什么无关 | 本节 |

界面那条没有 `lang` 参数 —— 它不是「默认繁體」,是「就是繁體」。

#### 为什么界面不能走运行时转换

最省事的写法是给界面套一个 `useHantUI` 一转了之。**否掉了**:那样首屏就要拉
438 KB 字典,而 §5.2 刚刚实测确认的「简体用户一个字节都不下」当场作废 ——
一个从不开面板、只用简体问答的工友,会为了他根本看不到的繁體按钮付 438 KB。

所以分两层:

```
静态文案(按钮/占位符/提示句/toast)  ──▶ **源码里就写成繁體**,零运行时、零字节
后端给的显示文本 + 留简体的「值」      ──▶ 面板里过 useHantUI(字典跟着面板走)
```

#### 🔴 落地时挖出的一条,把设计改了

原计划是「值/标签双表」:`HAZARD_SCOPES` 留简体送后端,另起一张繁體标签表上屏。
写到一半发现这个方案**根本不生效**:

```tsx
supervision.tsx:1292   {hazard.status_display || hazardStatusZh(hazard.status)}
                        ^^^^^^^^^^^^^^^^^^^^ 后端算好的简体,前端那张表只是兜底
```

屏幕上真正显示的那份**是后端来的**(`status_display` / `doc_type_display` /
`result_display` / `due_display` / `user_msg`)。拆多少张前端表都没用。

改成:**值一律留简体并登记,转换统一插在渲染处**。一处解决三个双重身份常量
(`HAZARD_SCOPE_*` / `GRADE_*` / `HAZARD_STATUS_ZH`),而且顺带把后端文本也覆盖了。

#### 四道关卡,以及每一道**抓不住**什么

一次动几百个串,而转错了基本都是静默的。所以先有判据再动手:

| 关卡 | 抓什么 | **抓不住什么** |
|---|---|---|
| `hant-scan.mjs` | 走 TS 的 AST 找中文串 | (不是关卡,是地基) |
| `hant-ui-strings.test.ts` ① | 「**还是简体**」 | 转成了**错的繁體**(`s2hk("籤發")` 原样返回) |
| `hant-verify-diff.mjs` | 「新值 ≠ s2hk(旧值)」= 手打的 | 新写的文案(没有旧值可比) |
| `hant-ui-strings.test.ts` ② | 参与匹配/传参的位置上有没登记的中文 | 中文串在别处被间接用作键 |

**为什么用 AST 不用正则**:本仓注释密度极高且全是中文,正则分不清注释和文案。
分不清就只有两条路 —— 要么守卫永远红最后被删,要么粗暴剥注释、剥漏一种写法就静默漏扫。
AST 里压根没有注释节点,这个问题结构上消失。

**为什么不能靠黑名单挡手打**:「復」本身是合法繁體字,「工程復工令」就该写「復」。
唯一可靠的判据是**溯源**:新值必须恰好等于 `s2hk(旧值)`。

#### 关卡②当场抓到的 6 条 —— 前三道全看不见

```
ProjectUploadPanel.tsx   平面 / 立面 / 剖面 / 剖    匹配用户上传的文件名,判图纸类型
human.tsx                照片(LiteralType)          匹配后端拼的 (照片编号:<32位hex>)
```

它们**简繁同形**,所以「还是简体」那条守卫永远不会报;转换也不会动它们,
溯源器同样沉默。而它们是判据不是标签 —— 哪天有人把「剖」当笔误删掉、
或者把这几个词换成别的说法,图纸类型判定会**静默全落空档**。

这 6 条是这套关卡最值钱的产出:它证明了「简体守卫 + 溯源」这两道**不够**,
必须有一道按**语法位置**判的。

#### 已登记必须留简体的(截至落地时)

|---|---|---|

往测试包里加了三个 `.mjs` 工具,`vitest` 全绿而 `tsc --noEmit` 当场十几条红

靠人记的结果就是这次漏了。静默降级的表现是:测试里写错字段名也不报,
覆盖看着在、其实是 `any` 在放行。补一行,让它变成响的。

#### 🔴 界面繁體挖出的功能缺陷:后端一个繁體日期都不认

这条不是界面问题,是**繁體上线后必然会撞的功能缺陷**,真机实测出来的:

```
parse_due(today=2026-08-18)
  下周三 → 2026-08-26 ✅        下週三 → 🔴 DueParseError
  周三 / 礼拜三 / 后天 / 3天后 ✅   週三 / 禮拜三 / 後天 / 3天後 → 🔴 全拒
```

而那句报错是「可以这样说:明天 / 后天 / 3天后 / 周三 / 下周三 / …」——
**在教港方监理改用简体写法**。

修法:`_strip_noise()` 第一行做一次繁→简折叠。挂在那儿而不是 `parse_due`,
因为那是所有解析入口的唯一必经之路。**只折输入** —— `format_display` 产出的
「8月14日(周五)」仍是简体,屏幕上的繁體由前端渲染层转(就是本节的分层)。

不引 opencc:动 `uv.lock` = 重建镜像,而 TODO-40 记着线上 30GB 的盘装不下
一次后端全量重建。手写封闭小字表,与 `lang-lib.ts`「为什么不引库」同一取舍。

**两张折叠表内容不一样**(dates 8 字、ranges 6 字),这是那两个模块
「刻意不共用词表」的第二处落点 —— 合并 = 往考勤塞两个它永远用不上的字。

⚠️ **仍然不认「下星期三」「下禮拜三」** —— 那是**词表缺口不是简繁缺口**
(简体的「下星期三」一样被拒:`_NEXT_WEEKS_RE` 只收「周」)。
港方说「下禮拜三」的概率明显高于内地工友说「下星期三」,大概率会在真机撞到。
扩不扩词表是产品决定,本批未动。

#### 🔴 §5.4 之后真人试用又抓到一条:后端拼的编号块在污染语种判别

| 用户打的 | 只看用户原话 | 拼上编号块 |
|---|---|---|
| 呢張係咩 | zh-Hant | **zh-Hans** 🔴 |

也就是说:**港方工友传一张图纸、配一句短繁體,答话会变成简体**,而且零报错。

「照片编号」碰巧是 0 票(编/号 不在字对表里),所以传**照片**看不出问题 ——

(`uploads.py` 产生 → `human.tsx` 渲染 → `lang-lib.ts` 摘除),已登记进 CLAUDE.md,
`lang-lib.test.ts` 有一条断言拿 `human.tsx` 的形参词拼出标记来验摘得掉。

⚠️ 这条也说明**六条真机验收还不够**:它们验的是「界面 / 答话 / 值 / 字典」四条轴,
而这个 bug 长在**两条轴的交点**上(传文件 × 打繁體)。真人试用抓得到,
是因为人不会按轴来用。

### 6.2.2 🔴 上面那个判断错了一半 —— jsdom 当天就补上了(2026-08-18)

第一版落地当天真机就崩了:

```
点开任一条有消息的线程 → Application error: a client-side exception has occurred

TypeError: Cannot read properties of null (reading 'length')
    at n.convert (opencc-js/cn2t.js)
    at basicStateReducer (react-dom)        ← 病根
    at useHantText (hant-convert.tsx)
```

病因是 `setConverter(conv)` 里 `conv` 是函数,**React 把它当 updater**
(`setState(prev => next)`)去调 `conv(null)`。

🔴 **当时 334 条测试全绿。** 因为没有任何测试**执行**过那个 hook ——
`lang-lib.test.ts` 不碰它,`conversion-seam.test.ts` 读源码不执行。

**§6.2.1 那个判断的前半段成立**(有两条不变量只有源码级看得见),
**漏的是后半段:渲染测试能查到的东西里,有一个真 bug 在等着。**

#### 依赖面比 §6.2.1 估的小得多

原估「react + react-dom + **react-markdown** + testing-library + jsdom
+ 三个路径别名 stub」。实测只要四个:

```
jsdom  react  react-dom  @testing-library/react     (全 dev-only)
```

因为 **只渲染那个 hook,不渲染 markdown-text.tsx** ——
`hant-convert.tsx` 只 import `react` 和 `@/lib/lang-lib`,碰不到那棵重依赖树。
而它虽然是 `.tsx` 后缀却**没有 JSX**,所以连 JSX 转换都不用配
(测试用 `createElement` 写)。

jsdom 只对 `hant-convert.render.test.ts` 生效(文件头 `@vitest-environment jsdom`),
其余测试仍是 `node` 环境。

⚠️ **默认环境不许改成 jsdom** —— 那会让「库代码不许有 window 假设」这条前提失效:
误用 `window` 的代码在测试里会悄悄跑通,换到 SSR / Node 才炸。

#### 顺带撞出一件下一个人一定会撞的事

`hant-convert.tsx` 是**第一个带真依赖的被测覆盖件**。而覆盖件躺在
`scripts/frontend-overrides/`,那个目录**没有 `node_modules`** ——
TS 和 Vite 都从文件所在目录往上找依赖,于是**两边都要给它指路**:

| 在哪 | 要加什么 |
|---|---|
| `vitest.config.ts` | `resolve.alias` 里 `react` / `react-dom` / `opencc-js/cn2t` 指到本包的那份 |
| `tsconfig.json` | `paths` 同上,**且 `@types/react` 要排在 `react` 前面** |

`@types` 排后面的症状很误导:报 TS7016 隐式 any,而文案建议你
「给 DefinitelyTyped 发 PR」—— 完全指向错误的方向。

#### 变异验证,以及一条「别把功劳记错人」

把 `setConverter(conv)` 写回去:**红 1 条**,报的就是生产上那个
`null.length`。但红的是**「字典拉到之后答话真的变成繁體」**那条,
**不是**「首帧渲染不抛」那条 —— 那个 TypeError 在**异步 setState** 里抛,
`expect(...).not.toThrow()` 压根碰不到它。

**所以真正的回归守卫是「等到转换结果」那条。** 两条都留着,
但测试里已经写明谁在守门 —— 记错了,下次有人删掉「等结果」那条
会以为回归还有人守。

**现状:9 条运行时断言 + 10 条源码级断言,两层都在。**

变异验证(2026-08-18 实跑):

## 8. 复审推翻自己的三条

> 本仓的传统:`docs/W5_…方案.md` 第 10 节记着「两条方案决策被实测推翻」。
> 这一节同理 —— 记的是第一版方案里**错的**地方,以及怎么发现的。

### 8.1 「先做 L2,风险最小」—— 没有依据

第一版把 L2 列成「1.5 天,风险最小,先做」。

**而 L2 整个建立在一行提示词上,这正是 CLAUDE.md 点名的那类做法。**
主流中文模型训练语料以简体为主,繁體输出会中途漂回简体,尤其是专业名词。
而这一层**没有结构件兜得住** —— 简→繁自动转换有一简对多繁的问题(§2.4 自己写的),
所以没法在输出侧纠正。

不对称:**English 大概率没问题**(模型对「answer in English」很听话),
**繁體是风险项且无回退**。

→ 加了第 0 步探针。

### 8.2 「砍掉整条管道」—— 成本估错一个数量级,而且会毁掉显式切换

第一版的 P1 建议是「砍掉 `gyt_lang` 管道,只往回扫线程」,依据是
「要读到得给每个 Agent 声明 `context_schema`,那是七个 Agent 的构造全改」。

**实测:`create_agent(` 全仓只有 `base_agent.py:210` 一处。加 `context_schema=`
是一个文件一行。** 成本估高了一个数量级。

更糟的是,砍掉管道之后「用户点了 English 切换器却被扫描拉回简体」(§3.1 那个场景)。
**第一版的两个目标自相矛盾,而我没发现。**

→ 改成两层,显式优先。

### 8.3 「追加 HumanMessage 会让 `test_require_tool.py` 红」—— 空头支票

第一版的变异表里写着这条。**实测下来它不会红** —— 那些测试直接构造 message list
测函数,不叠中间件栈;唯一跑真栈的 `test_report.py` 只走正常路径。

这正是 learnings 里 `red-line-satisfiable-without-being-honored` 那条的形状:
**「有守卫」不等于「守卫被这个改动触发」。**

→ §6.2 第一行标成必须新写的集成测试。
