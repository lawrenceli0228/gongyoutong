1 / Runbook

修正后的部署流程

每一步都标了它防的是哪个坑。 按顺序做,别跳。

1.0 前置:备份 + 摸底(只读,不改任何东西)

# 数据是唯一不可再生的东西(实测只有 181MB,备份很便宜)
mkdir -p ~/gyt-backups
rsync -az -e ssh animego-old:/opt/gyt/data/ ~/gyt-backups/data-$(date +%Y%m%d-%H%M%S)/

# 摸底:磁盘、镜像、容器
ssh animego-old 'df -h /; docker system df; docker images; docker ps'

⚠️ 注意 Build Cache 那一行。 它是 0B 就意味着下一次构建是全量的 (含 2.2GB 权重重下),峰值需求会高出一个量级 —— §3 的账全看这个数。

1.1 腾空间(§3 会给出这一步能不能省)

ssh animego-old 'journalctl --vacuum-size=50M; apt-get clean'

/opt/animego-mongo-final-*.tar.gz(214MB)可以挪到开发机再删 —— 先 scp 下来、比对 sha256 再删源。实测这一轮共回收 597MB(11G → 12G)。

1.2 同步代码 —— ⚠️ 别用旧文档里那条命令

# 演练:先看清楚要删什么(必做)
rsync -azn --delete -i --no-o --no-g --filter=':- .gitignore' \
  --exclude '.git' --exclude 'backups/' \
  ./ animego-old:/opt/gyt/

# 确认无误再真跑
rsync -az --delete --no-o --no-g --filter=':- .gitignore' \
  --exclude '.git' --exclude 'backups/' \
  ./ animego-old:/opt/gyt/

四个开关缺一不可,理由分别见 §2.2(--filter)、§2.3(--no-o --no-g)、 §2.2(--exclude '.git')、下面这一段(--exclude 'backups/')。

🔴 --exclude 'backups/' 是 2026-08-21 部署时演练档当场抓到的,别删

那次加了备份服务(docker-compose.vps.yml 的 backup),它往宿主 backups/ 写;.gitignore 里也加了 /backups/。 按「让 rsync 直接读 .gitignore」这条单一真相的设计,它应该被保护住 —— §2.2 ④ 那条也写着「--delete 默认不删被排除的文件」。

但演练档第一行就是 *deleting backups/。 实测结论:经 --filter=':- .gitignore' 合并进来的规则,在这个组合下 没能把接收端那个目录保护住,只有显式 --exclude 才行。

危害等级和 §2.2 那次一样、甚至更高:一旦备份服务跑起来,那个目录里装的是 这台机器唯一的备份,而删它的正是那条用来部署的命令。

⚠️ 教训不是「多加一个 exclude」,是演练档必须真的看:这条命令的三个已知坑 (对话历史、属主、.git)全是演练档抓出来的,这是第四个。 数一下 deleting 的行数比逐行读更省事:

rsync -azn --delete -i --no-o --no-g --filter=':- .gitignore' \
  --exclude '.git' --exclude 'backups/' ./ animego-old:/opt/gyt/ | grep -c deleting
# 期望 0。非 0 就逐行看清楚每一条,别 rsync 完再后悔。

1.3 构建后端 —— 在 VPS 上构,不要在开发机构了传

ssh animego-old 'cd /opt/gyt && DOCKER_BUILDKIT=1 \
  docker compose -f docker-compose.yml -f docker-compose.vps.yml build backend'

⚠️ 构建期间另开一个窗口盯磁盘(实测 6 分钟内从 13G 掉到 1.6G):

ssh animego-old 'while true; do df -h / | tail -1 | awk "{print \$4}"; sleep 30; done'

⚠️ 构完立刻回收缓存,别等:

ssh animego-old 'docker builder prune -af'   # 实测回收 7.89GB

1.4 起后端 —— ⚠️ 不带 --build

ssh animego-old 'cd /opt/gyt && \
  docker compose -f docker-compose.yml -f docker-compose.vps.yml up -d --no-build backend'

带 --build 会把刚构好的镜像再构一遍,理由见 §2.4。

1.5 前端:先重新生成 frontend/,再构

frontend/ 不进 git、也被 rsync 排除,VPS 上那份是旧的(§2.6):

ssh animego-old 'cd /opt/gyt && COREPACK_ENABLE_DOWNLOAD_PROMPT=0 bash scripts/setup-frontend.sh'

⚠️ VPS 上没有 pnpm,脚本装 qrcode.react 那一步会 die。用容器补(§2.7):

ssh animego-old 'cd /opt/gyt/frontend && docker run --rm -v "$PWD":/app -w /app \
  -e COREPACK_ENABLE_DOWNLOAD_PROMPT=0 node:22-slim \
  sh -c "corepack enable && pnpm add --save-exact qrcode.react@4.2.0"'

然后构建 + 起:

ssh animego-old 'cd /opt/gyt && DOCKER_BUILDKIT=1 \
  docker compose -f docker-compose.yml -f docker-compose.vps.yml build frontend'
ssh animego-old 'cd /opt/gyt && \
  docker compose -f docker-compose.yml -f docker-compose.vps.yml up -d --no-build'

1.6 Caddyfile 改了就必须 重建 caddy 容器,不是 reload

ssh animego-old 'cd /opt/gyt && \
  docker compose -f docker-compose.yml -f docker-compose.vps.yml up -d --no-build --force-recreate caddy'

caddy reload 在这套部署里用不了(admin API 没开), 而绑定挂载的 inode 问题让容器看不到新文件 —— 见 §2.8。

核对路由顺序(这是唯一可靠的判据,caddy validate 说 Valid 不算数):

ssh animego-old 'docker exec gyt-caddy caddy adapt --config /etc/caddy/Caddyfile' \
  | python3 -c "import json,sys;..."   # 完整脚本见 §2.8

/api/checkin* 必须排在 /api/* 之前。

1.7 验证

见 §0 那张表,或跑 scripts/postdeploy_checks.sh。

⚠️ 必须带登录会话去验,否则闸① 是假绿灯 —— 见 §2.11。

2 / Pitfalls

十二个坑

每个坑:现象 / 根因 / 判据 / 修法。标 🔴 的是会造成数据损失、站点故障或「假绿灯」的那几条。

2.1 🔴 在开发机构建再传镜像 —— 被上行带宽否决(白花约 1 小时)

当时的想法:30GB 盘装不下构建缓存(历史实测 9.34GB)+ 新镜像(6.4GB), 那就把构建搬到开发机,VPS 只负责装镜像 —— 镜像只要 6.4GB,11GB 够。

实测数据把这个方向直接否了:

实测
开发机上行0.27 MB/s(50MB 用 181 秒)
VPS 下行20 MB/s(200MB 用 10 秒)
传 6.38GB 镜像(gzip 后约 5GB)约 5.3 小时
VPS 自己下 4.4GB 权重约 3 分钟
教训:「把重活搬到本机」这个直觉,在「家庭宽带 → 机房」这个方向上是反的

家用上行通常只有下行的十分之一,而机房两个方向都快。 要搬之前先量两个方向的带宽,两条命令的事。

# 开发机上行
dd if=/dev/zero bs=1m count=50 | ssh animego-old 'cat > /dev/null'
# VPS 下行
ssh animego-old 'curl -sL -o /dev/null -r 0-209715200 <某个大文件 URL>'

中止是安全的:docker save | ssh | docker load 被 kill 之后,VPS 上 docker images 里没有任何新镜像、tag 没动 —— docker load 要么成功要么不打标签,不会留下 §2.9 那种半截状态。

2.2 🔴 文档里那条 rsync 会删掉生产的对话历史

旧命令(W6_VPS_队友接入.md 记的):

rsync -az --delete --exclude '.venv' --exclude '__pycache__' --exclude 'node_modules' \
  --exclude '.next' --exclude 'frontend/' --exclude 'data/artifacts' --exclude 'data/uploads' \
  --exclude 'data/gyt.sqlite3' --exclude '.env' --exclude '.env.vps' ./ gyt:/opt/gyt/
演练(-n)实测:会删掉生产 306 个文件
  • data/langgraph/ 整个目录 —— 那是全部对话历史(线上 88MB)。 而 commit 08f606d(「容器一重建,所有历史对话清零」)修的正是这个, 这条命令会把那次修复的成果抹掉;
  • data/cache/ 约 290 个 LLM 磁盘缓存文件(删了下次提问全部真花钱);
  • data/chroma(向量库)、data/demo、data/cad_index 同样不在清单里。

根因:线上 data/ 下有 8 样,而那份 exclude 清单只排了 3 样。 这是「维护一份平行清单」必然的漂移 —— 补四行不解决问题,下次加第九样还会漏。

修法:让 rsync 直接读 .gitignore,单一真相:

rsync -az --delete --no-o --no-g --filter=':- .gitignore' --exclude '.git' ./ animego-old:/opt/gyt/

实测效果:

旧命令新命令
传输922MB / 11388 文件2.8MB / 84 文件
删除306 个(含对话历史)3–8 个(全是 VPS 侧的构建日志)
data/ 与 .env会动零涉及

两道保护:① .gitignore 里有 /data/*、.env.*,filter 会排除它们; ② rsync 的 --delete 默认不删被排除的文件。

--exclude '.git' 单列是因为 .gitignore 不会忽略 .git 自己 —— 不排的话会连带删掉 VPS 上那份 .git(见 §2.10),也会白传几十 MB。

顺带:922MB 里有 870MB 是仓库根那个 gitignore 掉的 YOLO 训练素材 (construction-safety-monitor.v1i.yolov8*),旧清单同样没排。

2.3 🔴 rsync -a 会把 data/ 的属主改掉,容器从此写不进库

-a 含 -o(属主)与 -g(属组)。线上 /opt/gyt/data 是 10001:996(容器里的 gyt 用户),而开发机是 501:staff, rsync 在对端以 root 跑 —— data/ 会被 chown 成 501。

后果不是立刻报错

容器照样 healthy、页面照样打得开,但 uid 10001 没法在 data/ 下新建条目 —— SQLite 的 -wal / -journal 首当其冲。 这是 W6_VPS部署与访问口令.md:509-529 记过的老坑。

修法:加 --no-o --no-g。验证靠 itemize 输出那一列标志位:

.d..t.og. data/     ← 危险:o(属主)g(属组)都要改
.d..t.... data/     ← 加了 --no-o --no-g 之后,只剩 mtime

同步后顺手核一次:ssh animego-old 'stat -c "%u:%g" /opt/gyt/data' 必须仍是 10001:996。

2.4 🔴 up -d --build 把已经构好的镜像又构一遍,直接撞盘

后端镜像在 §1.3 已经构好了(BUILD_EXIT=0),然后我跑了 docker compose ... up -d --build 想一次把前后端都起来 ——

--build 是无条件重构,不看镜像在不在。 而我刚 builder prune -af 清空了缓存,于是全量重来,在下载权重那步撞 No space left on device。

修法:镜像已就绪时用 --no-build。要构就单独 build <service>, 构完再 up -d --no-build。

站点全程没受影响 —— 旧容器还跑着,失败的只是构建。

2.5 🔴 setup-frontend.sh 里 install_new_file 排在会 die 的步骤之后

现象:前端构建报 Module not found: Can't resolve './GytStatusCards'。

根因:两条分支合流时,我把队友那两个组件的 install_new_file 放在了 「装 qrcode.react」之后,而那一步在没有 pnpm 的机器上 die —— 整个脚本终止, 后面的拷贝一行都不执行。VPS 恰好没装 pnpm(§2.7)。

这个错的隐蔽处

报错指向「组件缺失」,而真因是「脚本提前退出」,中间隔着好几层。 脚本的输出里甚至能看到前三件装成功了 —— 更像是覆盖件坏了。

修法:所有 install_new_file / apply_override 必须排在任何可能 die 的步骤之前。 已在脚本里那一步前面加了警告注释。 判据很简单:拷文件不依赖任何外部工具,就该排在最前。

2.6 frontend/ 不进 git 也不进 rsync,VPS 上那份是旧的

frontend/ 在 .gitignore 里,所以 rsync 的 filter 会排除它 —— 代码同步不会更新前端。实测 VPS 上那份停在 8-11,打卡三件全缺。

修法:同步完代码后,在 VPS 上重跑 scripts/setup-frontend.sh 再构镜像。

这不是缺陷,是 frontend/ 由脚本生成这个设计的必然结果 —— 但很容易忘, 忘了的表现是「后端更新了、前端没有」,而两者都不报错。

2.7 VPS 上没有 pnpm

VPS 平时不装前端依赖(构建在 Docker 里做),所以宿主没有 node/pnpm。 而 setup-frontend.sh 装 qrcode.react 需要它。

修法:用一次性容器补(不给 VPS 装任何东西):

cd /opt/gyt/frontend && docker run --rm -v "$PWD":/app -w /app \
  -e COREPACK_ENABLE_DOWNLOAD_PROMPT=0 node:22-slim \
  sh -c 'corepack enable && pnpm add --save-exact qrcode.react@4.2.0'

⚠️ 必须写进 package.json 和 pnpm-lock.yaml 两处 —— 前端 Dockerfile 用的是 pnpm install --frozen-lockfile, lockfile 没更新会直接失败。

2.8 🔴 Caddyfile 改了,reload 用不了、容器也看不见新文件

两个问题叠在一起
  1. docker exec gyt-caddy caddy reload 报 dial tcp [::1]:2019: connect: connection refused —— admin API 没开 (这是刻意的,admin 端点能改整个配置)。所以 reload 这条路在这套部署里不存在。
  2. 更隐蔽的:Caddyfile 是绑定挂载 (/opt/gyt/Caddyfile → /etc/caddy/Caddyfile),而 rsync 是 新建文件再 rename 替换 —— 容器里那个挂载点仍指向旧 inode。 实测:宿主那份有 3 处 api/checkin,容器里 grep -c 是 0。

修法:--force-recreate caddy。

判据:caddy validate 说 Valid configuration 不算数 —— 这个文件自己的注释就记着「裸奔那次 validate 也说 Valid」。唯一可靠的是打路由树:

docker exec gyt-caddy caddy adapt --config /etc/caddy/Caddyfile 2>/dev/null | python3 -c "
import json,sys
cfg=json.load(sys.stdin)
def walk(rs,d=0):
    for r in rs:
        p=[x for m in (r.get('match') or []) for x in m.get('path',[])]
        if p: print('  '*d+str(p))
        for x in (r.get('handle') or []):
            if 'routes' in x: walk(x['routes'],d+1)
for s in cfg['apps']['http']['servers'].values(): walk(s.get('routes',[]))
"

正确输出(/api/checkin* 必须在 /api/* 之前):

['/login*']
['/logout*']
['/api/checkin', '/api/checkin/*']
['/api/*']
['/artifacts/*']

2.9 🔴 TODO-33 那个陷阱当场复现了一次

前端构建在最后一步失败:

#17 naming to docker.io/library/gyt-frontend:vps done      ← tag 已经打上去了
#17 unpacking to docker.io/library/gyt-frontend:vps
#17 ERROR: failed to extract layer …: no space left on device

docker images 里 gyt-frontend:vps 指向一个 591MB 的半截镜像 (正常的是 1.93GB)。机器一重启,compose 就会拿它起前端。

铁律(TODO-33 记过,这次证明它是对的): 构建失败之后,第一件事是 docker images 看 tag 指到哪儿了,不是看日志找原因。

修法:docker rmi 掉那个半截镜像,腾够空间再重构。

2.10 /opt/gyt 里其实有 .git,但连不上 GitHub

文档写「是 rsync 上去的工作副本,不是 git clone」—— 意思对,字面不准。 实测那儿有一份真的 .git(32MB,rsync 顺带拷上去的旧快照, HEAD 停在 a304109),git status 会报 dubious ownership, git fetch 报 Host key verification failed (服务器上没有 GitHub 凭据,这是刻意的)。

结论不变:别在服务器上 git pull,那儿 pull 不了。 但知道那儿有个 .git 有两个用处:① rsync 要 --exclude '.git',否则会删它; ② 有人可能会被 git log 显示的旧 commit 误导。

2.11 🔴 验证鉴权时,不带登录会话等于没验

站点每条 /api/* 都先过 Caddy 的 forward_auth。 没有会话时它自己就回 401 —— 于是「不带令牌 → 401 → 通过」这个判断在没会话时是 必然的假绿灯。

🔴 打卡端点完全裸奔也会绿

实测两种 401 长得不一样,这是唯一的分辨方法:

{"detail":"登录已过期,请刷新页面重新登录。"}   ← Caddy 门禁拦的,这条不构成验证
{"detail":"访问被拒绝,请联系发你链接的人。"}   ← 打卡端点的鉴权拦的,这才算数

正确的验法:先登录拿会话,再带着会话、不带令牌打过去,必须仍是「访问被拒绝」。

PW=$(cat /root/.gyt-basic-auth-plaintext)
curl -sk -c /tmp/cj.txt -X POST "$ORIGIN/login" --data-urlencode "pw=$PW"   # 字段名是 pw
curl -sk -b /tmp/cj.txt -X POST "$ORIGIN/api/checkin" …                     # 期望「访问被拒绝」

⚠️ 登录表单字段名是 pw,不是 password (serve_login.py:429 有断言守着)。

2.12 🔴 set -a; . ./.env 会毁掉登录口令哈希

现象:gyt-login 容器无限重启,日志刷 [错误] GYT_LOGIN_HASH 格式不对,应形如 scrypt$16384$8$1$<salt>$<hash>。

根因:bash 把 $$ 展开成了自己的进程 PID

.env 里存的是 scrypt$$16384$$8$$1$$… —— 双 $ 是给 docker compose 转义用的(compose 把 $$ 解析成一个字面 $)。 而我在命令里 set -a; . ./.env; set +a,bash 把 $$ 展开成 PID, 导出成 scrypt7587701…;compose 又优先使用环境变量而不是 .env 文件, 于是容器收到了这个坏值。

修法:别 source .env。 compose 自己会读它,并正确处理 $$。 所有 build args(GYT_PUBLIC_ORIGIN、GYT_ACCESS_TOKEN 等)compose 都会自动从 .env 拿,根本不需要先 source。

这个坑的普遍形态:任何在 .env 里为 compose 转义过的值(含 $$ 的), 都不能用 shell 的 source 读。要在 shell 里用,得自己反转义。

3 / Disk

30GB 磁盘怎么走完全程

历史记录说峰值几乎贴着 30GB,而这次的起点是已经占了 20GB。这一节是那笔账。

历史记录(W6_VPS部署与访问口令.md:283)说:一块 30GB 的盘走完整流程, 最终占用约 20GB,中途靠 docker builder prune -af 回收了 9.34GB。 也就是说峰值几乎贴着 30GB。而这次的起点是已经占了 20GB。

实测的磁盘曲线(全程 30G 盘)

起点                                          11.0G 可用
├ 清理(journal + apt + 挪走 214MB 冷备)  →   12.0G   实测回收 597MB
├ 删前端镜像(反正要重建)                 →   13.0G
├ 后端全量构建(6 分钟)                   →    1.6G   ← 最紧的一刻
├ builder prune -af                        →    7.1G   实测回收 7.89GB
├ 删旧后端镜像(新的已验证 healthy)       →   12.0G   释放 6.28GB
├ 前端构建(8 分钟)                       →    5.6G
├ builder prune -af                        →    8.9G
└ 终点                                     →    9.0G   已用 22G/30G

结论:30GB 走得完,但有三条硬要求

  1. 构建缓存必须构完就清,不能攒着。两次 prune 分别回收了 7.89GB 与 5.21GB;
  2. 前后端必须分开构,中间插一次 prune。一起构(up -d --build)必撞盘;
  3. 旧后端镜像要在新的验证通过后尽快删。它占 6.28GB,是最大的一块可回收空间。 删之前先确认新容器 healthy 且端点探针通过 —— 删了就没有本机回滚绳了 (但代码在 git 里,重建即可,只是要花构建的时间)。

如果盘更紧(比如已用 25GB):先删旧后端镜像再构建,代价是 构建期间站点后端不可用(约 6–10 分钟)。这次没走到这一步。
