## 1. 修正后的部署流程

**每一步都标了它防的是哪个坑。** 按顺序做,别跳。

### 1.0 前置:备份 + 摸底(只读,不改任何东西)

```bash
# 数据是唯一不可再生的东西(实测只有 181MB,备份很便宜)
mkdir -p ~/gyt-backups
rsync -az -e ssh gyt-prod:/opt/gyt/data/ ~/gyt-backups/data-$(date +%Y%m%d-%H%M%S)/

# 摸底:磁盘、镜像、容器
ssh gyt-prod 'df -h /; docker system df; docker images; docker ps'
```

⚠️ **注意 `Build Cache` 那一行。** 它是 0B 就意味着**下一次构建是全量的**(含 2.2GB 权重重下),
峰值需求会高出一个量级 —— §3 的账全看这个数。

### 1.1 腾空间(§3 会给出这一步能不能省)

```bash
ssh gyt-prod 'journalctl --vacuum-size=50M; apt-get clean'
```

`/opt/旧站冷备-*.tar.gz`(214MB)可以挪到开发机再删 —— **先 scp 下来、比对 sha256 再删源**。
实测这一轮共回收 **597MB**(11G → 12G)。

#### 2026-08-20 补:最有效的一招是**临时卸掉那个没在用的 swapfile**(这天三轮构建都靠它)

那台 VPS 有**两个 swapfile、共 8G**(`/swapfile` 与 `/swapfile2`),`swapon --show` 能看到。
其中 `/swapfile` 长期几乎没在用 —— 实测 `USED` 只有 **128K**,另一个是 **3.1G**。
全量重建后端需要约 **13G**,而常态可用只有 **11G 左右**,卸掉那个空的正好补上这 4G:

```bash
# 第一步:先看清哪个在用,别卸错
ssh gyt-prod 'swapon --show'

# 第二步:卸掉没在用的那个(11G → 15G)
ssh gyt-prod 'swapoff /swapfile && rm -f /swapfile'

# ……构建……

# 第三步:用完必须原样重建
# ⚠️ /etc/fstab 里那行还指着 /swapfile,不重建的话下次重启会报挂载失败
ssh gyt-prod 'fallocate -l 4294967296 /swapfile && chmod 600 /swapfile \
  && mkswap /swapfile && swapon /swapfile && swapon --show'
```

⚠️ **两条注意:**

1. **`df -h` 在同一次 ssh 会话里可能读到陈旧值。** 实测删完还显示 11G,**新开一次 ssh 才显示 15G**
   —— 别据此以为没删掉。**判据是 `ls -l /swapfile`**(文件在不在),不是 `df`。
2. **卸的必须是没在用的那个。** 卸正在用的会把 3G 页面往 RAM 里搬,而那台**只有 2GB 内存**。

**实测的磁盘曲线对照**(2026-08-20 三轮,同一个后端全量构建):

| 起步可用 | 结果 | 构建过程中的最低点 |
|---|---|---|
| **11G** | ❌ 失败 —— 在 unpack 阶段撞盘(见 §2.9) | — |
| **13G** | ✅ 成功 | **2.2G** |
| **15G** | ✅ 成功 | **3.3G** |

也就是说 **13G 是能过的下限,而且只剩 2.2G 余量**;11G 过不去。

### 1.2 同步代码 —— ⚠️ 别用旧文档里那条命令

```bash
# 演练:先看清楚要删什么(必做)
rsync -azn --delete -i --no-o --no-g --filter=':- .gitignore' \
  --exclude '.git' --exclude 'backups/' \
  ./ gyt-prod:/opt/gyt/

# 确认无误再真跑
rsync -az --delete --no-o --no-g --filter=':- .gitignore' \
  --exclude '.git' --exclude 'backups/' \
  ./ gyt-prod:/opt/gyt/
```

四个开关缺一不可,理由分别见 §2.2(`--filter`)、§2.3(`--no-o --no-g`)、
§2.2(`--exclude '.git'`)、下面这一段(`--exclude 'backups/'`)。

🔴 **`--exclude 'backups/'` 是 2026-08-21 部署时演练档当场抓到的**,别删。

那次加了备份服务(`docker-compose.vps.yml` 的 `housekeeping`,当天叫 `backup`),它往宿主 `backups/` 写;
`.gitignore` 里也加了 `/backups/`。按「让 rsync 直接读 .gitignore」这条单一真相的
设计,它**应该**被保护住 —— §2.2 ④ 那条也写着「`--delete` 默认不删被排除的文件」。

**但演练档第一行就是 `*deleting backups/`。** 实测结论:经 `--filter=':- .gitignore'`
合并进来的规则,在这个组合下没能把接收端那个目录保护住,只有显式 `--exclude` 才行。

危害等级和 §2.2 那次一样、甚至更高:一旦备份服务跑起来,那个目录里装的是
**这台机器唯一的备份**,而删它的正是那条用来部署的命令。

⚠️ 教训不是「多加一个 exclude」,是**演练档必须真的看**:这条命令的三个已知坑
(对话历史、属主、.git)全是演练档抓出来的,这是第四个。
数一下 `deleting` 的行数比逐行读更省事:

```bash
rsync -azn --delete -i --no-o --no-g --filter=':- .gitignore' \
  --exclude '.git' --exclude 'backups/' ./ gyt-prod:/opt/gyt/ | grep -c deleting
# 期望 0。非 0 就逐行看清楚每一条,别 rsync 完再后悔。
```

### 1.3 后端镜像 —— **2026-08-23 起不在 VPS 上构建了,从 GHCR 拉**

> **这一节整个重写过。** 原文是「在 VPS 上构,不要在开发机构了传」,那条结论
> 在当时的两个选项之间是对的,但**它把「构建必须发生在 VPS 上」当成了通则,
> 而那一步是错的** —— 完整推翻理由见改写后的 §2.1。

#### 为什么搬走

TODO-40 的结论原话:**「这台机器上,后端镜像的全量重建从来就不成立」** ——
2 核 / 1966MB / 30GB,而镜像 6.3GB,一次全量重建峰值约 13.2GB。
以前能成全靠增量缓存,而 §1.3 原文那句「构完立刻 `docker builder prune -af`」
恰恰保证了**下一次一定是全量的**。那两条建议在这台机器上互斥,
不是文档写错,是机器装不下。

现在:**构建在 CI**(`.github/workflows/ci.yml` 的 `build-push` job,
只在 push 到 main 或手点 workflow_dispatch 时跑),推到 GHCR;VPS 只 `pull`。

#### 一次性准备(每台机器只做一次)

在 VPS 上登录 GHCR。需要一把 **classic** PAT,**只勾 `read:packages`**:

```bash
ssh gyt-prod
echo '<你的 ghp_… >' | docker login ghcr.io -u <你的 GitHub 用户名> --password-stdin
```

⚠️ **必须是 classic token,fine-grained 不行** —— GitHub 官方文档明确说
fine-grained 不支持 ghcr.io 认证,社区里也是「classic 一次就过、
fine-grained 配好权限照样失败」。
⚠️ `read:packages` 在 UI 上缩进在 `write:packages` 底下,只点里面那个。
`repo` 一个都别勾 —— 服务器只需要下载镜像,不需要读代码。
⚠️ classic token 的 scope 是**账号级**的,勾了就能读你所有包,没法只限一个仓库。
这是 GHCR 不支持 fine-grained 换来的,知道就行。
⚠️ 凭据明文存在 `/root/.docker/config.json`(600 root:root)。实际暴露面比看上去小:
要读它得先有这台机器的 root,而有了 root 之后 `/opt/gyt` 里的源码、`.env` 里的
两把模型 Key、台账、工地照片本来就都在。
⚠️ **PAT 会过期,而过期没有任何预警** —— 表现是某天部署突然 401,
而那多半发生在你急着回滚的时候。建的时候把到期日记下来。

#### 每次部署

**第一步:先量磁盘,不够就别开始。**

```bash
# 从 registry 问精确的压缩下载量(不是估算)
ssh gyt-prod 'docker manifest inspect ghcr.io/<owner>/gyt-backend:<SHA> \
  | python3 -c "import json,sys; print(sum(l[\"size\"] for l in json.load(sys.stdin)[\"layers\"])//1048576, \"MB 压缩\")"'

ssh gyt-prod 'df -m / | tail -1'
```

判据:**可用 ≥ 压缩下载量 + 解开后大小**。2026-08-23 实测:压缩 1855MB、
解开 6.3GB,峰值约 8.2GB;当时可用 9.4GB,拉完剩 3.5GB。

**第二步:纯 `docker pull`,先不碰 compose。**

```bash
ssh gyt-prod 'docker pull ghcr.io/<owner>/gyt-backend:<40 位 commit SHA>'
```

✅ **这一步失败是安全的**,和 §2.9 那次构建失败完全不同:新镜像叫
`ghcr.io/…`,和本地的 `gyt-backend:*` 是**两个不同的名字**,拉挂了 docker
自己清掉半截内容,旧镜像一根汗毛都不动。所以不用像构建那样提心吊胆。

**第三步:设 tag,再切。**

```bash
ssh gyt-prod 'cd /opt/gyt && sed -i "s|^GYT_IMAGE_TAG=.*|GYT_IMAGE_TAG=<SHA>|" .env'
```

`docker-compose.vps.yml` 里 backend 与 housekeeping 都走同一个 YAML 锚点
`x-backend-image`,值是 `ghcr.io/<owner>/gyt-backend:${GYT_IMAGE_TAG:?…}`。
忘了设 tag 会在 `up` 那一刻**硬失败**,不会悄悄起一个别的版本。

⚠️ **housekeeping 也用这个镜像。** 它和 backend 共用锚点正是为了防这个:
写两遍的话升级时容易只改 backend,等旧镜像被删,housekeeping 就找不到镜像
起不来 —— **而它是定时清理任务,当时不会有人发现**。

### 1.4 起后端 —— **两个服务一起,`--no-build --no-deps`**

```bash
ssh gyt-prod 'cd /opt/gyt && \
  docker compose -f docker-compose.yml -f docker-compose.vps.yml \
  up -d --no-build --no-deps backend housekeeping'
```

- `--no-build`:理由见 §2.4(带 `--build` 会把镜像再构一遍)。现在更硬 ——
  VPS 上压根不该发生构建。
- `--no-deps`:见 §2.9 的连锁,镜像缺失期间不加它会顺手去动别的服务。
- **两个服务都要写**,理由同上面那条 housekeeping 的警告。

实测 **33 秒 healthy**(compose 里 healthcheck 的 `start_period` 写着 120s,
那是上限不是预期值)。

#### 切完必须验这四条

```bash
# ① 跑的是不是那个镜像(和 CI 报的 digest 逐字比对)
ssh gyt-prod 'docker inspect gyt-backend-vps gyt-housekeeping --format "{{.Image}}"'

# ② 对话历史还在不在(切换前后线程数必须一样)
#    机制是 docker-compose.vps.yml 里那条 ./data/langgraph:/app/.langgraph_api,
#    2026-08-11 真丢过一次才加的;2026-08-23 实测有效,13 → 13 零丢失。

# ③ 六个容器都在
ssh gyt-prod 'docker ps --format "{{.Names}} {{.Status}}"'

# ④ 磁盘
ssh gyt-prod 'df -m / | tail -1'
```

#### 🔴 最后才删旧镜像

**确认新容器 healthy、功能验过之后**,才:

```bash
ssh gyt-prod 'docker rmi gyt-backend:vps'
```

顺序反了就是 §2.9 / TODO-40 那条事故链的入口:旧镜像是你唯一的秒级回滚点,
而它**不在 GHCR 上**(它是当初在 VPS 上构建的),删了之后回退只能靠离线备份。

⚠️ 判断「还要不要留」的依据是**下一次拉取要不要空间**,不是洁癖。
如果近期有演示,留着更值 —— 而且下次部署若只改了源码,拉取只有几 MB
(镜像分层,权重那 2.3GB 一个字节都不重传)。

### 1.5 前端:先重新生成 `frontend/`,再构

`frontend/` 不进 git、也被 rsync 排除,VPS 上那份是旧的(§2.6):

```bash
ssh gyt-prod 'cd /opt/gyt && COREPACK_ENABLE_DOWNLOAD_PROMPT=0 bash scripts/setup-frontend.sh'
```

⚠️ VPS 上**没有 pnpm**,脚本装 `qrcode.react` 那一步会 die。用容器补(§2.7):

```bash
ssh gyt-prod 'cd /opt/gyt/frontend && docker run --rm -v "$PWD":/app -w /app \
  -e COREPACK_ENABLE_DOWNLOAD_PROMPT=0 node:22-slim \
  sh -c "corepack enable && pnpm add --save-exact qrcode.react@4.2.0"'
```

⚠️ **2026-08-20 补:要 pnpm 的不止 `qrcode.react` 一个了。** W12 的简繁转换库
**`opencc-js@1.4.1`**(`hant-convert.tsx` 里 `import("opencc-js/cn2t")` 用的那个)是同一种装法,
脚本在**同一处**会因为同一个原因 die。两个一起补,判据与救法见扩写后的 **§2.7**。

```bash
ssh gyt-prod 'cd /opt/gyt && DOCKER_BUILDKIT=1 \

ssh gyt-prod 'cd /opt/gyt && \
  docker compose -f docker-compose.yml -f docker-compose.vps.yml up -d --no-build'
```

### 1.6 Caddyfile 改了就必须 **重建 caddy 容器**,不是 reload

```bash
ssh gyt-prod 'cd /opt/gyt && \
  docker compose -f docker-compose.yml -f docker-compose.vps.yml up -d --no-build --force-recreate caddy'
```

`caddy reload` 在这套部署里**用不了**(admin API 没开),而绑定挂载的 inode 问题让容器看不到新文件 —— 见 §2.8。

核对路由顺序(**这是唯一可靠的判据,`caddy validate` 说 Valid 不算数**):

```bash
ssh gyt-prod 'docker exec gyt-caddy caddy adapt --config /etc/caddy/Caddyfile' \
  | python3 -c "import json,sys;..."   # 完整脚本见 §2.8
```

`/api/checkin*` 必须排在 `/api/*` **之前**。

### 1.8 登录页改了,必须**重启 `gyt-login`**(2026-08-20 新增)

⚠️ **编号排在 §1.7 后面只是因为它是后补的;真做的时机在 §1.7 验证之前**,和 §1.6 挨着做。

§1.6 说的是「Caddyfile 改了要重建 caddy」。**`scripts/login-page.html` 是同款问题** ——
rsync 把新页面同步上去了并不等于生效:

```bash
ssh gyt-prod 'cd /opt/gyt && \
  docker compose -f docker-compose.yml -f docker-compose.vps.yml up -d --no-build --force-recreate login'
```

**根因**:`scripts/serve_login.py` 的 `_read_page()` 在**进程启动时**把整页读进内存
(`serve_login.py:646` 那句 `page = _read_page(args.page)`),之后**再也不读盘**。
—— 所以不重启的话,容器手里一直是启动那一刻的旧页面。

**不重启的表现**:文件明明同步上去了,浏览器看到的还是旧的,**而且没有任何报错**。
**W12 繁體化那次就是这么撞的**:rsync 完打开登录页还是简体,第一反应是「同步失败了」,
于是回去查 rsync、查 filter、查 `.gitignore` —— 查了半天,而宿主上那份文件从头到尾就是对的。

**判据**(一条命令分清是「没传上去」还是「没重启」):

```bash
# 宿主那份 —— 传没传上去
ssh gyt-prod 'grep -c "繁體" /opt/gyt/scripts/login-page.html'
# 容器手里那份 —— 生没生效(注意它是启动时读进内存的,这里 exec 看到的是文件不是内存,
# 所以真正的判据是「重启过没有」:比对容器启动时间与文件 mtime)
ssh gyt-prod 'docker inspect gyt-login --format "{{.State.StartedAt}}"; \
  stat -c "%y" /opt/gyt/scripts/login-page.html'
```

**文件 mtime 比容器 StartedAt 新 = 页面没生效,去重启。**

### 2.1 🔴 在开发机构建再传镜像 —— 被上行带宽否决(白花约 1 小时)

> ## ⚠️ 2026-08-23 订正:这条的结论被推翻了一半,而错的那一半代价很大
>
> 下面的实测数据全部是真的,**当时的决定也是对的** —— 在「开发机构建再传」
> 和「VPS 上构建」这两个选项之间,0.27 MB/s 的上行确实把前者否掉了。
>
> **错的是从它引出的通则:「在 VPS 上构,不要在开发机构了传」。**
> 那句话被写进了 §1.3 的标题,于是「构建必须发生在 VPS 上」成了此后
> 八天里没人再质疑的前提 —— 而 TODO-40 证明这台机器**根本构建不了**
> (峰值 13.2GB,可用 11GB),这个前提直接把部署逼进了死角:
> 留着构建缓存要 8GB(装不下),不留则下次全量要 13GB(也装不下)。
>
> **量错的是链路,不是数字。** 这条测的是**开发机的上行**。而如果构建放在
> **CI**,开发机那条链路根本不在路径上 —— GitHub 的 runner 两个方向都快,
> VPS 只需要下行。2026-08-23 补量了当年没量的那两个方向:
>
> | 链路 | 实测 | 当年量过吗 |
> |---|---|---|
> | 开发机上行 → VPS | 0.46 MB/s | ✅ 就是它否决了方案 |
> | **VPS 上行 → 开发机** | **6.72 MB/s**(快 14 倍) | ❌ 没量 |
> | **VPS 下行** | **20 MB/s**(快 43 倍) | ✅ 量过,但没往「让别人构建」上想 |
>
> 而且镜像是**分层**的:改源码之后 VPS 只拉变化的那一层
> (`COPY . /app` 实测 2.96MB),权重那 2.3GB 一个字节都不重传 ——
> 「传 6.38GB 要 5.3 小时」这个算法只对**第一次**成立。
>
> **教训比原文那条更普适:被实测数据否决的方案,回头核一眼量的是不是真正的
> 瓶颈链路。** 一个真实的数字 + 一个没被质疑的前提,足以把一条正确的路
> 封死八天。现行流程见改写后的 §1.3。

**当时的想法**:30GB 盘装不下构建缓存(历史实测 9.34GB)+ 新镜像(6.4GB),
那就把构建搬到开发机,VPS 只负责装镜像 —— 镜像只要 6.4GB,11GB 够。

**实测数据把这个方向直接否了**:

| | 实测 |
|---|---|
| 开发机**上行** | **0.27 MB/s**(50MB 用 181 秒) |
| VPS **下行** | **20 MB/s**(200MB 用 10 秒) |
| 传 6.38GB 镜像(gzip 后约 5GB) | **约 5.3 小时** |
| VPS 自己下 4.4GB 权重 | **约 3 分钟** |

**教训**:「把重活搬到本机」这个直觉在**家庭宽带 → 机房**这个方向上是反的。
家用上行通常只有下行的十分之一,而机房两个方向都快。
**要搬之前先量两个方向的带宽**,两条命令的事:

```bash
# 开发机上行
dd if=/dev/zero bs=1m count=50 | ssh gyt-prod 'cat > /dev/null'
# VPS 下行
ssh gyt-prod 'curl -sL -o /dev/null -r 0-209715200 <某个大文件 URL>'
```

**中止是安全的**:`docker save | ssh | docker load` 被 kill 之后,VPS 上
`docker images` 里没有任何新镜像、tag 没动 —— `docker load` 要么成功要么不打标签,
不会留下 §2.9 那种半截状态。

### 2.2 🔴 文档里那条 rsync 会删掉生产的对话历史

**旧命令**(`W6_VPS_队友接入.md` 记的):

```bash
rsync -az --delete --exclude '.venv' --exclude '__pycache__' --exclude 'node_modules' \
  --exclude '.next' --exclude 'frontend/' --exclude 'data/artifacts' --exclude 'data/uploads' \
  --exclude 'data/gyt.sqlite3' --exclude '.env' --exclude '.env.vps' ./ gyt:/opt/gyt/
```

**演练(`-n`)实测:会删掉生产 306 个文件**,其中包括:

- `data/langgraph/` **整个目录** —— 那是**全部对话历史**(线上 88MB)。
  而 commit `08f606d`(「容器一重建,所有历史对话清零」)修的正是这个,这条命令会把那次修复的成果抹掉;
- `data/cache/` 约 290 个 LLM 磁盘缓存文件(删了下次提问全部真花钱);
- `data/chroma`(向量库)、`data/demo`、`data/cad_index` 同样不在清单里。

**根因**:线上 `data/` 下有 **8 样**,而那份 exclude 清单只排了 **3 样**。
这是「维护一份平行清单」必然的漂移 —— 补四行不解决问题,下次加第九样还会漏。

**修法:让 rsync 直接读 `.gitignore`**,单一真相:

```bash
rsync -az --delete --no-o --no-g --filter=':- .gitignore' --exclude '.git' ./ gyt-prod:/opt/gyt/
```

实测效果:

| | 旧命令 | 新命令 |
|---|---|---|
| 传输 | 922MB / 11388 文件 | **2.8MB / 84 文件** |
| 删除 | **306 个**(含对话历史) | **3–8 个**(全是 VPS 侧的构建日志) |
| `data/` 与 `.env` | 会动 | **零涉及** |

两道保护:① `.gitignore` 里有 `/data/*`、`.env.*`,filter 会排除它们;
② rsync 的 `--delete` **默认不删被排除的文件**。

`--exclude '.git'` 单列是因为 `.gitignore` 不会忽略 `.git` 自己 ——
不排的话会连带删掉 VPS 上那份 `.git`(见 §2.10),也会白传几十 MB。

顺带:922MB 里有 **870MB 是仓库根那个 gitignore 掉的 YOLO 训练素材**
(`construction-safety-monitor.v1i.yolov8*`),旧清单同样没排。

### 2.3 🔴 `rsync -a` 会把 `data/` 的属主改掉,容器从此写不进库

`-a` 含 `-o`(属主)与 `-g`(属组)。线上 `/opt/gyt/data` 是 **`10001:996`**(容器里的 gyt 用户),
而开发机是 `501:staff`,rsync 在对端以 root 跑 —— **`data/` 会被 chown 成 501**。

**后果不是立刻报错**:容器照样 healthy、页面照样打得开,但 uid 10001 没法在 `data/` 下**新建**条目
—— SQLite 的 `-wal` / `-journal` 首当其冲。这是 `W6_VPS部署与访问口令.md:509-529` 记过的老坑。

**修法**:加 `--no-o --no-g`。验证靠 itemize 输出那一列标志位:

```
.d..t.og. data/     ← 危险:o(属主)g(属组)都要改
.d..t.... data/     ← 加了 --no-o --no-g 之后,只剩 mtime
```

同步后顺手核一次:`ssh gyt-prod 'stat -c "%u:%g" /opt/gyt/data'` 必须仍是 `10001:996`。

### 2.4 🔴 `up -d --build` 把已经构好的镜像又构一遍,直接撞盘

后端镜像在 §1.3 已经构好了(`BUILD_EXIT=0`),然后我跑了
`docker compose ... up -d --build` 想一次把前后端都起来 ——
**`--build` 是无条件重构,不看镜像在不在**。而我刚 `builder prune -af` 清空了缓存,
于是全量重来,在下载权重那步撞 `No space left on device`。

**修法**:镜像已就绪时用 `--no-build`。要构就单独 `build <service>`,构完再 `up -d --no-build`。

**站点全程没受影响** —— 旧容器还跑着,失败的只是构建。

### 2.5 🔴 `setup-frontend.sh` 里 `install_new_file` 排在会 `die` 的步骤之后

**现象**:前端构建报 `Module not found: Can't resolve './GytStatusCards'`。

**根因**:两条分支合流时,我把队友那两个组件的 `install_new_file` 放在了
「装 qrcode.react」**之后**,而那一步在没有 pnpm 的机器上 `die` —— **整个脚本终止**,
后面的拷贝一行都不执行。VPS 恰好没装 pnpm(§2.7)。

**这个错的隐蔽处**:报错指向「组件缺失」,而真因是「脚本提前退出」,中间隔着好几层。
脚本的输出里甚至能看到前三件装成功了 —— 更像是覆盖件坏了。

**修法**:**所有 `install_new_file` / `apply_override` 必须排在任何可能 `die` 的步骤之前。**
已在脚本里那一步前面加了警告注释。判据很简单:拷文件不依赖任何外部工具,就该排在最前。

### 2.6 `frontend/` 不进 git 也不进 rsync,VPS 上那份是旧的

`frontend/` 在 `.gitignore` 里,所以 rsync 的 filter 会排除它 ——
**代码同步不会更新前端**。实测 VPS 上那份停在 8-11,打卡三件全缺。

**修法**:同步完代码后,在 VPS 上重跑 `scripts/setup-frontend.sh` 再构镜像。
这不是缺陷,是 `frontend/` 由脚本生成这个设计的必然结果 —— 但**很容易忘**,
忘了的表现是「后端更新了、前端没有」,而两者都不报错。

### 2.7 VPS 上没有 pnpm

VPS 平时不装前端依赖(构建在 Docker 里做),所以宿主没有 node/pnpm。
而 `setup-frontend.sh` 装 `qrcode.react` 需要它。

**修法**:用一次性容器补(不给 VPS 装任何东西):

```bash
cd /opt/gyt/frontend && docker run --rm -v "$PWD":/app -w /app \
  -e COREPACK_ENABLE_DOWNLOAD_PROMPT=0 node:22-slim \

```

⚠️ 必须写进 `package.json` **和** `pnpm-lock.yaml` 两处 ——
前端 Dockerfile 用的是 `pnpm install --frozen-lockfile`,lockfile 没更新会直接失败。

#### 2026-08-20 补①:要 pnpm 的**不止 `qrcode.react`**,`opencc-js` 也要

W12 简繁转换加的 **`opencc-js@1.4.1`**(`hant-convert.tsx` 里
`import("opencc-js/cn2t")` 那个懒加载库)走的是**同一段脚本、同一个 die**:


救法与上面一模一样,把包名换掉即可 —— 两个包**一次性一起补**,省一次容器启动:

```bash

  -e COREPACK_ENABLE_DOWNLOAD_PROMPT=0 node:22-slim \
  sh -c 'corepack enable && pnpm add --save-exact qrcode.react@4.2.0 opencc-js@1.4.1'
```

⚠️ **别以为「只补 qrcode.react 就完了」** —— 它俩在脚本里是两个相邻的独立步骤
(`setup-frontend.sh:618` 与 `:642`),前一个补上了,后一个照样 die,而**后面的步骤仍然一行都不执行**
(这正是 §2.5 那个坑的形状)。

#### 2026-08-20 补②:这个坑**不是每次部署都触发** —— 别以为它消失了

2026-08-20 那几轮里,这一步**大多数时候根本没触发**,脚本直接打印:

```
[跳过] qrcode.react@4.2.0 已在 package.json,无需重装
[跳过] opencc-js@1.4.1 已在 package.json,无需重装
```

**根因**:脚本是先 `grep` `package.json` 里有没有那个版本,有就跳过(`setup-frontend.sh:620` / `:644`),
**根本不看 `node_modules` 在不在**。所以只删了 `node_modules` 和 `.pnpm-store` 去省空间的话,
`package.json` 还在,这一步就是跳过的。

**判据 —— 这个坑只在下面两种情况出现:**

1. `frontend/` 被**整个删掉**(`package.json` 一起没了,脚本要重新 clone 上游);
2. **换新机器 / 新 VPS**(那儿从来没跑过 `setup-frontend.sh`)。

**为什么值得单写一条**:看到「跳过」两个字很容易得出「这个坑修好了」的结论,
于是下次真在新机器上部署时又被同一个 die 拦住,而那会儿人已经不记得有这一节了。

### 2.8 🔴 Caddyfile 改了,`reload` 用不了、容器也看不见新文件

**两个问题叠在一起:**

1. `docker exec gyt-caddy caddy reload` 报
   `dial tcp [::1]:2019: connect: connection refused` —— **admin API 没开**(这是刻意的,
   admin 端点能改整个配置)。所以 reload 这条路在这套部署里不存在。
2. 更隐蔽的:`Caddyfile` 是**绑定挂载**(`/opt/gyt/Caddyfile → /etc/caddy/Caddyfile`),
   而 rsync 是**新建文件再 rename 替换** —— 容器里那个挂载点仍指向**旧 inode**。
   实测:宿主那份有 3 处 `api/checkin`,容器里 `grep -c` 是 **0**。

**修法**:`--force-recreate caddy`。

**判据**:`caddy validate` 说 `Valid configuration` **不算数** ——
这个文件自己的注释就记着「裸奔那次 validate 也说 Valid」。唯一可靠的是打路由树:

```bash
docker exec gyt-caddy caddy adapt --config /etc/caddy/Caddyfile 2>/dev/null | python3 -c "
import json,sys
cfg=json.load(sys.stdin)
def walk(rs,d=0):
    for r in rs:
        p=[x for m in (r.get('match') or []) for x in m.get('path',[])]
        if p: print('  '*d+str(p))
        for x in (r.get('handle') or []):
            if 'routes' in x: walk(x['routes'],d+1)
for s in cfg['apps']['http']['servers'].values(): walk(s.get('routes',[]))
"
```

正确输出(`/api/checkin*` 必须在 `/api/*` **之前**):

```
['/login*']
['/logout*']
['/api/checkin', '/api/checkin/*']
['/api/*']
['/artifacts/*']
```

### 2.9 🔴 TODO-33 那个陷阱当场复现了一次

前端构建在最后一步失败:

```
#17 naming to docker.io/library/gyt-frontend:vps done      ← tag 已经打上去了
#17 unpacking to docker.io/library/gyt-frontend:vps
#17 ERROR: failed to extract layer …: no space left on device
```

**`docker images` 里 `gyt-frontend:vps` 指向一个 591MB 的半截镜像**(正常的是 1.93GB)。
**机器一重启,compose 就会拿它起前端。**

**铁律(TODO-33 记过,这次证明它是对的)**:
**构建失败之后,第一件事是 `docker images` 看 tag 指到哪儿了**,不是看日志找原因。

**修法**:`docker rmi` 掉那个半截镜像,腾够空间再重构。

#### 2026-08-20:同一天又复现两次,而且**第一次比上面记的更狠**

这天四轮部署里踩了两次。**第一次撞的是后端**,而且比 08-15 那次多丢了一样东西:

```
#27 exporting to image
#27 unpacking to docker.io/library/gyt-backend:vps
#27 ERROR: failed to extract layer sha256:9990832a…: write
    /var/lib/containerd/…/models--BAAI--bge-m3/blobs/…: no space left on device
```

- `gyt-backend:vps` 指向一个 **1.96GB 的半截镜像**(正常是 **6.38GB**);
- 🔴 **而且 `gyt-backend:known-good` 那次已经被删掉了。** 08-15 那次旧镜像还在、tag 回去就行;
  这次 `docker rmi` 报的是 **`No such image`** —— **没有可以 tag 回去的东西了。**
- 当时站点是靠「**容器还引用着已删除镜像的层**」撑着的。也就是说:
  **进程还活着,但它脚下的镜像已经不存在了** —— `docker compose restart` / 机器重启 /
  任何一次容器重建,**站点当场全完,而且没有回滚绳**。

**第二次**撞在同一个地方,但因为上一次的教训,恢复只用了**一句 `docker tag`**,
**站点全程没受任何影响**。

**结论要升级 —— 不只是「失败后看 tag」,而是:**

> 🔴 **每次构建之前,先确认 `known-good` 指向的就是正在跑的那个镜像。**

「有个叫 known-good 的 tag」不算数,**它得真的指向当前在跑的那个 image ID**。核法是两条命令对比:

```bash
# 正在跑的容器用的是哪个 image(拿到完整 sha256)
ssh gyt-prod 'docker inspect gyt-backend --format "{{.Image}}"'

# known-good 这个 tag 指向哪个 image(--no-trunc 才看得到完整 sha256)
ssh gyt-prod 'docker images --no-trunc | grep known-good'
```

**两个 sha256 必须逐字符相同。** 不同(或者 `known-good` 压根不存在)就先补上再构建:

```bash
ssh gyt-prod 'docker tag gyt-backend:vps gyt-backend:known-good'
```

⚠️ **为什么非要 `--no-trunc`**:短 ID 只有 12 位,肉眼扫一眼「看着一样」不构成判据 ——
而这条判据错了的代价,就是上面那个「站点靠悬空的层吊着命」的状态。

### 2.10 `/opt/gyt` 里其实**有** `.git`,但连不上 GitHub

文档写「是 rsync 上去的工作副本,**不是 git clone**」—— 意思对,字面不准。
实测那儿有一份**真的 `.git`**(32MB,rsync 顺带拷上去的旧快照,HEAD 停在 `a304109`),
`git status` 会报 `dubious ownership`,`git fetch` 报 `Host key verification failed`
(服务器上没有 GitHub 凭据,这是刻意的)。

**结论不变:别在服务器上 `git pull`,那儿 pull 不了。** 但知道那儿有个 `.git` 有两个用处:
① rsync 要 `--exclude '.git'`,否则会删它;② 有人可能会被 `git log` 显示的旧 commit 误导。

### 2.11 🔴 验证鉴权时,**不带登录会话等于没验**

站点每条 `/api/*` 都先过 Caddy 的 `forward_auth`。**没有会话时它自己就回 401** ——
于是「不带令牌 → 401 → 通过」这个判断在没会话时是**必然的假绿灯**:
**打卡端点完全裸奔也会绿。**

实测两种 401 长得不一样,这是唯一的分辨方法:

```
{"detail":"登录已过期,请刷新页面重新登录。"}   ← Caddy 门禁拦的,**这条不构成验证**
{"detail":"访问被拒绝,请联系发你链接的人。"}   ← 打卡端点的鉴权拦的,**这才算数**
```

**正确的验法**:先登录拿会话,再**带着会话、不带令牌**打过去,必须仍是「访问被拒绝」。

```bash
PW=$(cat /root/.gyt-basic-auth-plaintext)
curl -sk -c /tmp/cj.txt -X POST "$ORIGIN/login" --data-urlencode "pw=$PW"   # 字段名是 pw
curl -sk -b /tmp/cj.txt -X POST "$ORIGIN/api/checkin" …                     # 期望「访问被拒绝」
```

⚠️ 登录表单字段名是 **`pw`**,不是 `password`(`serve_login.py:429` 有断言守着)。

### 2.12 🔴 `set -a; . ./.env` 会毁掉登录口令哈希

**现象**:`gyt-login` 容器无限重启,日志刷
`[错误] GYT_LOGIN_HASH 格式不对,应形如 scrypt$16384$8$1$<salt>$<hash>`。

**根因**:`.env` 里存的是 `scrypt$$16384$$8$$1$$…` —— **双 `$` 是给 docker compose 转义用的**
(compose 把 `$$` 解析成一个字面 `$`)。而我在命令里 `set -a; . ./.env; set +a`,
**bash 把 `$$` 展开成了自己的进程 PID**,导出成 `scrypt7587701…`;
compose 又**优先使用环境变量**而不是 `.env` 文件,于是容器收到了这个坏值。

**修法:别 source `.env`。** compose 自己会读它,并正确处理 `$$`。
所有 build args(`GYT_PUBLIC_ORIGIN`、`GYT_ACCESS_TOKEN` 等)compose 都会自动从 `.env` 拿,
根本不需要先 source。

**这个坑的普遍形态**:任何在 `.env` 里为 compose 转义过的值(含 `$$` 的),
都不能用 shell 的 `source` 读。要在 shell 里用,得自己反转义。

### 2.13 🔴 `ssh … | tail` 会吃掉退出码,把失败读成成功(2026-08-20)

**现象**:后台构建任务报 **`exit code 0`**,我据此判定「构建成功」往下走 ——
而构建其实在 unpack 阶段就失败了(就是 §2.9 那次)。

**根因**:管道的退出码是**最后一段**的退出码。

```bash
ssh gyt-prod '… docker compose … build backend' | tail -40
#                └── 它失败了,退出码非 0                    └── 但拿到的是 tail 的退出码 = 0
```

**判据 —— 这条坑最难的地方是:它没有任何征兆。**
日志被 `tail -40` 截断之后,**连那行 `no space left on device` 都看不到**(报错落在那 40 行之外),
而退出码又白纸黑字说成功。**两个信息源同时说没事,而事情已经坏了。**

**修法:别走管道。把退出码写进文件,再单独读它。**

```bash
ssh gyt-prod 'cd /opt/gyt && rm -f /tmp/build.rc && \
  (DOCKER_BUILDKIT=1 docker compose -f docker-compose.yml -f docker-compose.vps.yml \
     build backend > /tmp/build.log 2>&1; echo $? > /tmp/build.rc) &'

# 轮询这个文件,拿到的才是真退出码;日志要看多少看多少,互不影响
ssh gyt-prod 'cat /tmp/build.rc 2>/dev/null || echo "还在构"'
ssh gyt-prod 'tail -40 /tmp/build.log'
```

⚠️ **这条不只影响构建。部署脚本里凡是走管道的地方,退出码都是骗人的** ——
`ssh … | grep`、`ssh … | head`、`docker … | tee` 全是同一个形状。
真要在管道里判成败,得 `set -o pipefail`(bash)或者像上面这样把退出码单独落一个文件。

### 2.14 构建失败之后,**别急着 `docker builder prune -af`**(2026-08-20)

**现象**:2026-08-20 第一次撞盘失败后,我的第一反应是腾地方 —— 立刻
`docker builder prune -af`,回收了 **4.187GB** 缓存,然后重构。

**那是错的。**

**根因**:那次失败发生在 **unpack 阶段** —— 也就是**所有层都已经构好了、只差落地**。
留着缓存重试,只需要重做 export + unpack 这最后一段;
prune 掉就是**从头再来一遍**,含 **2.2GB 的 BGE-M3 权重重新下载**。
我亲手把「只差最后一步」变回了「从第一步开始」。

**判据 —— 看失败发生在哪个阶段:**

| 日志里失败点的位置 | 含义 | 该怎么办 |
|---|---|---|
| `#27 exporting to image` / `#27 unpacking to …` **之后**失败 | 层已经构好了,只差落地 | 🔴 **别 prune**,腾别处的地方(§1.1 那招 swap)然后直接重试 |
| 更早的阶段失败(拉基础镜像、装依赖、下权重) | 层本来就没构完 | 才考虑 prune 腾地方 |

**修法**:先 `tail` 日志看清失败在哪个阶段,**再决定动不动缓存**。
落在 unpack 之后的,正确动作是去 §1.1 卸那个空 swapfile(白拿 4G),**缓存一个字节都不要动**;
腾完直接重跑同一条 build 命令,它会命中缓存、几分钟内走到刚才失败的那一步。

⚠️ **与 §1.3「构完立刻回收缓存」不矛盾** —— 那条说的是**构建成功之后**。
成功之后的缓存是纯占地方;**失败之后的缓存是你离成功最近的那段距离。**

### 2.15 🔴 `ruff format --check` 要跑**整树**,只跑改过的文件会在 CI 红(2026-08-20)

**现象**:本机绿,CI 在 **「格式检查 (ruff format --check)」** 那一步红
(`.github/workflows/ci.yml:211`)。

**根因不是环境,是跑法。** CI 跑的是 `uv run ruff format --check .` —— **整树 148 个文件**;
而人在本机往往只对自己改过的那几个 `.py` 跑 `--check`。
于是**新写的测试文件从头到尾没被格式检查看过一眼**,本机自然全绿。

**判据**:本机对着改动文件跑绿、CI 对着 `.` 跑红 —— 那么两边跑的**根本不是同一批文件**。
复现只要一条命令:`cd backend && uv run ruff format --check .`。

**修法:用整树口径的 make 目标,跟 CI 同一把尺子。**

```bash
make fmt    # ruff format . && ruff check --fix .   ← 整树格式化,对应 CI 的「格式检查」
make lint   # ruff check .                          ← 整树静态检查,对应 CI 的「静态检查」
```

⚠️ 这条严格说是 CI 不是部署,写在这儿是因为**它会挡住合并、从而挡住部署**;
而且症状是**「本机绿 CI 红」**这种最容易怀疑错方向的 ——
第一反应总是去查 ruff 版本、查 Python 版本、查缓存,
而真因只是「整树 148 个文件里,你只跑了自己改的那几个」。

### 2.16 前端产物里**搜不到常量名,要搜它的值**(2026-08-20)

**现象**:想验证「新写的客户端压缩代码真的进了前端镜像」,于是去产物里
`grep UPLOAD_BUDGET` —— **一个都搜不到**,看着像是覆盖件没装上、或者构建用了旧代码。

**根因**:Next.js 的压缩器会把 `const` **内联**掉。
`UPLOAD_BUDGET_BYTES`(`image-compress.ts:138`,值是 `600 * 1024`)在产物里根本不以名字存在,
它已经被替换成了字面量,而且连乘法都在编译期算完了。**标识符名字不是可靠的判据。**

**判据:搜值,或者搜压不掉的字符串字面量** —— 这两类东西压缩器动不了,才配当判据。

- 搜**值** —— `600 * 1024` 折叠成 `614400`;
- 搜**字符串字面量** —— `imageSmoothingQuality`(Canvas API 的属性名)、
  `acTL`(APNG 的块标识,代码里是比较用的字符串)、MIME 串 `image/png`。

**修法**:验「代码进没进镜像」时,**挑两三个上面这类锚点一起搜,别用常量名**;
一个锚点命中就够了,三个都不命中才是真没进去。
(新写代码时顺手留一个「压不掉的锚点」是很便宜的事 —— 一个 API 属性名、一个协议字面量都行。)

2026-08-20 实测(在前端镜像的产物里 grep):

| 搜什么 | 命中次数 |
|---|---|
| `614400` | **1** |
| `imageSmoothingQuality` | **1** |
| `acTL` | **1** |
| `image/png` | **9** |
| `UPLOAD_BUDGET` / `UPLOAD_BUDGET_BYTES` | **0** ← 不代表代码没进去 |

**四条都证明代码进去了,而常量名一个都搜不到。**
⚠️ 反过来说:**拿常量名 grep 不到就断定「代码没进镜像」是错判**,
这个错判会把人送去重跑 `setup-frontend.sh`、重建镜像、查覆盖件注册 —— 全是白工。

### 2.17 🔴 删掉一件 `apply_override` 之后,老机器上的 `frontend/` 不会自愈(2026-08-21)

`frontend/` 是生成物、不进 git,而 `setup-frontend.sh` 对**已存在**的目录是
**跳过 clone、原地打补丁**的。于是删掉一件 `apply_override` 之后:

| | 那个目标文件是什么 |
|---|---|
| 新机器(全新 clone) | 上游原版 —— **对的** |
| 老机器(已有 `frontend/`) | **上一版的补丁,永远留着** —— 错的 |

两边行为不一样,而**没有任何东西会说话**。具体到 2026-08-21 删掉的
`stream-provider.tsx`:老机器那份 `Stream.tsx` 还 `import { recordTiming }`,
而那个导出已经没了 —— `pnpm build` 报 `Module not found`。响是响的,
但查的人会先去怀疑 `timing-lib.ts` 写错了,而不是想到「这台机器的 `frontend/` 是旧的」。

**已经在脚本里补了闸** `check_retired_override`:按**内容标志串**判(不是判文件在不在
—— 目标文件在上游本来就有),命中就当场 `die` 并给出修法。2026-08-21 在 VPS 上
实测响过一次,退出码 1。

```bash
# 撞到它就是这一条,别想别的
ssh gyt-prod 'rm -rf /opt/gyt/frontend'
# 然后照 §1.5 重新生成(整个目录是生成物,删了没损失)
```

#### 🔴 但 `rm -rf frontend` 会**顺带升级上游**,这才是真正咬人的那一半

重新 clone 拿到的是**当天的上游 HEAD**,不是你上次那份。2026-08-21 实测:

```
老机器那份 frontend/package.json:  "typescript": "~5.8.3"
全新 clone 的:                     "typescript": "~6.0.3"
```

TypeScript 6 把 `BufferSource` 收窄成了 `ArrayBufferView<ArrayBuffer> | ArrayBuffer`,
而裸 `Uint8Array` 的默认类型参数是 `ArrayBufferLike`(可能由 `SharedArrayBuffer` 支撑)——
于是 `checkin-lib.ts` 里一句**一年没动过**的 `subtle.digest("SHA-256", bytes)` 当场 TS2345,
前端构建整个失败。

**这类错的特征是「只在干净机器上出现」**:

| 在哪儿跑 | 用的 TS | 结果 |
|---|---|---|
| 开发机 `pnpm tsc --noEmit`(旧 clone) | 5.8 | ✅ 绿 |
| `make test-frontend`(自带的 TS) | 5.8 | ✅ 绿 |
| VPS 全新 clone 里 `pnpm build` | **6.0** | ❌ 红 |

也就是说**本地怎么验都发现不了**,提交前的所有关卡全绿。

**判据**:凡是删过 `apply_override` 或者动过 `frontend/` 的部署,
在构镜像**之前**先用容器里的新 TS 单跑一次类型检查 —— 比构一遍镜像快得多:

```bash
ssh gyt-prod 'cd /opt/gyt/frontend && docker run --rm -v "$PWD":/app -w /app \
  -e COREPACK_ENABLE_DOWNLOAD_PROMPT=0 node:22-slim \
  sh -c "corepack enable >/dev/null 2>&1; pnpm exec tsc --noEmit"'
```

⚠️ 顺带一条:修这种类型错时**别用新语法去迁就新 TS**(比如写
`Uint8Array<ArrayBuffer>`)—— 那样下次上游再抬版本还得回来改,而且开发机那份
旧 TS 可能反过来不认。挑一种**不依赖版本**的写法(那次用的是 `bytes.slice().buffer`,
取一段确定由普通 `ArrayBuffer` 支撑的字节;顺带也更正确,带 `byteOffset` 的视图
直接取 `.buffer` 会把整个底层缓冲区都算进去)。

## 3. 30GB 磁盘怎么走完全程(2026-08-15)

> 2026-08-20 那天量了另外三条曲线(**11G / 13G / 15G 三种起步各是什么下场**),
> 记在 **§1.1** 那一节 —— 与本节的账互为对照,一起读。

历史记录(`W6_VPS部署与访问口令.md:283`)说:一块 30GB 的盘走完整流程,
最终占用约 20GB,**中途靠 `docker builder prune -af` 回收了 9.34GB**。
也就是说峰值几乎贴着 30GB。而这次的起点是**已经占了 20GB**。

**实测的磁盘曲线**(全程 30G 盘):

```
起点                                          11.0G 可用
├ 清理(journal + apt + 挪走 214MB 冷备)  →   12.0G   实测回收 597MB
├ 删前端镜像(反正要重建)                 →   13.0G
├ 后端全量构建(6 分钟)                   →    1.6G   ← 最紧的一刻
├ builder prune -af                        →    7.1G   实测回收 7.89GB
├ 删旧后端镜像(新的已验证 healthy)       →   12.0G   释放 6.28GB
├ 前端构建(8 分钟)                       →    5.6G
├ builder prune -af                        →    8.9G
└ 终点                                     →    9.0G   已用 22G/30G
```

**结论:30GB 走得完,但有三条硬要求:**

1. **构建缓存必须构完就清**,不能攒着。两次 prune 分别回收了 7.89GB 与 5.21GB;
2. **前后端必须分开构**,中间插一次 prune。一起构(`up -d --build`)必撞盘;
3. **旧后端镜像要在新的验证通过后尽快删**。它占 6.28GB,是最大的一块可回收空间。
   删之前先确认新容器 healthy 且端点探针通过 —— 删了就没有本机回滚绳了
   (但代码在 git 里,重建即可,只是要花构建的时间)。

**如果盘更紧(比如已用 25GB)**:先删旧后端镜像再构建,代价是**构建期间站点后端不可用**
(约 6–10 分钟)。这次没走到这一步。

4. 🔴 **`use-file-upload.tsx` 的查重竞态 —— 已知未修**(2026-08-20 隔离出来的)。

   **形状**:三条上传路(选文件 `:104` / 拖拽 `:160` / 粘贴 `:291`)全是同一个写法 ——
   **先算 `uniqueFiles`,再 `await` 转块**:

   ```ts
   const uniqueFiles = validFiles.filter((file) => !isDuplicate(file));  // 读的是当时的 state
   const newBlocks = await Promise.all(uniqueFiles.map(fileToContentBlock));  // ← 异步窗口
   ```

   `isDuplicate` 读的是闭包里那份**旧 state**。两次 change 事件都落在这个异步窗口内时,
   第二次看到的还是「还没加进去」的旧列表,**查重直接失效**。

   **后果链**:同一张图产生**两个块** → 后端 `uploads.py` **登记两份产物** →
   **识图跑两遍、钱花两份**。

   **实测隔离结果**(三种时序):

   | 时序 | 结果 |
   |---|---|
   | 单次 change 事件 | **1 个块** ✅ |
   | 第二次派发,但等前一次做完 | **1 个块** ✅(查重生效) |
   | 两次都落在异步窗口内 | **2 个块** ❌ |

   **⚠️ 而且这个窗口最近变宽了**:2026-08-19 加的客户端压缩(`image-compress.ts`)
   给 `fileToContentBlock` 多塞了一次 **decode + canvas + encode**,
   窗口从**约 50ms** 拉到**约 300ms** —— **六倍,更容易撞上。**

   **没修的原因**:三条路要一起改(改一条剩两条照样漏),而正确的修法是把「查重」搬到
   `await` **之后**、或者改用 ref 存已收文件的指纹 —— 都要动状态归属,不适合在部署当口顺手改。
