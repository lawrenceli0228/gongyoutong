## 1. 为什么要有这一轮

W4 那一轮验收 19/25。挂掉的 6 条里,4 条是日期字面量过期(测试自己的毛病),
**另外 2 条是产品的真问题**:

### C2 —— 英雄链会概率性漏掉「出报告」那一环

```
用户: 查一下这张照片,顺便出份巡检记录(照片编号 xxx)
  │
  ├─ supervisor ──transfer_to_inspection──► 英雄链子图
  │                                            │
  │                                   START ──► safety ──硬边──► report ──► END
  │                                                                 │
  │                                          硬边保证 report 被叫起来 ✅
  │                                          但没人保证 report 真调工具 ❌
  │                                                                 │
  └─ [report] 「巡检记录出好了,编号 GYT-20260809-153739」  ← 没调 render_inspection_report
                                                              磁盘上没有那份 docx
```

当初把 `safety → report` 写成硬边,解决的是「supervisor 有时不派第二跳」。
**漏的位置换了**:硬边把 report 叫起来了,但 report 自己凭上下文编了段话。

这跟 schedule 那次「不调工具凭记忆编回执」是同一种病。当时的解法是
`agents/schedule/guard.py` 的 `RequireLedgerTool` —— **而 report 是裸的**。

观察样本只有 2 次(一次挂一次过)。**这不是发生率,是个信号**,但它长在演示主路径上。

### A8 —— 红了,但查不出是哪种红

A8 断「乱日期报人话带举例」。我去查工具层:

```
「猴年马月」这个期限我没看懂。可以这样说:明天 / 后天 / 3天后 / 周三 / 下周三 / 月底 / 9月1号 / 2026-08-15。
```

含「明天」✅ 不含「开小差」✅ —— **断言在工具层必然通过**。所以红在上一层。
只剩两种可能:模型根本没调工具,或者调了但把文案改写了。

**而分不出是哪种** —— 脚本只记 PASS/FAIL,不留消息轨迹。想查就得重跑真调模型,
而重跑很可能不复现(C2 就是这样)。

## 3. 七个决策

| # | 决策 | 选定 |
|---|---|---|
| D1 | 防假账结构件放哪 | **下沉 `core/require_tool.py`,做成可配置** |
| D2 | 重试仍不调工具时 report 怎么办 | **硬错** —— 不让编造的编号出去 |
| D3 | 验收断言挂了留不留轨迹 | **失败就 dump 完整消息轨迹** |
| D4 | 验收脚本的「今天」从哪取 | **从后端取**(读 `list_tasks` 的 `data.today`) |
| D5 | A10 一周三天必红 | **按星期分支,两边都断** |
| T1 | knowledge/cad 也接结构件 | 记 TODO,不现在做(无实测证据) |
| T2 | 「断措辞」改「断事实」 | 记 TODO,要逐条拿捏 |

### D2 值得展开:为什么 report 和 schedule 的失败语义不一样

```
schedule 放行的后果        report 放行的后果
─────────────────────    ─────────────────────
嘴上销了、库里没销    →   工友拿到编号 GYT-xxx
      ↓                        ↓
D 组直查库,当场揭穿      磁盘上没有那份 docx
      ↓                        ↓
  有人兜底 ✅            没有任何人会发现 ❌
```

「没出成」工友看得见也重试得了,「以为出成了」无法补救,而且那个假编号会
污染后续所有引用(打印、转发、报给管理员)。

### D4 值得展开:后端本来就在吐今天

`schedule/tools.py::list_tasks` 的返回体:

```python
return ok(data={"tasks": …, "undated": …, "today": today_iso, …})
                                            ↑ 后端 date.today(),容器时区算出来的
```

验收 A2(「下周三之前还有哪些任务没完成」)**本来就会调 `list_tasks`**。
从那条 ToolMessage 里读 `data.today` 即可 —— **零新增接口、零额外模型调用**。

⚠️ 这条选择的已知弱点:容器时区若配错,脚本会跟着错、静默全绿。
缓解(不推翻决策):把取到的 today **原样打印**,并与 `Asia/Shanghai` 比一下,
不一致时打一条醒目的警告但**不判红** —— 判红会让部署在别的时区时误报,
而警告能让人一眼看见 2026-08-10 那种「容器裸 UTC」的配置事故。

## 4. 改造后的样子

```
core/require_tool.py                      ← 新(从 schedule/guard.py 下沉)
  RequireToolCall(
      tools_hint="记任务用 add_task…",     ← 各 Agent 自己的中文提示词
      on_give_up="pass" | "fail",         ← D2:schedule 放行 / report 硬错
      fail_msg="巡检记录没生成成功…",       ← 硬错时给工友看的人话
  )
        │
        ├── agents/schedule/__init__.py  extra_middleware=[RequireToolCall(… on_give_up="pass")]
        └── agents/report/__init__.py    extra_middleware=[RequireToolCall(… on_give_up="fail")]

agents/schedule/guard.py                  ← 变成薄薄一层 re-export,或直接删掉改引用
```

中间件层次不变(`create_gyt_agent` 里 Focus 在外、本件在内):

```
middleware=[FocusOnOwnWork(name), RequireToolCall(...)]
             外层:裁上下文          内层:守住「必须调工具」
```

## 7. 失败模式

| 新代码路径 | 一种真实的生产失败 | 有测试? | 有错误处理? | 工友看得见? |
|---|---|---|---|---|
| `RequireToolCall` 重试 | 模型两次都不调工具 | T2 补 | D2 → 硬错 | ✅ 人话错误 |
| `on_give_up="fail"` | `fail_msg` 写成了内部术语 | 无 | — | ⚠️ 需人工把关文案 |
| 验收读 `data.today` | `list_tasks` 那步本身失败,拿不到 today | T4 补 | 需显式处理 | — |
| 验收 dump 轨迹 | 目录不可写 | 无 | 需 try/except,**绝不能因此吞掉原始失败** | — |

**0 个 critical gap**(没有「无测试 + 无错误处理 + 静默」的组合)。

⚠️ 一条要人工把关的:`fail_msg` 是工友直接看到的字符串,必须是工地师傅的人话,
不许出现「Envelope」「tool_call」这类词。这条机器测不出来。
