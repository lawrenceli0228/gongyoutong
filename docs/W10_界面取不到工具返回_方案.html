2 / Why not

为什么不能靠改 output_mode 解决

graph.py 的 OUTPUT_MODE = "last_message" 是刻意选的,它自己的注释写着:

「选它而不是 full_history,是因为工地场景里子 Agent 的中间步骤 (检索到的 20 段原文、DXF 里的几百个实体)对调度决策没用, 全带回来只会把 supervisor 的上下文撑爆、烧掉额度。」

改成 full_history 等于用每一次对话的成本与稳定性去换几张卡片。不划算。

订阅 subgraphs 也不行:那样能在实时流里看到,但刷新页面就没了 —— 而留档文书是要事后回来取的东西。

3 / Fix

把操作台与取件从聊天流里解耦

处置面板是操作台,不是聊天产物。它该有自己的入口和自己的数据源。 仓里有现成的先例:W7 的打卡面板 —— 界面上一个常驻按钮 → 点开面板 → 直连 HTTP 端点, 一个字都不经过聊天流。W9 的处置面板本来就该长这样。

7.2 挖出一个比 W10 更早、形状完全相同的洞

本机容器从来没服务过任何一条自定义 HTTP 路由

⚠️ 那条「十条路由都挂进了 webapp」的单元测试当时也是绿的 —— 它在宿主 Python 进程里直接 import,根本不经过容器。详见 TODO-46。

7.3 手工验当场抓到的两个 bug(单测全绿时它们都在)

两个是同一类:「点了,但屏幕上还写着旧的」。

  1. 确认之后徽章还写「待确认」 —— patchHazard 改了 status, 而渲染用的是 status_display(后端按旧状态拼好的那句中文)。 工友会以为没点成、再点一次,而下一颗按钮是签发法律文书。
  2. 签发之后那一行还写「还没下过整改期限」 —— 动作回执的 data 形状是冻结的,带不回 due_date。改成动作成功后从详情端点回填权威值 (那份数据本来就要拉)。
这两条正是 §5 那句「不许只看测试绿」要防的东西

它们不在任何断言的射程里:后端对、库里对、类型对、213 条纯函数测试全绿 —— 只有人眼看得见。

7.4 一次真实的数据丢失

实现途中,某条泳道跑变异测试还原时执行了 git checkout -- src/gyt/supervision_api.py —— 而那个文件当时从未提交,610 行实现整个被抹掉。

从该泳道的 transcript 回放它的 20 次 Edit 恢复了(.pyc 已被重编译,那条路是死的)。 恢复件通过了另一个泳道独立写成的 923 行行为测试 —— 这是这次恢复最强的交叉验证。

教训是编排上的,不是谁的手误

「所有泳道不要 commit」导致没有任何东西受 git 保护。 并行开工时应当尽早提交(哪怕是 WIP),让 git checkout 有东西可回滚。
