2 / Why not

为什么不能靠改 output_mode 解决

graph.py 的 OUTPUT_MODE = "last_message" 是刻意选的,它自己的注释写着:

「选它而不是 full_history,是因为工地场景里子 Agent 的中间步骤 (检索到的 20 段原文、DXF 里的几百个实体)对调度决策没用, 全带回来只会把 supervisor 的上下文撑爆、烧掉额度。」

改成 full_history 等于用每一次对话的成本与稳定性去换几张卡片。不划算。

订阅 subgraphs 也不行:那样能在实时流里看到,但刷新页面就没了 —— 而留档文书是要事后回来取的东西。

3 / Fix

把操作台与取件从聊天流里解耦

处置面板是操作台,不是聊天产物。它该有自己的入口和自己的数据源。 仓里有现成的先例:W7 的打卡面板 —— 界面上一个常驻按钮 → 点开面板 → 直连 HTTP 端点, 一个字都不经过聊天流。W9 的处置面板本来就该长这样。

   └ 工具返回 ✂ 被砍掉              └ 点开面板

🔴 筛子逻辑不许再写第四份

同一套判据已经有三份(端点闸门 / _advise / 前端 availableActions, 见 TODO-45 A 组)。list_hazards 的 scope 筛子与超期判定在 agents/supervision/tools.py,而那个模块会拉 langchain 栈。

做法:把纯逻辑抽到 agents/supervision/scoping.py(零 langchain 依赖), tools.py 与 supervision_api.py 都 import 它。方向合法 —— supervision_api 已经 import agents.supervision.documents。

3.3 巡检记录卡:同一个根因,单独一批

本批只记账,不做 —— 范围,而且它牵扯 report 与 hazards 的关系,该单独想清楚。

5 / Verify

验证怎么做
不许只看「测试绿」

这个洞的全部特征就是:后端对、测试绿、界面上什么都没有。

  1. 端到端手工:传照片 → 按钮徽章出现计数 → 点开看到两条 pending → 确认 → 严重那条出现「签发暂停令」→ 签发 → 三张下载卡 → 点开能下到 docx

  4. 新端点的鉴权照 checkin_api 同款(设令牌后无钥匙必拒)
