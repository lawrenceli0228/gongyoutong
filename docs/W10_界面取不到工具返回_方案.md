# W10 界面拿不到任何工具返回 —— 根因与修法

> 2026-08-16 手工点界面时发现。**不是 W9 引入的**,W9 只是又往这个洞里放了一件东西。
> 影响面比看上去大:**巡检记录卡也从来没显示过**,而 CLAUDE.md 把它当成在用的功能写着。

---

## 0. 一句话

**supervisor 的 `output_mode="last_message"` 把子 Agent 的工具返回丢掉了,
而前端所有「从工具返回渲染出来的卡片」都挂在那份返回上 —— 于是它们一张都渲染不出来。**

不是代码写错,是**入口挂在了架构会丢弃的东西上**。

## 2. 为什么不能靠改 `output_mode` 解决

`graph.py` 的 `OUTPUT_MODE = "last_message"` 是**刻意选的**,它自己的注释写着:

> 选它而不是 `"full_history"`,是因为工地场景里子 Agent 的中间步骤(检索到的 20 段原文、
> DXF 里的几百个实体)对调度决策没用,全带回来只会把 supervisor 的上下文撑爆、烧掉额度。

改成 `full_history` 等于用**每一次对话的成本与稳定性**去换几张卡片。不划算。

订阅 `subgraphs` 也不行:那样能在**实时流**里看到,但刷新页面就没了 ——
而留档文书是要事后回来取的东西。

---

## 3. 修法:把操作台与取件从聊天流里解耦

**结论:处置面板是操作台,不是聊天产物。** 它该有自己的入口和自己的数据源。

仓里有现成的先例:**W7 的打卡面板**(`checkin.tsx`)。它就是「界面上一个常驻按钮 →
点开面板 → 直连 HTTP 端点」,一个字都不经过聊天流。W9 的处置面板本来就该长这样。

```
 现在(坏)                          改后(照 checkin 的先例)
 ─────────────────────            ──────────────────────────
 聊天流                            界面常驻按钮(带待确认计数)
   └ 工具返回 ✂ 被砍掉                └ 点开面板
       └ 隐患卡(渲不出)                  └ GET  /supervision/hazards      清单
           └ 处置面板(到不了)            └ GET  /supervision/hazards/{no} 详情+证据链
                                          └ POST /supervision/confirm 等七个(已有)
```

### 3.1 后端补三个端点

| 端点 | 干什么 | 备注 |
|---|---|---|
| `GET /supervision/hazards` | 清单,支持 `scope`(在办/待确认/超期/全部;2026-09-18 加「待复查」)与 `project_id` | 复用现有筛子语义 |
| `GET /supervision/hazards/{hazard_no}` | 单条详情 + 证据链(含每次复查的照片编号) | F4 修完的那些字段终于有出口 |
| `POST /supervision/reject` | 否决一条 pending | **TODO-45 B 组**:`db.delete_pending()` 现在零调用入口 |

**🔴 筛子逻辑不许再写第四份。** 现在同一套判据已经有三份(端点闸门 / `_advise` /
前端 `availableActions`,见 TODO-45 A 组)。`list_hazards` 的 scope 筛子与超期判定
在 `agents/supervision/tools.py` 里,而那个模块会拉 langchain 栈。

做法:把**纯逻辑**(scope 筛选 + 超期判定)抽到 `agents/supervision/scoping.py`
(零 langchain 依赖),`tools.py` 与 `supervision_api.py` 都 import 它。
方向合法 —— `supervision_api` 已经 import `agents.supervision.documents`。

### 3.2 前端加常驻入口

照 `frontend/src/components/thread/index.tsx:593` 的 `<CheckinEntry />` 那一行,
在旁边加一个 `<SupervisionEntry />`:

- **带待确认计数徽章** —— 没有它,没人知道有东西要确认(pending 不催办,是 D17 定的)
- 点开就是现有的 `supervision.tsx` 面板,数据源换成新的 GET 接口
- 「否决」按钮接上新端点,不再只是本地划掉

⚠️ 这要改 `thread-index.tsx` 覆盖件(已有一件,DXF 上传那组的)。
`apply_override` 计数 **12 不变**(改的是已有件);`install_new_file` 仍是 7。

### 3.3 巡检记录卡:同一个根因,单独一批

它是 W3/W5 的洞,不是 W9 的。修法同源但要另开一批:
巡检记录的 docx 是 `artifacts` 里的产物,而它**不在** `hazard_docs` 里,
所以现有的详情接口捞不到它。要么给它一个产物列表接口,要么把它挂进隐患的证据链。

**本批只记账,不做**(理由:范围;而且它牵扯 report 与 hazards 的关系,该单独想清楚)。

### 7.3 手工验当场抓到的两个 bug(单测全绿时它们都在)

两个是同一类:**「点了,但屏幕上还写着旧的」**。

1. **确认之后徽章还写「待确认」** —— `patchHazard` 改了 `status`,而渲染用的是
   `status_display`(后端按**旧状态**拼好的那句中文)。工友会以为没点成、再点一次,
   而下一颗按钮是签发法律文书。
2. **签发之后那一行还写「还没下过整改期限」** —— 动作回执的 `data` 形状是冻结的,
   带不回 `due_date`。改成动作成功后从详情端点回填权威值(那份数据本来就要拉)。

**这两条正是 §5 那句「不许只看测试绿」要防的东西。** 它们不在任何断言的射程里:
后端对、库里对、类型对、213 条纯函数测试全绿 —— 只有人眼看得见。

第三条是测试自己的偶发红:`_new_hazard` 造编号没走撞号重试,同一秒造几十条时
会撞 UNIQUE。偶发红比没测试更坏,它教会人「再跑一遍就好了」。

### 7.4 一次真实的数据丢失,以及它的教训

实现途中,某条泳道跑变异测试还原时执行了
`git checkout -- src/gyt/supervision_api.py` —— 而那个文件当时**从未提交**,
610 行实现整个被抹掉。

从该泳道的 transcript 回放它的 20 次 Edit 恢复了(`.pyc` 已被重编译,那条路是死的)。
**恢复件通过了另一个泳道独立写成的 923 行行为测试** —— 这是这次恢复最强的交叉验证。

教训是编排上的,不是谁的手误:**我让所有泳道「不要 commit」,结果没有任何东西
受 git 保护。** 并行开工时应当尽早提交(哪怕是 WIP),让 `git checkout` 有东西可回滚。

### 7.5 验证做到哪一步

`docs` 里的验证清单(§5)四条全部实做,证据如下:

- **端到端手工**:传→确认→定级→签发→三份下载卡→**点开真下到 37615 字节的合法 docx**,
  正文里编号、级别、整改期限「8月19日(周三)」、照片编号全对。
- **刷新页面再来一遍**:刷新后徽章仍在(数字随台账变)、面板重开、
  **证据链里昨天签的文书照样取得回来** —— 这条是 W10 的全部意义。
- **库级对照**:每一步都直查 `data/gyt.sqlite3`。否决那条尤其要紧:
  成功时确认那一行**真没了**,被 409 拒时确认那一行**还在** ——
  「拒了」和「拒了但也删了」在回执上长得一模一样。
- **鉴权**:两条 GET 各一条单测(设令牌后无钥匙必拒)。**没做**活体令牌翻转,
  本机没配令牌;这一条以单测为准,如实记账。

顺带活体验证了 D7:新建隐患编号是 `GYT-H-20260816-**1845**07`,而本机时钟是 20:45
—— 这台机器在 AEST(UTC+10),编号用的是香港时间(UTC+8)。
**用宿主时区的话会写成 `2045`。**
