# W10 界面拿不到任何工具返回 —— 根因与修法

> 2026-08-16 手工点界面时发现。**不是 W9 引入的**,W9 只是又往这个洞里放了一件东西。
> 影响面比看上去大:**巡检记录卡也从来没显示过**,而 CLAUDE.md 把它当成在用的功能写着。

---

## 0. 一句话

**supervisor 的 `output_mode="last_message"` 把子 Agent 的工具返回丢掉了,
而前端所有「从工具返回渲染出来的卡片」都挂在那份返回上 —— 于是它们一张都渲染不出来。**

不是代码写错,是**入口挂在了架构会丢弃的东西上**。

---

## 1. 证据(全部实测,不是推理)

### 1.1 后端干完了活

传一张工地照片,safety 正常判读、隐患正常入库:

```
GYT-H-20260816-171404-7194  未穿反光衣   现场「一般」→ 监理「一般」  pending
GYT-H-20260816-171404-f95e  临边无防护   现场「较大」→ 监理「严重」  pending
```

`pending`(D17)、`project_id=''`(D6,没选工地)—— 全对。

### 1.2 而线程状态里没有那条工具返回

```
[human ]
[ai    ] supervisor   → transfer_to_safety
[tool  ] transfer_to_safety
[ai    ] safety                      ← 只剩这条纯文本
[ai    ] safety       → transfer_back_to_supervisor
[tool  ] transfer_back_to_supervisor
[ai    ] supervisor
```

**7 条消息,没有 `analyze_site_photo`。** 而隐患卡的判据是
「工具名在白名单 **且** `data.hazards` 存在」。

### 1.3 三条路全堵

| 取数路径 | 实测结果 |
|---|---|
| 线程状态 `/threads/{id}/state` | 9 条线程,业务工具返回 **0** |
| 历史检查点 `/threads/{id}/history` | 全部检查点,业务工具返回 **0** |
| 实时流 `useStream` | `frontend/src/providers/Stream.tsx:86` **没有 `subgraphs` 选项** |

子 Agent 是编译后的子图,它内部的 `ToolMessage` 属于子图命名空间 ——
不订阅 `subgraphs` 就不会流出来;而 `output_mode="last_message"` 决定了它也不进状态。

### 1.4 所以这不只是 W9 的问题

`scripts/frontend-overrides/tool-calls.tsx` 里三张卡,判据分别是:

| 卡 | 判据 | 能否命中 |
|---|---|---|
| 巡检记录(W3/W5 就有) | 工具名 `=== render_inspection_report` | ❌ 从来没有 |
| 监理文书(W9) | 信封 `data.documents` 是数组 | ❌ |
| 隐患台账(W9) | 工具名在白名单 **且** `data.hazards` | ❌ |

**三张全部不可达。** 而 CLAUDE.md 的「前端覆盖件」一节把巡检记录卡写成在用的功能,
整条 `ARTIFACT_BASE` 同源清单(`human.tsx` + `tool-calls.tsx` + `checkin.tsx` +
Dockerfile ARG + compose + Caddy)就是为了让那张卡能取件而建的 —— **那条链一直是死的。**

> ⚠️ 这条洞**仓库自己记过**:验收 dump 的头部和 `read_backend_today` 的 docstring 都写着
> 「轨迹看不见子 Agent 的工具调用和工具返回 —— 那是 `output_mode=last_message` 砍掉的」。
> 知道归知道,前端还是照着「工具返回会到界面上」写了三张卡。

## 2. 为什么不能靠改 `output_mode` 解决

`graph.py` 的 `OUTPUT_MODE = "last_message"` 是**刻意选的**,它自己的注释写着:

> 选它而不是 `"full_history"`,是因为工地场景里子 Agent 的中间步骤(检索到的 20 段原文、
> DXF 里的几百个实体)对调度决策没用,全带回来只会把 supervisor 的上下文撑爆、烧掉额度。

改成 `full_history` 等于用**每一次对话的成本与稳定性**去换几张卡片。不划算。

订阅 `subgraphs` 也不行:那样能在**实时流**里看到,但刷新页面就没了 ——
而留档文书是要事后回来取的东西。

---

## 3. 修法:把操作台与取件从聊天流里解耦

**结论:处置面板是操作台,不是聊天产物。** 它该有自己的入口和自己的数据源。

仓里有现成的先例:**W7 的打卡面板**(`checkin.tsx`)。它就是「界面上一个常驻按钮 →
点开面板 → 直连 HTTP 端点」,一个字都不经过聊天流。W9 的处置面板本来就该长这样。

```
 现在(坏)                          改后(照 checkin 的先例)
 ─────────────────────            ──────────────────────────
 聊天流                            界面常驻按钮(带待确认计数)
   └ 工具返回 ✂ 被砍掉                └ 点开面板
       └ 隐患卡(渲不出)                  └ GET  /supervision/hazards      清单
           └ 处置面板(到不了)            └ GET  /supervision/hazards/{no} 详情+证据链
                                          └ POST /supervision/confirm 等七个(已有)
```

### 3.1 后端补三个端点

| 端点 | 干什么 | 备注 |
|---|---|---|
| `GET /supervision/hazards` | 清单,支持 `scope`(在办/待确认/超期/全部)与 `project_id` | 复用现有筛子语义 |
| `GET /supervision/hazards/{hazard_no}` | 单条详情 + 证据链(含每次复查的照片编号) | F4 修完的那些字段终于有出口 |
| `POST /supervision/reject` | 否决一条 pending | **TODO-45 B 组**:`db.delete_pending()` 现在零调用入口 |

**🔴 筛子逻辑不许再写第四份。** 现在同一套判据已经有三份(端点闸门 / `_advise` /
前端 `availableActions`,见 TODO-45 A 组)。`list_hazards` 的 scope 筛子与超期判定
在 `agents/supervision/tools.py` 里,而那个模块会拉 langchain 栈。

做法:把**纯逻辑**(scope 筛选 + 超期判定)抽到 `agents/supervision/scoping.py`
(零 langchain 依赖),`tools.py` 与 `supervision_api.py` 都 import 它。
方向合法 —— `supervision_api` 已经 import `agents.supervision.documents`。

### 3.2 前端加常驻入口

照 `frontend/src/components/thread/index.tsx:593` 的 `<CheckinEntry />` 那一行,
在旁边加一个 `<SupervisionEntry />`:

- **带待确认计数徽章** —— 没有它,没人知道有东西要确认(pending 不催办,是 D17 定的)
- 点开就是现有的 `supervision.tsx` 面板,数据源换成新的 GET 接口
- 「否决」按钮接上新端点,不再只是本地划掉

⚠️ 这要改 `thread-index.tsx` 覆盖件(已有一件,DXF 上传那组的)。
`apply_override` 计数 **12 不变**(改的是已有件);`install_new_file` 仍是 7。

### 3.3 巡检记录卡:同一个根因,单独一批

它是 W3/W5 的洞,不是 W9 的。修法同源但要另开一批:
巡检记录的 docx 是 `artifacts` 里的产物,而它**不在** `hazard_docs` 里,
所以现有的详情接口捞不到它。要么给它一个产物列表接口,要么把它挂进隐患的证据链。

**本批只记账,不做**(理由:范围;而且它牵扯 report 与 hazards 的关系,该单独想清楚)。

## 4. 不在范围

| 项 | 为什么 |
|---|---|
| 改 `output_mode` 为 `full_history` | 拿每次对话的成本与稳定性换几张卡片,不划算(§2) |
| 订阅 `subgraphs` | 刷新即失,而留档文书要事后回来取 |
| 巡检记录卡 | 同一根因但属 W3/W5,牵扯 report↔hazards 的关系,单独一批(§3.3) |
| TODO-45 A 组那三条跨实现漂移 | 与本方案正交;但 §3.1 抽 `scoping.py` 时**别再制造第四份** |

## 5. 验证怎么做

**不许只看「测试绿」。** 这个洞的全部特征就是:后端对、测试绿、界面上什么都没有。

1. **端到端手工**:传照片 → 按钮徽章出现计数 → 点开看到两条 pending →
   确认 → 严重那条出现「签发暂停令」→ 签发 → 三张下载卡 → **点开能下到 docx**
2. **刷新页面再来一遍** —— 这一条是关键:现在的卡片就算 live 能渲染,刷新也会没;
   新入口必须刷新后照样在
3. **库级对照**:界面上显示的条数/状态,与直接查 `data/gyt.sqlite3` 一致
4. 新端点的鉴权照 `checkin_api` 同款(设令牌后无钥匙必拒)
